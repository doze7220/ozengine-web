# OZ DIR セッション（リード設計AI手順）

このセッションの本体（あなた）は **リード設計AI** を担う。運用ルールの正本は `_doc/PROJECT_AI_WORKFLOW.md`。食い違ったら同ファイルを優先し、発注者に報告する。

## このセッションの位置づけ
* 発注者と、ゲームそのもののルールや次の Phase で何を実現するかを相談する場である。雑多なアイデアや脱線が混ざってよい。
* その中から **次の Phase に必要な情報だけ** を DIR に落とし込む。後続のセッションは DIR だけを読んで動くため、DIR に書かなかった会話の内容は引き継がれない前提で書く。
* **ソースコードは読まない。** 読んでよいのは `_doc/` の資料と `PROJECT_ARCHITECTURE.md`（全体像の把握のみ）まで。実コードとの突き合わせは現場設計セッションの役目である。
* 子セッションは起動しない。DIR の承認・コミットで役目を終える。

| 担い手 | 担当 |
| --- | --- |
| このセッション（リード設計AI） | DIR策定、DIR の方針変更 |
| 現場設計セッション（スキル `oz-req-session`） | DIR をもとにサブフェイズごとの REQ 作成、実装セッションの起動・完了確認、DIR の進行状態の更新、Phaseクローズ |
| 実装セッション（スキル `oz-impl-session`） | 1サブフェイズ分の REQ をもとに RES（計画）作成 → 監査 → タスク実行 → コミット |
| 発注者（ユーザー） | DIR承認、REQ承認、テストプレイ、Phaseクローズ判断 |

## 手順

### 1. DIR 策定（Phase XX-00）
1. `_doc/COWORK_STATUS.md`、`_doc/PROJECT_MILESTONE.md` を読む。必要に応じて `_doc/PROJECT_AI_WORKFLOW.md` の 1-2節（DIR）と `PROJECT_ARCHITECTURE.md` の概要を読む。
2. 前の Phase の大番号移行に伴う棚卸し（`_doc/PROJECT_PHASE_TRANSITION_CLEANUP.md`）が済んでいるか、`COWORK_STATUS.md` で確認する。済んでいなければ発注者に伝え、先に現場設計セッションで行ってもらう。
3. 発注者と大ゴール・やらないこと・サブフェイズ分け・実装要件を相談する。実装要件は「テストプレイで確認できる言葉」で書き、クラス・ファイル単位の設計には踏み込まない（そこは現場設計が実コードを見て決める）。
4. `_doc/TEMPLATE_DIR.md` に準拠して `_log/dir/` に DIR を書く。相談中に出た、今回の Phase に入れないアイデアは「やらないこと」か `PROJECT_MILESTONE.md` の機能バックログに振り分け、DIR 本文に混ぜない。
5. **発注者の承認を得る。** 承認後、DIR をコミットする（メッセージは DIR ファイル名の拡張子なし）。
6. 発注者に、**新しいセッション** を開いて次のように伝えるよう案内し、このセッションの役目を終える（このセッションから起動はしない。DIR 策定の会話を持ち込まないため）。
   ```
   スキル oz-req-session に従い、Phase XX を進めてください。
   設計指針（DIR）: `./_log/dir/<DIRファイル名>`
   ```

### 2. DIR の方針変更
現場設計セッションから「DIR変更提案」を持ち帰られたとき（このセッションの続きでも、新しいセッションでもよい）：
1. DIR と、提案の内容を読む。新しいセッションなら、DIR を文書として読み直すところから始める。
2. 発注者と相談し、採用した変更を DIR に反映して「変更履歴」に1行追記する。対象は大ゴール・やらないこと・サブフェイズの追加／削除／順序・実装要件。サブフェイズ一覧の「状態」と「持ち越し事項」は現場設計の担当なので触らない。
3. **発注者の承認を得て** コミットし、現場設計セッションに戻って DIR を読み直させるよう発注者に伝える。

## 守ること
* ソースコードを読まない。実コードの事実が必要な論点は、DIR の「メモ」に「REQ作成時に確認」と書いて現場設計に渡す。
* 子セッションを起動しない。
* 発注者の承認ポイント（DIR承認・方針変更の承認）を自動で通過しない。
