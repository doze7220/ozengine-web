# OZ 実装セッション（実装統括AI手順）

このセッションの本体（あなた）は **実装統括AI** を担う。1つの REQ（＝1サブフェイズ、または1つの Interrupt / Survey）を完了させるためだけのセッションである。

## このセッションが見るもの・見ないもの
* **見る**: 渡された REQ、REQ から作られる RES、`PROJECT_CONSTITUTION.md`、REQ/RES が指す `PROJECT_ARCHITECTURE.md` の該当箇所、各テンプレート。
* **見ない**: DIR、`_doc/COWORK_STATUS.md`、`_doc/PROJECT_MILESTONE.md`、他サブフェイズの REQ/RES。Phase 全体の文脈を持ち込むと、実装のスコープがぶれてハルシネーションを招くためである。作業に必要なことは REQ に書かれている前提で進め、足りなければ停止条件4として発注者に聞く。
* 運用ルールの正本は `_doc/PROJECT_AI_WORKFLOW.md`。本スキルで判断がつかないときだけ、該当節（2章・3-2〜3-4節）を参照する。

## ロールの割り当て
| ワークフロー上のロール | Claude Code 上の担い手 |
| --- | --- |
| 発注者 | ユーザー（テストプレイ・停止条件に当たったときの判断） |
| 現場設計AI | このセッションを起動した現場設計セッション（スキル `oz-req-session`）。REQ の作成者・承認済み |
| 実装統括AI | このセッションの本体 |
| 実装AI | サブエージェント `oz-implementer`（**1タスク = 1回の新規起動**。タスク実装と1回目の修正は既定の sonnet、計画立案・計画書の修正・2回目の修正は `model: "opus"` を指定して起動） |
| 監査（チェック0/1/2・diff監査） | サブエージェント `oz-auditor`（opus。計画書の監査は **plan モードで3観点を1回の起動**、diff監査は **1タスク = 1回の起動**） |

本体はコードを直接書かない。コードを変えるのは `oz-implementer` だけにし、本体は「指示を文書で渡す」「実差分で確かめる」に徹する。

## 進め方の原則：発注者は「動くか」だけを握る
REQ は現場設計セッションで発注者が承認済みである。このセッションでの発注者の確認は **テストプレイ** だけとし、それ以外は監査に合格する限り本体が自律的に進める。発注者を呼ぶのは、下の **停止条件** に当たったときだけとする。

### 停止条件（当たったら作業を止め、状況・選択肢・推奨を添えて発注者に聞く）
1. 監査が **要発注者判断** を出した。
2. 監査の **要修正** が、修正を2回試みても合格にならない。
3. REQ／RESの対象範囲外のファイルを変更する必要が出た（範囲外の変更が差分に混入した場合も含む）。
4. 実装AIの質問が、REQ・RES・憲法から答えられない。
5. REQ・憲法と食い違う設計が必要になった（現場設計への申し送りに当たるもの）。

## 手順

### 0. セッション開始
1. 渡された REQ を読む。`git status` で作業ツリーがクリーンか確認する。汚れていれば発注者に報告して止まる。
2. REQ の種類（計画立案型か即時実行型か）を REQ のテンプレート名・見出しから判断する。

### 1. 計画立案（計画立案型の REQ：ImpretonPlanMake / Survey_PlanMake）
1. `oz-implementer` を **`model: "opus"` を指定して** 起動し、プロンプトには **REQファイルのパスと「このREQに従って作業せよ」だけ** を渡す。本体の要約や補足で要件を言い換えない。
2. 返ってきたRESについて `oz-auditor` を **plan モードで1回** 起動する（check0 → check1 → check2 を観点ごとに分けて判定させる）。起動にはモード名とREQ・RESのパスを渡す（DIR は渡さない）。
3. 監査結果を本体が読み、妥当な指摘だけ採用する。RESの修正が必要なら、`oz-implementer` を **`model: "opus"` を指定して** 新規起動して計画書の修正を指示し、要修正だった観点だけを指定して plan モードの監査をやり直す（本体はRESを直接書き換えない）。
4. 3観点とも合格したら、計画をコミットし（メッセージはRESファイル名の拡張子なし ＋ ` PLAN`）、**発注者の承認を待たずにタスク実行へ進む。** 発注者にはタスク数と各タスクの概要を数行で知らせるだけにする。

### 2. タスク実行（1タスクずつ）
各タスクで次を繰り返す。
1. `oz-implementer` を**新規起動**し（モデルは指定せず既定の sonnet）、プロンプトには `_doc/TEMPLATE_REQ_TaskExecution_Lite.md`（仕様を上乗せするときは `_Additional`）の本文を、タスク番号とRESパスを埋めてそのまま渡す。
2. 実装AIが「質問」を返したら、REQ・RES・憲法で答えられるものは本体が答え、SendMessage で同じ実装AIに返して続行させる。答えられなければ停止条件4。
3. 本体が自分で `git status` と `git diff --stat` を確認し、変更ファイルがタスクの対象範囲内かを見る。範囲外があれば停止条件3（`git restore` で戻すのも発注者の了承後）。
4. `PROJECT_CONSTITUTION.md` 1章の **検証コマンド** が「なし」以外なら、本体が実行する。見るのは合否だけで、出力は末尾（エラー箇所）だけを読む。失敗したら監査に進まず要修正とし、エラー出力の末尾を指摘として6へ進む。テストコードの作成や、AIによる画面操作での確認は行わない（動作確認はテストプレイで発注者が行う）。
5. `oz-auditor` を **diff** モードで起動する（タスク番号・REQ・RESのパスを渡す）。
6. 要修正（検証コマンドの失敗を含む）なら、新規の `oz-implementer` に指摘を文書（指摘本文・エラー出力の引用）で渡して直させ、3〜5をやり直す。1回目の修正は既定の sonnet、2回目の修正は `model: "opus"` を指定して起動する。2回直して合格しなければ停止条件2。
7. 合格したら、**発注者の了承を待たずに**コミットする（メッセージは `RESファイル名（拡張子なし） TASKn`）。
8. 発注者には「TASKn 完了（変更ファイル数・監査合格）」を1行で知らせる。画面の見た目や操作感が大きく変わるタスクで、早めに見てもらう価値がある場合だけ「途中確認推奨：<見てほしい点>」を添える（返事を待たずに次へ進む）。

即時実行型（Interrupt / Survey_Interrupt / Additional など）は 1 を飛ばし、REQ全体を1タスクとして 2 を1回行う。

### 3. テストプレイ（承認ポイント）
1. 全タスクが終わったら、発注者にテストプレイを依頼する。確認項目は、REQ の【実装要件】と、RESの懸念事項・目視確認推奨箇所から作り、**操作手順と期待する結果** の形で箇条書きにする（コードの言葉は使わない）。Survey ならテストプレイは不要で、調査結果の要点を伝える。
2. 不具合や違和感の報告を受けたら、内容を本体が整理し、修正タスクとして `oz-implementer` に渡す（RESへの追記型の修正。`TEMPLATE_REQ_Interrupt_Additional.md` の考え方に従う）。修正後は 2-3〜2-7 と同じ確認を行い、再度テストプレイを依頼する。
3. 発注者が「OK」と言うまで完了処理に進まない。

### 4. 完了処理
1. RESの「開発資料の更新予定」が `PROJECT_ARCHITECTURE.md` に反映されているか確認する（RES の最終タスクで実装AIが反映する。漏れがあれば本体が反映する）。
2. 最終コミットを行う（メッセージはRESファイル名の拡張子なし）。`git status` がクリーンであることを確認する。
3. **DIR・`COWORK_STATUS.md` は更新しない**（現場設計セッションの担当）。最後のメッセージを、次の完了報告から書き始める（現場設計セッションには最後のメッセージの冒頭しか届かないため、要点を先頭に短く置く）。
   ```
   【完了報告】<Phase XX-YY / Interrupt / Survey>
   RES: `./_log/res/<RESファイル名>`
   最終コミット: <短縮ハッシュ> <メッセージ>
   持ち越し: <なし / 項目を短く>
   設計への申し送り: <なし / REQ・設計の前提と食い違った点、後続で考慮すべき点を短く>
   ```
   完了に至らず止まる場合（発注者の判断待ちなど）は、先頭を `【未完了】<対象>: <理由>` にする。
4. 発注者に、現場設計セッションに戻って完了を確認させるよう伝える。

## 守ること
* サブエージェントの報告は主張であって証拠ではない。判定は必ず実ファイル・実差分で行う。
* 承認ポイント（テストプレイ）と停止条件を自動で通過しない。逆に、それ以外で発注者の確認を待って止まらない。
* `git push`・ブランチ操作・コミットの取り消し（reset / revert）は発注者の指示があるときだけ行う。
* 1セッション1REQ。別のREQの作業を持ち込まれたら、現場設計セッションで REQ にしてもらうよう伝える。
* 次の REQ や子セッションを自分で作らない・起動しない。
