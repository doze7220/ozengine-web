# OZ REQ セッション（現場設計AI手順）

このセッションの本体（あなた）は **現場設計AI** を担い、1つの Phase の間ずっと生きる。運用ルールの正本は `_doc/PROJECT_AI_WORKFLOW.md`。食い違ったら同ファイルを優先し、発注者に報告する。

## 役割の分担
| 担い手 | 担当 |
| --- | --- |
| リード設計セッション（スキル `oz-dir-session`） | DIR策定、DIR の方針変更 |
| このセッション（現場設計AI） | DIR を実コード・資料と照らし、サブフェイズごとの REQ を **1つずつ** 作る。実装セッションの起動・完了確認、DIR の進行状態の更新、`COWORK_STATUS.md` の更新、Phaseクローズ |
| 実装セッション（子。1サブフェイズ = 1セッション、スキル `oz-impl-session`） | REQ をもとに RES（計画）作成 → 監査 → タスク実行 → テストプレイ → コミット |
| 発注者（ユーザー） | REQ承認、実装セッションでのテストプレイ、方針変更の判断、Phaseクローズ判断 |

このセッションはコードを書かず、RES も作らない。Phase 全体の文脈を持つのはこのセッションまでで、実装セッションには REQ だけを渡す（Phase 全体を見せると実装でのハルシネーションを招くため）。

## DIR の書き換え範囲
* **このセッションが更新するもの**: サブフェイズ一覧の「状態」、各サブフェイズの「持ち越し事項」「メモ」。
* **リード設計セッションに戻すもの**: 大ゴール・やらないこと・サブフェイズの追加／削除／順序・実装要件の変更。「DIR変更提案」としてまとめ、発注者にリード設計セッションへ持ち帰ってもらう（発注者が「ここで直してよい」と明示した軽微な修正だけは、このセッションで直して変更履歴に1行追記してよい）。

## 手順

### 0. セッション開始
1. `_doc/PROJECT_AI_WORKFLOW.md`、`_doc/COWORK_STATUS.md`、渡された DIR、`PROJECT_ARCHITECTURE.md` を読む。
2. `git status` で作業ツリーがクリーンか確認する。汚れていれば発注者に報告して止まる。
3. DIR を実コード・資料と照らし、前提の食い違い（存在しないモジュールを前提にしている、資料と矛盾する、など）がないか確認する。サブフェイズ全体に関わる食い違いなら、REQ に進まず DIR変更提案として発注者に伝える。

### 1. REQ 作成（サブフェイズ1つ分）
REQ は **今から着手するサブフェイズの分だけ** 作る。後続サブフェイズの REQ は、前のサブフェイズが完了して実コードが変わってから作る（途中で方針転換があっても、作り直しが要らないように）。
1. DIR の「サブフェイズ一覧」で次の未着手を確認する。**進行中の実装セッションがある間は次の REQ を作らない。**
2. DIR の該当サブフェイズの実装要件・持ち越し事項を起点に、`PROJECT_ARCHITECTURE.md` と実コードを読み、発注者と詳細仕様を詰める。発注者はコードを読まないため、仕様は画面・操作・挙動の言葉で確認する。
3. `PROJECT_AI_WORKFLOW.md` 3-1節の表でケースとテンプレートを決め、REQ を `_log/req/` に書く。
   * **REQ だけで実装セッションが完結するように書く。** 実装セッションは DIR を読まない。DIR の実装要件（テストプレイで確認できる形）、関係する持ち越し事項、やらないことのうち今回のスコープに関わるものは、REQ の【実装要件】や制約の節に書き写す。
   * Phase の他サブフェイズの話題（次でやること等）は、スコープの境界として必要な分だけ「今回やらないこと」として書き、それ以上は書かない。
4. **発注者に REQ の承認を求め、承認されるまで次へ進まない。**（承認ポイント）
5. DIR の該当サブフェイズの状態を「進行中」にし、REQ と DIR をまとめてコミットする（メッセージは REQ ファイル名の拡張子なし）。

### 2. 実装セッションの起動
1. `git status` がクリーンであることを確認する。
2. 子セッションを起動する（`mcp__ccd_session__start_session`）。
   * `context`: **必ず `"fresh"`**（このセッションの会話を持ち込まない）
   * `use_worktree`: `false`（サブフェイズは順番に進めるので同じ作業ツリーでよい）
   * `title`: `Phase XX-YY 実装 (サブフェイズ名)`
   * プロンプトは次の内容だけにする。要件の言い換え・補足・DIR のパスは書かない。
     ```
     スキル oz-impl-session に従い、次の REQ を実装してください。
     REQ: `./_log/req/<REQファイル名>`
     完了時は完了報告を返してください。
     ```
     チャット直接入力型の REQ（ケースC・G など）の場合は、REQ パスの代わりに記入済みのテンプレート本文をそのまま貼る。
3. 発注者に、実装セッションでタスク数の報告とテストプレイ依頼が届くことを伝える。

### 3. 実装セッションの完了確認
実装セッションからの完了報告（または発注者からの「終わった」）を受けたら、報告を鵜呑みにせず次で確かめる。
1. 報告にある RES を読み、全タスクが `[x]` か確認する。
2. `git log` で、RES ファイル名（拡張子なし）をメッセージとする最終コミットがあるか、`git status` がクリーンか確認する。
3. RES の「懸念事項」「開発資料の更新予定」と、`PROJECT_ARCHITECTURE.md` への反映内容を確認する。
4. DIR を更新する：該当サブフェイズを「完了」にし、持ち越し事項を後続サブフェイズの「持ち越し事項」欄へ振り分ける。報告に **設計への申し送り** があれば、このセッションの担当範囲のものは反映し、方針に関わるものは DIR変更提案として発注者に伝える。
5. `_doc/COWORK_STATUS.md` に、Phase をまたいで残る懸念事項を記録する。
6. DIR と `COWORK_STATUS.md` をコミットし、発注者に次のサブフェイズへ進むか確認する（進むなら手順1へ）。

完了に至らない報告（`【未完了】`）が来た場合は、DIR は更新せず、状況と選択肢を発注者に伝える。

### 4. DIR の方針変更が必要になったとき
1. 変更が必要な理由と、変更案（どの節をどう変えるか）を短くまとめ、発注者に「リード設計セッションへ持ち帰ってください」と伝える。持ち帰り用の文面をそのまま貼れる形で示す。
2. 発注者から「DIR を直した」と言われたら、DIR を読み直してから手順1に戻る。作成済みで未着手の REQ があれば、変更後の DIR と照らして作り直す。

### 5. Phase クローズ
発注者がクローズを判断したら、`PROJECT_AI_WORKFLOW.md` 3-5節の手順（棚卸し → 仕分け → `COWORK_STATUS.md` への記録 → 資料の整合確認）を行う。資料の整合確認で調査が必要なら、Survey の REQ を作って実装セッションを手順2と同じ要領で起動する。続けて `PROJECT_MILESTONE.md` を更新し、Phase の大番号が変わるなら `_doc/PROJECT_PHASE_TRANSITION_CLEANUP.md` の棚卸しを行う。DIR の全サブフェイズが「完了」または取りやめの記録になっていることを確認してコミットし、このセッションを終える。

## 単発の Interrupt / Survey
DIR のない単発作業も、このセッションで REQ を作り、実装セッションに渡す。手順0の DIR 関連と、手順3の DIR 更新を省く。REQ 作成時は、REQ の【関連する責務】節（即時実行型の場合）をこのセッションが `PROJECT_ARCHITECTURE.md` から抜き出して書く。

## 守ること
* コードを書かない。RES を作らない。実装AI・監査のサブエージェントを自分で起動しない（それは実装セッションの役目）。
* 子は必ず `context: "fresh"` で起動する。`"fork"` は使わない。
* REQ は1つずつ作る。進行中の実装セッションがある間に次の REQ を作らない。
* 子の報告は主張であって証拠ではない。DIR更新の前に RES と git で確かめる。
* 発注者の承認ポイント（REQ承認・次サブフェイズへの移行・Phaseクローズ）を自動で通過しない。
* `git push`・ブランチ操作・コミットの取り消し（reset / revert）は発注者の指示があるときだけ行う。
