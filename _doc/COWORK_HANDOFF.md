# COWORK_HANDOFF.md
## 運用ツール割り当てメモ（固定方針編）

---

### このファイルについて
* `PROJECT_AI_WORKFLOW.md` は特定のAI製品名を含まない普遍的な役割構造として書かれている。本ファイルは「現在どのツールがどの役を担っているか」と、その判断理由を記録する運用メモである。ツールを乗り換えるときは本ファイルとスキル・エージェント定義だけを書き換える。
* 現在の進捗・懸念事項はここに書かない（`_doc/COWORK_STATUS.md` に書く）。
* ファイル名の `COWORK_` は、Claude Cowork を設計AIに使っていた頃の名残である。

### 1. ロールとツールの割り当て（Claude Code 単独運用）

| ワークフロー上のロール | 担い手 | 手順の正本 |
| --- | --- | --- |
| 発注者 | ユーザー（人間） | `_doc/PROJECT_README.md` |
| リード設計AI | リード設計セッション（DIR策定・方針変更。ソースは読まない。子は起動しない） | `.claude/skills/oz-dir-session/SKILL.md` |
| 現場設計AI | 現場設計セッション（Phase の間ずっと生きる。発注者が DIR を渡して新しく開く。REQ を1つずつ作り、実装セッションを起動・完了確認し、DIR の進行状態を更新する） | `.claude/skills/oz-req-session/SKILL.md` |
| 実装統括AI | 実装セッション（現場設計セッションから新規コンテキストで起動。1 REQ = 1セッション。DIR は読まない） | `.claude/skills/oz-impl-session/SKILL.md` |
| 実装AI | サブエージェント `oz-implementer`（1タスクごとに新規起動） | `.claude/agents/oz-implementer.md` |
| 監査（チェック0/1/2・diff監査） | サブエージェント `oz-auditor`（読み取り専用。計画書の監査は plan モードで3観点を1回の起動、diff監査は1タスクごとに新規起動） | `.claude/agents/oz-auditor.md` |

`CLAUDE.md` は全セッション・全サブエージェントに自動で読み込まれるため、最小限の案内のみを書く。`PROJECT_AI_WORKFLOW.md` を `CLAUDE.md` から読み込ませてはならない（実装AIに読ませない設計のため）。

### 2. 判断の理由

| 項目 | 判断 | 理由（要約） |
| --- | --- | --- |
| 受け入れ基準／検証証跡の必須化 | **不採用** | 意図とのズレは結局テストプレイでしか判定できない。スコープ逸脱はGit diffの方が確実に拾える。AIの自己申告テキストは信用度が低い上にトークンの無駄。 |
| 検証コマンドの実行 | **採用（最小限）** | 既存のビルド・構文チェック等を1回実行して合否だけを見るのは安価（出力の末尾を読むだけ）で、起動すらしない状態をテストプレイ前に止められる。テストコード作成・AIによる画面操作での確認はトークンが重く、操作感の判定も苦手なため行わず、テストプレイに任せる。 |
| REQ差し戻し権 | **不採用** | パターンA（計画立案）は計画時の二重チェック（作成AI＋監査AI）で担保済み。即時実行系もコミット前の監査＋revertの安全網で担保済み。 |
| 監査深度の階層化（Lv1〜3） | **形式上は不採用** | 発注者（人間）側に技術的な判断力の限界がある。実質的な深度判断は設計AIが担う。人間向けの代替として「チェック0」を設けた。 |
| RES→REQ逆リンク | **採用** | 低コスト（RES冒頭に1行）。REQファイルの上書き事故を検知する手がかりとして機能した実績がある。 |
| Phaseクローズ手順 | **採用（軽量版）** | 専用レポートファイルは作らず`COWORK_STATUS.md`に集約する。 |
| Claude Code 単独運用 | **採用** | 設計AI・実装AI・監査を同一ツール内で、セッション（親・子）とサブエージェントに分けて担わせる。各担い手のコンテキストを分離したまま、ファイル受け渡しの手作業をなくせる。 |
| 実装AIをサブエージェントにする | **採用** | 「タスクごとに新規コンテキスト」という実装AIの設計をそのまま満たす。指示は設計AIの要約ではなく、REQ/RESのパスとテンプレート本文で渡す（伝言による劣化を防ぐ）。 |
| 監査を別サブエージェントにする | **採用** | 実装した側の思い込みを引き継がない新規コンテキストで、成果物と実差分だけを根拠に判定させる。チェック0/1/2は plan モードで1回の起動にまとめ、観点ごとに分けて順に判定させる（観点を混ぜると視点がぼやけるため、判定は観点ごとに分ける）。 |
| DIR更新者を親セッションに一本化 | **廃止（2026-11-14）** | リード設計・現場設計・実装の3層に分けたため。代わりに書き換え範囲で分担する（次行）。 |
| DIRの書き換えを範囲で分担 | **採用** | 方針（大ゴール・やらないこと・サブフェイズ構成・実装要件）はリード設計、進行状態・持ち越し事項・メモは現場設計が書く。両者は同時に動かない（方針変更は発注者が持ち帰り、現場設計は直った DIR を読み直す）ので衝突しない。実装セッションは DIR を書かず、申し送りを完了報告に含めるのみ。 |
| リード設計・現場設計・実装を別セッションにする | **採用** | リード設計はアイデアの相談で雑多な情報が入り乱れるため、必要な情報だけを DIR に落として後続に渡す。現場設計は Phase 全体と実コードを見て REQ を作る。実装は1つの REQ だけを見る（Phase 全体を見せると実装でハルシネーションを招くため）。下流ほど扱う情報を絞る。 |
| REQ を1つずつ作る | **採用** | 後続サブフェイズの REQ は、前のサブフェイズの実コードを見て書いたほうが正確で、途中で方針転換があっても作り直しが要らない。 |
| 発注者の承認ポイントを2つに絞る | **採用** | 発注者はコードを読まないため、確認は「REQ承認（何を作るか）」と「サブフェイズ完了時のテストプレイ（動くか）」に絞る。計画承認・タスクごとのコミットは監査合格を条件に設計AIが自動で進め、所定の停止条件に当たったときだけ発注者を呼ぶ。慎重さを監査とタスク単位のコミット（取り消し可能）で担保し、発注者の確認待ちで止まる時間を減らす。 |
| 各セッションを新規コンテキストで起動 | **採用** | 前の工程の会話を持ち込まず、DIR・REQを文書として読み直すことで、不備に気づける立場を保つ。現場設計セッションは発注者が新しく開き、実装セッションは現場設計から `context: "fresh"` で起動する。 |

### 3. セッション運用方針
* Phase ごとに、リード設計セッションで DIR を作り、それを渡して現場設計セッションを1つ開く。サブフェイズは現場設計から実装セッションとして**順番に**起動する（並行させるのは Phase と無関係な Interrupt のみ）。
* 単発の Interrupt / Survey も、現場設計セッション（`oz-req-session`）で REQ を作り、実装セッションに渡す。
* 発注者の確認は、現場設計セッションでのREQ承認と、実装セッションでのテストプレイの2点。それ以外は停止条件（`oz-impl-session` に定義）に当たったときだけ呼ぶ。
* 実装セッションの完了報告は主張であって証拠ではない。現場設計は RES と git で確かめてから DIR を更新する。
* 雑談・アイデアの発散やゲームのルールの相談は、リード設計セッション（または claude.ai 側）で行う。
