### 3. 保留・後回しにした事項（バックログ）
* 憲法3章の「ファイル先頭への『責務定義』記述の義務付け」（すべてのソースファイルの先頭に、責務を JSDoc で3行以内に書く）と、同章の「生成物の手編集禁止」が、エディタの書き出しファイルではぶつかる。書き出しファイルの先頭のコメントには「責務:」の記載がなく、行数も3行を超える。`assets/sprites/ship.js` の差し替えでは「生成物の手編集禁止」を優先し、先頭のコメントに手を入れなかった。憲法に「書き出しファイルは責務定義の対象外」と書き足すかを判断する（REQ: `./_log/req/closed/261112_2133_Interrupt_機体のスプライトをエディタの書き出しに差し替える.md` 要件1）。
* フレーム処理の外からのシーン操作で `init`・`destroy` が例外を投げると、ループは止まらず、スタックが途中の状態で残る。現在は `oz/ENGINE_API.md` 15章に書くだけとしている。
* `oz/index.js` を import した時点で `window` が必要である（`Sound` が入力の登録を読み込み時に行うため）。Phase 02-04 の自動テストは `oz/src/` を直接 import し、`oz/index.js` を読み込まないことで回避した。`Sound` をテストの対象にするときに、スタブを用意してから動的 import するか、登録の時期を見直すかを決める（`PROJECT_ARCHITECTURE.md` 4章「自動テスト（`test/`）の規則」）。`Sound.playSe` の `rate` の検証（`RangeError` になる条件）も、この理由で自動テストが無く、ブラウザのコンソールでだけ確かめた（RES: `./_log/res/closed/261113_2321_RES_Interrupt_SEの再生速度を指定できるようにする.md`）。
* `Storage` の保存データの読み込みでは、版番号が同じなら保存値の型や中身を確かめずにそのまま使う。このことは `oz/ENGINE_API.md` 22章に書かれていない。書くかどうかを判断する（RES: `./_log/res/closed/261109_1730_RES_Phase02-04_自動テストの導入.md` 5章）。
* `oz/VERSION` を上げる時期の規則がない（Phase 02 で `oz/` を変えたときも `0.1.0` のまま）。新規プロジェクトの手順書では、更新の要否を版ではなく指紋一覧どうしの比較で確かめる形にした。規則を決めるかを判断する（RES: `./_log/res/closed/261109_2115_RES_Phase03-01_新規プロジェクトの作り方とゲーム用のルール.md` 5章）。2026-11-14 の発注者の判断：バトリティアを一通り作り終えるまでは、そのためのエンジンの修正を一連の作業とみなし、版は `0.1.0` のまま上げない。規則はその後に決める。
* 手順書 `_doc/newgame/NEW_GAME_GUIDE.md` 6-3 の見本の素材の参照調べは `assets/` の中を調べないので、組み立て用のスプライト（`assets/sprites/_*.js`）を土台に入れると、そのパーツが「参照されていない」と判断されて消されるおそれがある。組み立て用のJSを土台に入れるときに 6-3 を見直す（RES: `./_log/res/closed/261109_2115_RES_Phase03-01_新規プロジェクトの作り方とゲーム用のルール.md` 5章）。
* `oz/src/Engine.js` の `requireStarted` は、既存の `requireScenes` と同じ判定・同じエラー文の重複である。動作に問題はない。`Engine.js` を次に触るときにまとめるかを判断する（RES: `./_log/res/closed/261110_1013_RES_Phase03-02_マルチタッチとバーチャルコントローラー.md` タスク5の監査）。
* `test/Screen.test.js` の `createFakeCanvas` の JSDoc で、関数の説明文が `@param rect` の後ろに書かれていて、引数の説明の続きとして読まれる。動作には影響しない。次に触るときに直す（RES: `./_log/res/closed/261110_1219_RES_Phase03-03_スマホ対応の残りと実機での確認.md` タスク2の監査）。
* `CanvasCache` は、Canvas の大きさ・メモリの上限（特に iPhone の Safari）に対処していない。大きな範囲と倍率の組み合わせや、焼き付けを大量に持ち続けると、絵が出ない・作るときにエラーになることがある。`oz/ENGINE_API.md` 25章に注意として書くだけにした。バトリティアなど実際のゲームで問題になったら、上限の扱いを決める（RES: `./_log/res/closed/261119_1414_RES_Phase04-01_焼き付けの仕組み.md` 5章）。
* OZ Vector Editor の `bounds` は線の太さの半分だけを含むが、書き出しの `draw` は `miter` の角で描くため、鋭い角の線は `bounds` の外へ出て、焼き付けで切れることがある（エンジンの余白 2 画素を超える分）。土台の機体は線を描かないので影響しない。線のある絵で問題になったら、エディタ側の `bounds` の求め方として連絡票で相談する（同RES 5章）。2026-11-20、エディタの書き出し形式の版3の確かめ用スプライト（太さ 4 px の線、角は最も鋭いもので約 70°）を焼き付けて目視したところ、角の先の欠けはなかった（計算上のはみ出しは最大約 0.35 px で、余白の内側）。エディタへの返信にもこの件を補足として書いた（RES: `./_log/res/closed/261120_1545_RES_Interrupt_エディタの版3の曲線のスプライトの表示の確認.md`）。2026-11-23、版4の確かめ用スプライト（回した矩形・平行四辺形など。太さ 4 px の線、角は最も鋭いもので約 70°）でも、焼き付けの欠けはなかった（発注者の目視と、画素の倍率 1 での画素の比較）。計算上、角の先はすべて絵全体の `bounds` の内側（最も近いもので約 4.9 px 内側）で、はみ出しはない。鋭い角が外枠の辺に接していない絵なので、この件を試す例にはなっていない。同じ図形を1つだけで書き出した場合の計算上のはみ出しは、平行四辺形で約 1.38 px、回した矩形と半月形で約 0.73 px になる。余白は焼き付けた画像の 2 画素なので、倍率 1 なら収まるが、倍率が大きい画面（スマートフォンなど。倍率 2 で余白は 1 px）では切れることがありうる（画面では確かめていない）。エディタへの返信にも補足として書き、直す依頼はしていない（RES: `./_log/res/261122_2134_RES_Interrupt_エディタの版4の変形したスプライトの表示の確認.md`）。
* `CanvasCache.create` の `options` に知らない項目（`scal` などの書き間違い）があっても、エラーにせず無視する。`Engine.addVirtualPad` は知らない項目をエラーにしているので、扱いがそろっていない。そろえるかを判断する（同RES 5章）。
* `CanvasCache` で多数の絵を描いたときに直接描くより軽くなるか、また回転も拡大もせずにゆっくり動く物が画素合わせで1画素ずつ段々に動くのが気にならないかは、確かめていない。土台の機体は1機だけで、ほぼ常に回転して描かれる（補間で描かれ、画素合わせを通らない）ため、土台では確かめられない。バトリティアなど多数の絵を描くゲームで確かめ、問題があれば連絡票で受け取る（同RES 5章、RES: `./_log/res/closed/261119_1635_RES_Phase04-02_ゲームの土台での利用と資料の仕上げ.md` 5章）。
* UI 部品（`oz/ENGINE_API.md` 26章）で、土台の2つの窓では要らなかったため作っていない口が3つある。(1) スクロールする領域の中身の高さは、中の部品の下端から求めるので、いちばん下の部品の下に余白を作れない。(2) 選択肢の列には項目名が無く、土台では上に数値・文字の表示を置いて代わりにしている。(3) 土台の窓を置くシーン `js/scenes/WindowScene.js` は、背面と同じ配置のパッドとして `VIRTUAL_PAD_LAYOUT` を固定で登録する（配置の違う画面の上に窓を置くと、パッドの位置の押下で窓が閉じる。手順書 7-4 に記載）。バトリティアの開発用パネル・設定画面を作るときに要ると分かったら、連絡票で受け取って足すかを判断する（RES: `./_log/res/closed/261122_1008_RES_Phase05-04_タブとスクロールする領域.md` 5章、`./_log/res/closed/261122_1307_RES_Phase05-05_ゲームの土台での利用と資料の仕上げ.md` 5章）。
* UI 部品の既定の大きさ（ボタンの高さ 88 など）は、ゲームの短い辺 720 をスマートフォンの短い辺に合わせて表示する前提の値で、土台（横長 1280×720）のスマートフォンでの確かめは横に持って行った。縦長のゲーム（バトリティアは縦長のスマートフォンで押しやすい大きさを求めている）で既定の大きさが合うかは確かめていない（`oz/ENGINE_API.md` 26章「既定の大きさ」、RES: `./_log/res/closed/261121_2143_RES_Phase05-02_窓と部品の土台.md` 5章）。
* `PROJECT_ARCHITECTURE.md` 4章の `js/ui/` の責務に「つまみの描画の大きさ」が無い。`js/ui/virtualPadConfig.js` の責務の文と `knobRadius` にはある。資料に書き足すかを判断する（RES: `./_log/res/261123_1312_RES_Survey_デバッグ機能と定数の置き場所の現状.md` 5章）。
