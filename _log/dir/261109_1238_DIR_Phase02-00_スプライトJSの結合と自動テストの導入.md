* **完了の目安**: ゴール型。次の3点がすべて成り立つ状態を達成状態とする。

## 4. サブフェイズごとの実装要件

### Phase 02-01: スプライトJSの形式をエディタに合わせる
* **目的**: エディタの書き出しファイルを差し替えるだけで読み込めるように、土台のスプライトの読み込み方と手書きの `assets/sprites/ship.js` を、エディタの書き出し形式（既定の export だけを持つ形）に合わせる。
* **実装要件**:
  * 手書きの `assets/sprites/ship.js` を既定の export で `draw` を持つ形に書き直しても、タイトルとプレイで機体が今までと同じ大きさ・向き・見た目で表示される。
  * `_doc/bridge_samples/ship.js` を `assets/sprites/ship.js` の代わりに置くと、`js/` を変えずに、エラーなく機体の位置に絵が描かれる（向き・大きさ・色が合わないのは描いた内容の問題なので、このサブフェイズでは問わない）。
  * 目印（`ozengine sample`）の付いた部分をすべて消しても、エラーなく起動できる状態が保たれている。
* **持ち越し事項**: なし
* **メモ**:
  * 形式の正本は、往復が終わるまで `D:\ozlab\ozvectoreditor\PROJECT_ARCHITECTURE.md` 2章の「スプライト（書き出し形式）」とする。食い違いの一覧は `_doc/BRIDGE_FROM_VECTOREDITOR.md` にある。
  * 読み込み側は `js/scenes/FlightScene.js` の `import * as shipSprite` を既定の import に変える（マイルストーンでの決定）。エンジン（`oz/`）は変えない見込み。
  * 憲法3章「生成物の手編集禁止」により、`ship.js` の書き直しは REQ で明示する。書き直した `ship.js` に `format`・`formatVersion` などのデータを持たせるかは REQ 作成時に決める。
  * `PROJECT_ARCHITECTURE.md` 2.1章の改訂は Phase 02-03 で行う。このサブフェイズで 2.1章と実装が食い違う期間ができることは許容する。

### Phase 02-02: M1 の確認とエディタとの往復
* **目的**: エディタで描いて書き出した機体を土台に表示して M1 を確認し、エンジン側で使えない点があればエディタへ伝える。
* **実装要件**:
  * 発注者がエディタで機首を +X に向け、ゲーム内の大きさ（手書きの `ship.js` と同じ約 45×36 px）で描いて書き出した `ship.js` を `assets/sprites/` に置くと、`js/` を変えずにタイトルとプレイで機体として表示される。
  * 確認の間だけ背景を明るくして、黒い線の機体が見える。確認が終わったら背景は元に戻っている。
  * 確認が終わったら、土台の機体は Phase 02-01 で書き直した手書きの `ship.js` に戻っている。
  * エンジン側で困った点・エディタに直してほしい点があれば、`D:\ozlab\ozvectoreditor\_doc\BRIDGE_FROM_ENGINE.md` に書かれている。なければ「往復は1回で完了」と書かれている。
* **持ち越し事項**: なし
* **メモ**:
  * 絵を描いて書き出すのは発注者の作業である。子セッションは描いてほしい条件（向き・大きさ・置き場所）を伝え、書き出しを待つ。
  * 背景を明るくする方法と戻し方は REQ 作成時に決める（マイルストーンでの決定：変更は残さない）。
  * `BRIDGE_FROM_ENGINE.md` はエディタのリポジトリのファイルである。エディタ側の取り込み・コミットはエディタのセッションに任せ、本リポジトリからはコミットしない。
  * エディタが書き出しを直した場合は、連絡票（`_doc/BRIDGE_FROM_VECTOREDITOR.md`）が「往復2回目」として更新される。往復が続く間は、このサブフェイズを完了にしない。

### Phase 02-03: スプライトの規約の改訂
* **目的**: 往復の結果を受けて、`PROJECT_ARCHITECTURE.md` 2.1章をエンジン側の約束だけを書いた形に改訂し、エディタとの連絡に使った一時ファイルを片付ける。
* **実装要件**:
  * `PROJECT_ARCHITECTURE.md` 2.1章が、形式の定義をエディタ側の記載への参照とし、エンジン側の約束（既定の export の `draw(ctx)` を呼ぶだけ、`draw` は `ctx` の状態を元に戻す、座標は px で基準点は原点、配置は呼ぶ側が `ctx` の変換で行う、土台の機体は前方 +X）だけを書いた内容になっている。
  * AI が書くつなぎのスプライトも既定の export で `draw` を持つ形にすることが、2.1章に書かれている。
  * 組み立て用のJS（名前の頭に `_`）が「外部依存のない1ファイル」の例外になるかどうかの扱いが、2.1章に書かれている。
  * `PROJECT_ARCHITECTURE.md` 4章の `assets/sprites/*.js` の行が、実態（手書きの `ship.js` をエディタの P5 の後に差し替える）と合っている。
  * `_doc/BRIDGE_FROM_VECTOREDITOR.md` と `_doc/bridge_samples/` が削除されている。
  * `_doc/PROJECT_MILESTONE.md` の P2「OZ Vector Editor との結合」の項目のうち、完了したものが削除されている。
* **持ち越し事項**: なし
* **メモ**:
  * 憲法3章「生成物の手編集禁止」の「書き出し機能ができるまでの手書きスプライト」は、書き出し機能ができた今は実態と合わない。つなぎのスプライト（エディタで描けない絵、P3 で AI が書くもの）の扱いに合わせて文面を直すかを、発注者と決める。憲法の変更は発注者の承認を得る。
  * 組み立て用のJSの扱いは、エディタ側の P7 の方針（`D:\ozlab\ozvectoreditor\PROJECT_ARCHITECTURE.md` 2章の組み立て用のJSの例）を参照して決める。実装は行わない。
  * スプライトの規約の案内を `oz/ENGINE_API.md` に置くかどうかは Phase 03 で判断する（`_doc/COWORK_STATUS.md` 2章）。このサブフェイズでは 2.1章の改訂だけを行う。
  * 実コードの変更はない見込み。資料の改訂だけなので、計画立案を伴わない経路（Interrupt 相当）で進めてもよい。

### Phase 02-04: 自動テストの導入
* **目的**: ブラウザなしで動くエンジンのモジュールに `node --test` の自動テストを入れ、検証コマンドに加える。
* **実装要件**:
  * 決めたコマンド1つで自動テストを実行でき、すべて成功する。
  * テストの対象は `Time`、`Scenes`、`Screen` の座標変換、`Storage` に絞られている。
  * テストの対象のモジュールにわざと不具合を入れると、テストが失敗する（確認後は元に戻す）。
  * `PROJECT_CONSTITUTION.md` 1章の検証コマンドに自動テストの実行が含まれている。
  * エンジンの配布単位（`oz/`）にテストのファイルが含まれていない。
  * `PROJECT_ARCHITECTURE.md` 1章のフォルダ構造にテストの置き場所が書かれている。
* **持ち越し事項**: `oz/index.js` を import した時点で `window` が必要になる件（`_doc/COWORK_STATUS.md` 3章）。スタブを用意してから動的 import するか、登録の時期を見直すかを決める。
* **メモ**:
  * 外部ライブラリは入れない（`node:test` と `node:assert` だけを使う）。`package.json` を置くかどうかは REQ 作成時に決める（置くと憲法1章の検証コマンドの注記が変わる）。
  * テストは各モジュールを `oz/src/` から直接 import してよいかを REQ 作成時に決める（憲法3章「入口の一本化」は利用側の規則であり、テストは利用側ではない）。
  * 参考：エディタは `test/` に `node --test` のテストを置き、Node.js をテストの実行にのみ使っている（`D:\ozlab\ozvectoreditor\PROJECT_ARCHITECTURE.md` 1章）。
  * Phase 02-01〜02-03 と依存関係はない。
