# 設計指針書 DIR: Phase 03 : 新規プロジェクトの準備とスマホ対応
* ルール: `./PROJECT_CONSTITUTION.md`
* 開発資料: `./PROJECT_ARCHITECTURE.md`

## 1. 大ゴール
本リポジトリから新しいゲームのプロジェクトを作れるようにし、あわせて土台をスマートフォンで遊べるようにする。次に VANGUARDRIFTER のリメイクを新しいプロジェクトフォルダで始めるため、その前に作り方の手順とゲーム側のルールが必要である。VANGUARDRIFTER はスマートフォンにも対応するので、マルチタッチとバーチャルコントローラーを先にエンジンと土台に入れる。本 Phase は本リポジトリの作業だけで閉じ、VANGUARDRIFTER の進み具合は完了の目安に含めない（`_doc/PROJECT_MILESTONE.md` の「P3：方針」）。

* **完了の目安**: ゴール型。次の3点がすべて成り立つ状態を達成状態とする。
  * 本リポジトリの手順書に従うだけで、新規プロジェクトを作れる（作り方の手順、ゲーム用のルールの文面、Claude Code の設定例がそろっている）。
  * 土台の機体を、スマートフォンの実機でバーチャルコントローラーを使って操作できる（GitHub Pages で公開したページで確認する）。
  * Phase 03-03 の実装要件（スマートフォン対応の残り）が満たされている。

## 2. やらないこと（Non-goals）
* VANGUARDRIFTER のリメイク本体（送り先: 新しいプロジェクトフォルダ。本 Phase のサブフェイズにはしない。Phase 03-01 の完了後に並行して始めてよい）
* VANGUARDRIFTER で見つかったエンジンの不足への対応（送り先: Interrupt。本リポジトリの `_doc/BRIDGE_FROM_VANGUARDRIFTER.md` で受け取る）
* `_doc/PROJECT_MILESTONE.md` の「P3 以降で検討する機能」（カメラ、当たり判定、Entity基底クラス、パーティクル、遷移演出、UI部品など）（送り先: VANGUARDRIFTER で必要になったときの Interrupt、または以降の Phase）
* ゲームパッド、スティックのアナログ値を読み取る API（送り先: 必要になってから検討する）
* フルスクリーン表示、ホーム画面への追加（PWA）、オフライン対応（送り先: 未定）
* 土台の機体の本番の絵への差し替え（送り先: エディタの P5 の後）
* フォントの読み込み、PC の見開きとスマートフォンの単ページの切り替え（送り先: Phase 04 の候補）
* `Sound`・`Input` など、ブラウザが必要なモジュールの自動テスト（送り先: 未定）

## 4. サブフェイズごとの実装要件

### Phase 03-01: 新規プロジェクトの作り方とゲーム用のルール
* **目的**: 本リポジトリから新しいゲームのプロジェクトを作る手順と、ゲーム側の AI が守るルールの文面をそろえる。
* **実装要件**:
  * 本リポジトリに新規プロジェクトの手順書があり、その手順どおりに一時フォルダへプロジェクトを作ると、目印（`ozengine sample`）の付いたコードが消えた状態で、エラーなく起動する。
  * 手順書に、エンジンの更新方法（`oz/` の置き換えだけで行う）が書かれている。
  * ゲームのプロジェクトの憲法に貼り付けるルールの文面がある。文面には、`oz/` を編集しない、`oz/src/` を読まない、エンジンの機能が足りないときは回避策を書かず、不足を RES に記録してエンジン側で直してから `oz/` を置き換える、が含まれている。
  * ゲームのプロジェクトで使う Claude Code の設定例（`oz/src/` の読み書きと `oz/` の編集を拒否する）があり、その設定を入れた状態で `oz/src/` のファイルを読もうとすると拒否される。
  * ゲームのプロジェクトで `oz/` が改変されていないかを確かめる方法が、手順書に書かれている。
  * ゲームのプロジェクトで見つかったエンジンの不足を本リポジトリへ伝える方法（連絡票 `_doc/BRIDGE_FROM_<ゲーム名>.md`）が、手順書に書かれている。
  * ゲーム側の AI がスプライトJSの約束（`PROJECT_ARCHITECTURE.md` 2.1章の内容）を、`oz/src/` を読まずに知ることができる。
* **持ち越し事項**:
  * スプライトの規約（エンジン側の約束）は `PROJECT_ARCHITECTURE.md` 2.1章にあり、`oz/ENGINE_API.md` には `import` で読み込むことしか書いていない。案内の置き場所を判断する（`_doc/COWORK_STATUS.md` 2章）。
  * `PROJECT_ARCHITECTURE.md` 4章の `js/main.js` の行にある「見本の部分」は、目印を消した新規プロジェクトでは該当がなくなる。この記述を見直す（`_doc/COWORK_STATUS.md` 2章）。
* **メモ**:
  * `template-app` の場所は、REQ 作成時に発注者に確認する（本リポジトリの外にある）。`template-app` 自体は汎用のままにし、変更しない。
  * 手順書、ルールの文面、設定例を `oz/` に入れるか（エンジンの更新と一緒にゲームへ届く）、本リポジトリの `_doc/` などに置くか（コピーのときだけ使う）は、REQ 作成時に決める。`oz/` に入れる場合は憲法3章「入口の一本化」などとの関係を確かめる。
  * `oz/` の改変の確かめ方（ハッシュの照合など）は、外部ライブラリとビルドを使わない範囲で REQ 作成時に決める。
  * バーチャルコントローラーの既定の画像（Phase 03-02 で追加）は、新規プロジェクトで同じファイル名で上書きする。手順書にこの点を書くのは Phase 03-02 で行う。
  * Phase 03-02・03-03 と依存関係はない。本サブフェイズが完了したら、VANGUARDRIFTER のプロジェクトを作り始めてよい。

### Phase 03-02: マルチタッチとバーチャルコントローラー
* **目的**: エンジンにマルチタッチの受信とバーチャルコントローラーの仕組みを入れ、土台の機体をスマートフォンで操作できるようにする。
* **実装要件**:
  * スマートフォンの実機で、画面のスティックを指で動かすと機体が旋回し、別の指で加速のボタンを押すと、旋回しながら加速する（2本の指を同時に使える）。
  * スマートフォンの実機で、ポーズができ、ポーズを解除して再開できる。
  * バーチャルコントローラーの入力は、ゲームのロジックからはキーボードと同じに見える（`Engine.isKeyDown`・`onKeyDown` に届く）。土台のキーボードでの操作は今までどおり動く。
  * バーチャルコントローラーが処理した指は、シーンの `onPointer` に届かない。それ以外のタップは今までどおり届き、タイトルからタップで開始できる。
  * `js/main.js` の設定でバーチャルコントローラーを OFF にすると、画面に何も表示されず、画像も読み込まれず、今までの PC での操作だけが動く。
  * バーチャルコントローラーの既定の画像が `assets/images/vpad/` にあり、同じファイル名の画像に置き換えると見た目が変わる。
  * バーチャルコントローラーの描画コードと既定の画像には `ozengine sample` の目印が付いていない。目印の付いた部分をすべて消しても、ON と OFF の両方でエラーなく起動する。
  * `oz/ENGINE_API.md` だけを読んで、バーチャルコントローラーの設定、キーの割り当て、見た目の描き方が分かる。
  * Phase 03-01 の手順書に、既定の画像を同じファイル名で上書きすることが書かれている。
* **持ち越し事項**:
  * Phase 03-01 の手順書は `_doc/newgame/NEW_GAME_GUIDE.md` にある。同書 6-3 は、目印を消した後に `index.html`・`js/` から参照されない `assets/` のファイルを「見本の素材」として消す。既定の画像が新規プロジェクトで消されないこと（`js/` から参照される形になっているか、6-3 の記述を直すか）を確かめる（RES: `./_log/res/261109_2115_RES_Phase03-01_新規プロジェクトの作り方とゲーム用のルール.md` 2章 要件2）。
  * `oz/` を変更したら、指紋一覧 `oz/FINGERPRINTS.txt` を作り直す（`PROJECT_ARCHITECTURE.md` 4章「指紋一覧の規則」）。
* **メモ**:
  * 役割の分担（マイルストーンでの決定）：エンジン（`oz/`）は、マルチタッチの受信、指の追跡、スティックとボタンの当たり判定、押下状態を持つ。配置、見た目の描画、キーの割り当てはゲーム側（土台の `js/`）が持つ。エンジンは `assets/` を参照せず、画像の読み込みと描画は土台の `js/` が行う（憲法3章の依存の向き）。
  * `onPointer` は単一ポインタのまま変えない（`oz/ENGINE_API.md` 16章の「マルチタッチは扱わない」との関係は REQ 作成時に整理する）。
  * 土台のポーズ・スロー・ミュートは現在キーボードでしか操作できない。スマートフォンでポーズをどう操作するか（バーチャルコントローラーのボタン、Canvas のボタンなど）と、スローとミュートを扱うかは、REQ 作成時に発注者と決める。
  * タッチのない PC でバーチャルコントローラーを表示するかどうか（自動で切り替えるか、設定だけで決めるか）は、REQ 作成時に決める。
  * テストプレイの前に、発注者が本リポジトリの GitHub Pages を公開する。公開先のパスはリポジトリ名の下（`/ozengine-web/`）になるので、`/` から始まるパスを使わない。PC の Chrome のタッチの再現機能では2本の指を同時に試せないので、実機で確認する。
  * 既定の画像の絵柄は、REQ 作成時に発注者と決める。
  * Phase 03-01 の手順書への追記を除き、Phase 03-01 と依存関係はない。

### Phase 03-03: スマホ対応の残りと実機での確認
* **目的**: スマートフォン、特に iPhone の Safari で土台を遊ぶときに残っている問題を片付け、実機で確認する。
* **実装要件**:
  * iPhone の Safari で、電話の着信や他のアプリへの切り替えなどで音が止まったあと、土台に戻って画面に触れると、音がまた鳴る。
  * 高解像度のスマートフォンで、線と文字がぼやけずに表示される。対応しないと判断した場合は、その理由が記録されている。
  * タッチの最初の押下で音の出始めが指を離すときになる件と、押したままの間に鳴らした SE が離したときにまとめて鳴る件を実機（iPhone の Safari を含む）で確認し、`oz/ENGINE_API.md` 21章「タッチの最初の押下」の記述が確認結果と合っている。
  * PC のブラウザでの土台の動作が今までと変わらない。
* **持ち越し事項**:
  * AudioContext が `running` になると再開用のイベントを解除するので、iOS の割り込みなどでブラウザが止めた場合は自動で再開しない（`_doc/COWORK_STATUS.md` 3章）。
  * タッチの最初の押下と音の出始めの実機確認（`_doc/COWORK_STATUS.md` 2章）。確認の手順は `./_log/res/closed/261105_2358_RES_Interrupt_タッチの最初の押下と音の出始め.md` 4章にある。確認用ページはリポジトリに入っていないので、作り直す。
* **メモ**:
  * 高解像度への対応（`devicePixelRatio`）は、`Screen` の座標変換と自動テスト（`test/Screen.test.js`）に影響する可能性がある。
  * 実機で新しい問題が見つかったときは、このサブフェイズで扱うか Interrupt に分けるかを発注者と決める。
  * 実機での確認には Phase 03-02 で公開した GitHub Pages を使う。
  * Phase 03-02 の後に行う（実機確認の環境と、マルチタッチの入力の実装に依存するため）。
