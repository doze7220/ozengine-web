# 設計指針書 DIR: Phase 04 : キャンバスキャッシュ
* ルール: `./PROJECT_CONSTITUTION.md`
* 開発資料: `./PROJECT_ARCHITECTURE.md`

## 1. 大ゴール
描く処理を前もって別の Canvas に焼き付けておき、毎フレームはその画像を貼るだけにする仕組み（キャンバスキャッシュ）をエンジンに入れる。焼き付ける対象は、スプライトJSに限らず、`draw(ctx)` で描けるもの（図形、文字を含む）すべてとする。焼き付けた結果は `draw(ctx)` を持つオブジェクトとして返し、呼ぶ側はスプライトJSと同じ書き方のまま差し替えられるようにする。最初のゲーム（バトリティア）では多数のスプライトを同時に描くので、その前にエンジン側で仕組みを用意する。
* **完了の目安**: ゴール型。ゲームの土台の機体がキャンバスキャッシュを通して描かれ、直接描いたときと見た目の区別がつかないこと。PC とスマホで、ウィンドウの大きさや画面の向きを変えても、焼き付けた絵がぼやけないこと。使い方が `oz/ENGINE_API.md` に書かれていること。

## 2. やらないこと（Non-goals）
* 画素の加工（`getImageData` などによる色の差し替え、色違いの自動生成）。色違いが要るときは、色ごとに別の描く処理を渡して焼き付ける（送り先: 未定）
* 線の太さを倍率で割り戻す描き方（大きさを変えても線の太さを保つ描き方）。線の太さは絵と同じ割合で変わるものとする（送り先: やらない）
* 複数の絵を1枚の Canvas にまとめる仕組み（スプライトシート、アトラス）（送り先: 未定）
* 時間で変わる絵（アニメーション、`draw(ctx, t)` などの時間の引数）の焼き付け（送り先: エンジンの M2 以降）
* スプライトJSを読み込んだ時点で自動的に焼き付けること。焼き付けは、呼ぶ側が明示したときだけ行う（送り先: やらない）
* ゲームのプロジェクト（バトリティアなど）への導入。各ゲームが手順書のとおり `oz/` を置き換えたあとに、ゲーム側で行う（送り先: 各ゲーム）
* `oz/VERSION` を上げること。バトリティアを一通り作り終えるまでは上げない（`_doc/COWORK_STATUS.md` 3章）（送り先: バトリティアの完成後）

## 4. サブフェイズごとの実装要件

### Phase 04-01: 焼き付けの仕組み
* **目的**: 描く処理を焼き付けて、`draw(ctx)` を持つオブジェクトとして返す仕組みをエンジンに入れる。
* **実装要件**:
  * 呼ぶ側は「描く処理（`draw(ctx)` を持つオブジェクト、または描く関数）」「焼き付ける範囲」「表示する倍率（論理座標での拡大率）」を渡して焼き付けられる。返ってきたオブジェクトの `draw(ctx)` を呼ぶと、元の描く処理を同じ倍率で直接描いたときと同じ位置・同じ大きさに絵が出る。
  * 焼き付けた絵を、呼ぶ側が `ctx` の変換（位置、回転、拡大縮小）を掛けて描ける。使い方はスプライトJSの `draw(ctx)` と同じである。
  * 焼き付ける範囲は、OZ Vector Editor の書き出しにある `bounds` をそのまま渡せる。`bounds` を持たない描く処理（手書きのスプライト、図形、文字）では、呼ぶ側が範囲を渡す。
  * 焼き付ける解像度は、エンジンが「表示する倍率 × 画面の実際の画素の倍率」で決める。呼ぶ側は画面の画素の倍率を知らなくてよい。
  * ウィンドウの大きさや画面の向きが変わって画面の画素の倍率が変わったら、エンジンが自動で焼き直す。焼き直したあとも、呼ぶ側は同じオブジェクトをそのまま使える。
  * 呼ぶ側が明示して焼き直せる（色や演出を切り替えたあとに、新しい見た目で焼き付ける）。
  * 要らなくなった焼き付けを、呼ぶ側が手放せる（自動の焼き直しの対象から外れる）。
  * 引数が正しくないとき（範囲が空、倍率が 0 以下、描く処理が無いなど）は、ほかの API と同じ形のエラーになる。
* **持ち越し事項**:
  * Phase 04（キャンバスキャッシュ）で焼き付ける解像度（`_doc/COWORK_STATUS.md` 2章 A）。Phase 03-03 で Canvas の画素数を「表示サイズ × min(devicePixelRatio, 2)」にした。画面の画素の倍率は利用側に公開しない方針（`PROJECT_ARCHITECTURE.md` 3章「Canvas の画素数」）なので、エンジンの中で焼き付けの仕組みに渡す。
* **メモ**:
  * `bounds` を読むことは、`oz/ENGINE_API.md` 23章「`draw` 以外のキーは、エンジンも利用側も読まない」と食い違う。23章を「エディタの書き出しの `bounds` は読んでよい」と改める。バトリティアは、23章のこの記述のために、絵の範囲を自分のコードに手で書き写していて、兵とゴブリンでは `bounds` と値がずれている（バトリティアの Survey `261118_1948_RES_Survey_スプライトの線の太さ.md` 6章）。
  * 置き場所: `PROJECT_ARCHITECTURE.md` 4章で、`Assets` の「キャッシュ生成」は責務違反としている。新しいモジュールにするかなどを、REQ作成時に決める。同章の「エンジンに入れないもの: スプライトの描画処理」とは、エンジンが絵の中身を描かない（渡された描く処理を呼ぶだけ）という点で両立させる。描画（Canvas 2D と 3D）を分ける構想がマイルストーンの「アイデア（温め中）」節の「three.js による 3D 描画」にあり、分けるならキャンバスキャッシュは描画側に置くことになる。置き場所を決めるときに参考にする（本 Phase で描画を分けることはしない）。
  * 焼き付けた画像を拡大して描くとぼやけ、縮小して描くと細い線が淡くなる。これは直接描いたときと同じ性質で、本 Phase では対処しない。表示する倍率と大きく違う倍率で描くときの扱いは、`oz/ENGINE_API.md` に注意として書く。
  * 抜き出し元の参考: `D:\ozlab\phaseout\js\render\SpriteCacheManager.js`（参考のみで、phaseout 自体は変更しない。ゲーム固有の中身は持ち込まない）。
  * 自動テストの対象にできる範囲（Node.js には Canvas が無い）は、REQ作成時に確認する。

### Phase 04-02: ゲームの土台での利用と資料の仕上げ
* **目的**: ゲームの土台を焼き付けの仕組みで描くように変え、新しいゲームが使い始められる状態に資料をそろえる。
* **実装要件**:
  * ゲームの土台の機体が、焼き付けた絵で描かれる。回転しながら飛んでいても、直接描いていたときと見た目の区別がつかない。
  * PC とスマホで、ウィンドウの大きさや画面の向きを変えても、機体がぼやけない。
  * `oz/ENGINE_API.md` に、使い方、使い方の例、焼き直しの扱い、注意点（表示する倍率と大きく違う倍率で描くとぼやける・淡くなること）が書かれている。
  * `oz/FINGERPRINTS.txt` が新しい `oz/` に合っている。新規プロジェクトの手順書（`_doc/newgame/`）に、直す必要がある箇所が残っていない。
* **持ち越し事項**: なし
* **メモ**:
  * 土台で直接描くのと焼き付けて描くのを見比べる方法（切り替えの手段を一時的に用意するかなど）は、REQ作成時に決める。
  * 04-01 で見つかった懸念は、この欄に追記される。
