* ルール: `./PROJECT_CONSTITUTION.md`

## 1. 大ゴール
画面に重ねて開く窓と、その中に並べる UI 部品（タブ、ボタン、チェックボックス、スライダー、選択肢の列、数値・文字の表示、スクロールする領域）をエンジンに入れる。エンジンは素っ気ない標準の見た目で部品を描き、ゲームは部品の種類ごとに描く関数を渡して見た目を差し替えられる。あわせて、FPS の表示を実行中に出し入れできるようにする。最初のゲーム（バトリティア）が、開発用の調整パネルと遊ぶ人向けの設定画面を作るために求めている（連絡票 `_doc/BRIDGE_FROM_BATTLITAIRE.md`、2026-11-21）。ほかのゲームでも同じものを毎回書かずに済むようにする。
* **完了の目安**: ゴール型。ゲームの土台で、標準の見た目の開発用パネル（FPS の出し入れを含む）と、見た目を差し替えた設定画面（音量）を開き、PC のマウスとスマホの指で8種類の部品をすべて操作できること。使い方が `oz/ENGINE_API.md` に書かれていること。

## 2. やらないこと（Non-goals）
* 文字を入力する欄（テキストボックス）と、キーボード・ゲームパッドでの部品の操作（フォーカスの移動など）。部品はポインタ（マウスと指）で操作する（送り先: 未定）
* 部品の自動の並べ方（縦に積む、折り返すなどのレイアウトの計算）。部品の位置と大きさは、呼ぶ側が論理座標で渡す（送り先: 未定）
* 窓や部品の開閉・切り替えの演出（フェード、スライドなど）（送り先: 「P3 以降で検討する機能」の遷移演出とあわせて検討）
* フォントの読み込み。標準の見た目の文字は、Canvas の既定のフォントの指定で描く（送り先: P6 ゲームブックRPG）
* 既存の `Engine.addButton`（`oz/ENGINE_API.md` 18章）の仕様を変えること。押したときだけ反応する矩形として残し、描く・無効にするなどは新しい部品のボタンで行う（送り先: やらない）
* ゲームのプロジェクト（バトリティアなど）への導入。各ゲームが手順書のとおり `oz/` を置き換えたあとに、ゲーム側で行う（送り先: 各ゲーム）
* `oz/VERSION` を上げること。バトリティアを一通り作り終えるまでは上げない（`_doc/COWORK_STATUS.md` 3章）（送り先: バトリティアの完成後）

## 4. サブフェイズごとの実装要件

### Phase 05-01: FPS の表示の出し入れ
* **目的**: FPS の表示を実行中に出し入れでき、値をゲームが読めるようにする。
* **実装要件**:
  * 実行中に、FPS の表示を出したり消したりできる。`debug` の指定で起動したときの表示（`oz/ENGINE_API.md` 14章）は、これまでどおり出る。
  * ゲームが FPS の値を読める（パネルの数値の表示に出すため）。表示を消している間も読める。
  * FPS の表示の位置を変えられる（パネルと重ならないようにするため）。既定の位置は、これまでどおり左上。
  * 引数が正しくないときは、ほかの API と同じ形のエラーになる。
* **持ち越し事項**: なし
* **メモ**:
  * 連絡票では「表示の位置を変えられると（できれば）」とある。位置の指定の方法（座標で渡すか、四隅から選ぶかなど）は REQ作成時に決める。
  * `debug` の指定に、FPS の表示以外の意味を持たせるか（起動時の初期値だけにするかなど）は、REQ作成時に `PROJECT_ARCHITECTURE.md` の `DebugOverlay` の責務と照らして決める。
  * REQ作成時の決定（`_log/req/261121_1920_Phase05-01_FPSの表示の出し入れ.md`）: 位置は四隅から選ぶ。`debug` は表示の起動時の値だけを決める。土台のプレイ中のメニューに FPS の表示の切り替え（OFF・四隅）を足し、テストプレイの後も残す（05-05 の開発用パネルと重なる場合の扱いは 05-05 の REQ作成時に決める）。

### Phase 05-02: 窓と部品の土台
* **目的**: 窓と、部品の共通の仕組み（描き方の差し替え、値のつなぎ方、入力の受け方）を入れ、最も単純な部品（ボタン、数値・文字の表示）で使えるようにする。
* **実装要件**:
  * 窓を開ける。窓には、タイトルバー、閉じるボタン、背面の暗幕がある。窓の外を押したら閉じるかどうかを、呼ぶ側が選べる。
  * 窓は、`Engine.pushScene`（`oz/ENGINE_API.md` 6章）で積むシーンの中に置ける。窓を開いている間は、背面のシーンに入力が届かない。
  * 窓の中に、ボタンと、数値・文字の表示（押せないラベルと、いまの値）を並べられる。位置と大きさは論理座標（4章）で渡す。
  * エンジンは、部品を素っ気ない標準の見た目で描く。部品の種類ごとに描く関数を渡すと、その見た目に差し替わる。差し替えても、押したと判定される範囲は変わらない。
  * 部品には、値を読む関数と書く関数を渡す。部品は値を直接書き換えず、変えたら書く関数を呼ぶ（その場で反映する）。描くたびに読む関数で表示を合わせるので、値が外から変わっても表示が追従する。保存（22章 `Storage`）はゲーム側が書く関数の中で行う。
  * 部品は、ポインタ（16章の `'down'`・`'move'`・`'up'`）で動く。バーチャルパッド（24章）が処理した指は、部品に届かない。
  * 既定の大きさは、縦長のスマホで指で押しやすい大きさにする。
  * 引数が正しくないときは、ほかの API と同じ形のエラーになる。
* **持ち越し事項**: なし
* **メモ**:
  * 置き場所: `PROJECT_ARCHITECTURE.md` 4章で、`Buttons` は「ボタンの描画、タブやスクロールなどのUI部品」を責務外としている。新しいモジュールにするかなどを、REQ作成時に決める。標準の見た目を描くのは、エンジンが UI 部品を描く初めての例になる（`DebugOverlay` の FPS の表示を除く）。同章の「エンジンに入れないもの」との関係も、REQ作成時に確かめて `PROJECT_ARCHITECTURE.md` に書く。
  * 05-03 のスライダーと 05-04 のスクロールはドラッグで動く。`Engine.addButton` の押下の独占（18章「その押下は、離すまでの `'move'`・`'up'` も含めて、シーンの `onPointer` に届かない」）とぶつからない入力の受け方を、この時点で決めておく。
  * 窓をシーンの中に置く形（窓そのものをシーンにするか、シーンが窓を持つかなど）は、REQ作成時に決める。
  * 抜き出し元の参考: `D:\ozlab\phaseout\js\render\UIComponents.js`（参考のみで、phaseout 自体は変更しない。ゲーム固有の中身は持ち込まない）。連絡票には、バトリティアの RES（`D:\ozlab\battlitaire\_log\res\261121_1843_RES_Survey_エンジンへの要望の材料集め.md` 4章 R1〜R3・R5）に phaseout を調べた結果が載っているとあるが、リード設計の時点ではファイルが見つからなかった。REQ作成時に有無を確かめ、あれば参考にする。
  * 自動テストの対象にできる範囲（判定と値のつなぎ方は Node.js で確かめられる見込み）は、REQ作成時に確認する。
  * REQ作成時の決定（`_log/req/261121_2143_Phase05-02_窓と部品の土台.md`）: 部品は新しいモジュールとして `Ui` の名前で公開する。窓はシーンが持ち、シーンが受けたポインタを窓に渡す（`Engine.addButton` とエンジンの入力の登録は使わない）。押し始めた部品が離すまでの入力を受け取る。ボタンは離したときに反応し、外へずらして離すと取り消しになる。窓の外を押して外で離したら閉じるのを既定にする。バトリティアの RES は見つからなかった。土台のプレイ中のメニューに「UI の見本」を足し、標準の見た目と差し替えた見た目の2つの見本の窓を置く（05-05 で作り替える）。

### Phase 05-03: 値を変える部品
* **目的**: チェックボックス、スライダー、選択肢の列を入れる。
* **実装要件**:
  * チェックボックスを押すと、入りと切りが切り替わる。
  * スライダーをドラッグすると値が変わる。呼ぶ側は、最小・最大・刻みを渡せる。指が少しずれても、意図しない値にならない。
  * 選択肢の列（ラベルと値の一覧を渡し、1つを選ぶボタンの列）で、押したものが選ばれ、選ばれているものが分かる。
  * 3種類とも、05-02 の描き方の差し替えと値のつなぎ方に従う。
* **持ち越し事項**: なし
* **メモ**:
  * 05-02 で見つかった懸念は、この欄に追記される。
  * 05-02 の既定の大きさ（ボタンの高さ 88 など、`oz/ENGINE_API.md` 26章）は、ゲームの短い辺をスマートフォンの短い辺に合わせて表示する前提で決めた。3種類の部品の既定の大きさも、この前提にそろえるかを REQ作成時に決める（RES: `_log/res/261121_2143_RES_Phase05-02_窓と部品の土台.md` 5章）。
  * REQ作成時の決定（`_log/req/261122_0137_Phase05-03_値を変える部品.md`）: 3種類とも `read`・`write` で値をつなぎ、同じ値になる操作では `write` を呼ばない。チェックボックスと選択肢の列は、ボタンと同じく離したときに反応し、外へずらすと取り消せる。スライダーは、溝のどこかを押すとその位置へ値が飛び、そのままドラッグで追う。押している間に外へずれても離すまで追い、離したときの位置では値を変えない。選択肢の列は、横か縦かを呼ぶ側が選べる（省略は横）。既定の大きさは 05-02 と同じ前提にそろえる。土台では、05-02 の見本の窓はそのままにして、3種類を並べた見本の窓を別に足す（05-02 の見本の窓の「値を変える部品へ」から開く）。

### Phase 05-04: タブとスクロールする領域
* **目的**: 窓の中の部品を、タブで切り替えたり、スクロールで収めたりできるようにする。
* **実装要件**:
  * タブを押すと、そのタブの部品だけが表示され、操作できる。
  * スクロールする領域の中の部品は、指やマウスでドラッグしてずらせる。領域の外にはみ出した部品は描かれず、押せない。
  * スクロールする領域の中で、タップ（部品を押す）とドラッグ（ずらす）が区別される。ずらそうとしたときに、中の部品が押されない。
  * 領域の中に、スライダーなどのドラッグで動く部品を置いても、どちらの操作か区別される。
  * 2種類とも、05-02 の描き方の差し替えに従う。
* **持ち越し事項**:
  * 05-03 のスライダーは、押した瞬間に値を書く（押した位置へ値が飛ぶ。発注者の決定）。このままスクロールする領域の中に置くと、縦にずらしてスクロールするつもりの指でも、押した瞬間に値が変わる。領域の中の部品への `'down'` を遅らせるか、スライダーの押した瞬間の書き込みを横へ動かすまで遅らせるかなど、取り合いの決め方を REQ作成時に決める（RES: `_log/res/261122_0137_RES_Phase05-03_値を変える部品.md` 5章）。
  * 05-03 のスライダーには、刻みの境目で値が行き来しないための遊び（幅 8）がある。チェックボックスと選択肢の列は、ボタンと同じく離したときに反応し、外へずらすと取り消せる（`oz/ENGINE_API.md` 26章）。タップとドラッグを分ける距離を決めるときに、これらとの関係を確かめる（同RES）。
* **メモ**:
  * タップとドラッグを分ける距離や、領域の中のスライダーとの取り合いの決め方は、REQ作成時に決める。
  * マウスのホイールでのスクロールは、REQ作成時に要否を決める（連絡票にはない）。
  * REQ作成時の決定（`_log/req/261122_1008_Phase05-04_タブとスクロールする領域.md`）: タブは横に並べ、離したときに切り替わる。どのタブにも入れない部品は、どのタブでも出る。選ばれているタブとスクロールの位置は窓の側が持ち、ゲームから読む・変える口は作らない。スクロールは縦だけで、慣性は作らない（発注者の決定）。マウスのホイールは入れず、`Input` は変えない（発注者の決定）。タップとドラッグは決まった距離で分け、ドラッグになったら押されていた部品は取り消す。領域の中のスライダーは、動かした向き（横ならスライダー、縦ならスクロール）で決め、動かさずに離すと押した位置へ値が飛ぶ（発注者の決定）。05-05 の持ち越しのうち、スライダーの `step ≤ max - min` の判定と、26章の刻みの値の丸めの端の場合の記述は、この REQ で扱う。土台では、これまでの見本の窓はそのままにして、タブとスクロールの見本の窓を別に足す（05-02 の見本の窓の「タブとスクロールへ」から開く）。

### Phase 05-05: ゲームの土台での利用と資料の仕上げ
* **目的**: ゲームの土台で部品を使い、新しいゲームが使い始められる状態に資料をそろえる。
* **実装要件**:
  * ゲームの土台で、標準の見た目の開発用パネルを開ける。パネルのチェックボックスで、FPS の表示を出し入れでき、パネルに FPS の値が出る。
  * ゲームの土台で、見た目を差し替えた設定画面を開ける。BGM と効果音の音量をスライダーで変えると、その場で音量が変わり、次に起動したときにも残っている。
  * 2つの窓で、8種類の部品（窓、タブ、ボタン、チェックボックス、スライダー、選択肢の列、数値・文字の表示、スクロールする領域）がすべて使われ、PC のマウスとスマホの指で操作できる。
  * `oz/ENGINE_API.md` に、部品ごとの使い方、見た目の差し替え方、値のつなぎ方、使い方の例が書かれている。
  * `oz/FINGERPRINTS.txt` が新しい `oz/` に合っている。新規プロジェクトの手順書（`_doc/newgame/`）に、直す必要がある箇所が残っていない。
* **持ち越し事項**:
  * 05-01 で、土台のプレイ中のメニューに FPS の表示の切り替えの項目（OFF・左上・右上・右下・左下。PC は F キーでも）を足し、残してある。開発用パネルのチェックボックスと役目が重なるので、メニューの項目を残すか、パネルに一本化するかを REQ作成時に決める（RES: `_log/res/261121_1920_RES_Phase05-01_FPSの表示の出し入れ.md`）。
  * FPS を右上に出すと、土台のタイトルとプレイの画面の右上の「ミュート中」「スロー」の表示と縦に近く、少し重なって見えることがある（同RES 5章）。パネルを置く位置、FPS の表示の位置と合わせて、土台の表示の位置を見直すかを REQ作成時に決める。
  * 05-02 で、土台のプレイ中のメニューに「UI の見本」を足し、見本の窓を2つ（標準の見た目で外を押すと閉じる窓と、見た目を差し替えて閉じるボタンでだけ閉じる窓）置いてある（`js/scenes/uiSample.js`・`UiSampleScene.js`・`uiSampleLook.js`）。開発用パネルと設定画面に作り替えるか、置き換えて消すかを REQ作成時に決める。メニューは6項目になり、いちばん上の項目が背面の「メニュー」のボタンと暗幕の下で少し重なって見える（動きには影響しない）（RES: `_log/res/261121_2143_RES_Phase05-02_窓と部品の土台.md` 5章）。
  * 背面のシーンにバーチャルパッドがあるとき、窓を置くシーンが同じ配置のパッドを登録しないと、パッドの位置を押した指が「窓の外の押下」として窓に届き、外を押すと閉じる窓が閉じてしまう（05-02 の REQ の見込みと違った。見本の窓のシーンはパッドを登録して対処し、`oz/ENGINE_API.md` 26章に注意を書いた）。2つの窓を開くシーンでも同じ扱いにする（同RES）。
  * 05-02 の既定の大きさ（ボタンの高さ 88 など）は、ゲームの短い辺をスマートフォンの短い辺に合わせて表示する前提で決めた。横長の土台（1280×720）を縦に持つと、ボタンは約 26 CSS 画素になり押しにくい。土台のスマートフォンでの確かめは横に持って行った。2つの窓の部品の大きさと、手順書・26章での前提の書き方を REQ作成時に確かめる（同RES）。
  * 05-03 で、05-02 の見本の窓に「値を変える部品へ」を足し、3種類の部品を並べた見本の窓（「値を変える部品の見本（標準）」「（差し替え）」）を別に置いてある（`js/scenes/` の見本のファイル）。窓の高さは 708 で画面の高さ 720 に近く、標準の見た目では「見た目を切り替える」の文字が横に縮む。05-02 の見本の窓と合わせて、作り替えるか消すかを REQ作成時に決める（RES: `_log/res/261122_0137_RES_Phase05-03_値を変える部品.md` 5章）。
  * 05-03 の軽微な残り（資料の仕上げで扱う。(1)・(2) は 05-04 の REQ に前倒しした）: (1) スライダーの「`step` が `max - min` より大きい」の判定は小数のまま比べるので、`min 0.1・max 0.3・step 0.2` のような指定が丸めの誤差でエラーになりうる（設計どおりの動き。直すか、26章に書くかを決める）。(2) 26章の刻みの値の説明に、どの桁数でも表せない数のときは丸めない、という端の場合の記述がない。(3) チェックボックスと選択肢の列の、窓の内側で切り取られた部分の自動テストは押したときだけで、押したままずらしたとき・離したときは確かめていない（実装は監査で正しいことを確認済み）（同RES、完了報告）。
* **メモ**:
  * 土台のどのシーンから2つの窓を開くか（ボタン、キーなど）は、REQ作成時に決める。新規プロジェクトの手順書で、土台の見本を消す手順（`_doc/newgame/NEW_GAME_GUIDE.md` 6章）に影響が出ないかも確かめる。
  * 05-01〜05-04 で見つかった懸念は、この欄に追記される。
