## 1. 大ゴール
起動設定 `debug` を「開発モードで起動したか」を表すものにし、ゲームから読めるようにする。ゲームの土台では、開発用の入口（FPS の表示のキー、スローのキー、開発用パネル）を開発モードのときだけ使えるようにし、どのゲームでも使う最小の開発用パネル（FPS と速度）を、新しいゲームにも残る雛形として `js/` に置く。あわせて、土台の `js/` で複数のファイルに別々に書かれている名前（レイヤー、素材、キー）のうち、片方だけ変えると動かなくなるものを1か所にまとめる。P5 で FPS の出し入れと UI 部品がそろい、開発用の機能が増えたが、公開時に隠す手段が FPS の表示にしかないため、次のゲーム向けの機能を足す前に整理する。
* **完了の目安**: ゴール型。次の3点を満たすこと。
  * 土台を `?debug` なしで開くと開発用の入口が1つも使えず、`?debug` 付きで開くとすべて使えること（PC とスマホ）。
  * 新規プロジェクトの手順書 6章で見本を消した後のプロジェクトで、開発用パネルの雛形を開き、ゲームの項目を足せること。
  * 対象の名前を変えるときに直す箇所が、名前ごとに1か所になっていること。

### Phase 06-01: 起動設定 `debug` の意味
* **目的**: `debug` を「開発モードで起動したか」を表すものにし、ゲームから読めるようにする。
* **実装要件**:
  * ゲームが、開発モードで起動したかどうかを実行中に読める。読み取りだけで、実行中に切り替えられない。
  * `debug` を真にして起動すると、これまでどおり FPS を表示した状態で始まる。その後に FPS の表示を消しても、開発モードかどうかは変わらない。
  * エンジンは、開発モードかどうかで、起動時の FPS の表示のほかの動きを変えない。何を隠すかはゲームが決める。
  * 土台を、URL に `?debug` を付けて開くと開発モードになる。付けない場合と、`?debug=0` の場合は開発モードにならない。
  * 新規プロジェクトの手順書 6章で見本を消した後も、上の URL の指定が使える。
  * 起動設定を変えていない既存のゲームは、新しい `oz/` に置き換えても、これまでと同じに動く。
  * `oz/ENGINE_API.md` の該当する章（起動設定、FPS の表示など）が新しい意味に合っている。
* **持ち越し事項**: `_doc/COWORK_STATUS.md` 2章の「デバッグ機能と定数の置き場所を整理する Phase」の項のうち、`debug` に関する部分 → 対応済み（2026-11-24。RES: `./_log/res/261124_1257_RES_Phase06-01_起動設定debugの意味.md`）
* **メモ**:
  * 現状の調査: `./_log/res/261123_1312_RES_Survey_デバッグ機能と定数の置き場所の現状.md`（まとめは4章タスク23。4826行あるので、全体ではなく必要な節だけを読む。棚卸しの後は `./_log/res/closed/` にある）。行番号は調査の時点のものである。
  * 読み取りの API の名前は `Engine.debug` に決めた（REQ: `./_log/req/261124_1257_Phase06-01_起動設定debugの意味.md`）。URL の指定で偽になる値は `0` だけとする（`?debug=false` などは開発モードになる）。
  * 既存のゲームの起動設定 `debug` の使用は確認済み（2026-11-24）。`D:/ozlab` で `oz/` を使うゲームはバトリティアだけで、`debug` を渡していない。
  * `js/main.js` の URL を読む行は、今は目印の中にあり、手順の後に消える。目印の外へ出すと、新しいゲームは URL を知っている人なら誰でも開発モードで開ける。公開するときに `debug` を偽に固定する方法を、06-04 で手順書に書く。

### Phase 06-02: 開発用パネルの雛形と開発用の入口
* **目的**: 最小の開発用パネルを新しいゲームにも残る雛形にし、土台の開発用の入口を開発モードのときだけにする。
* **実装要件**:
  * 開発用パネルの雛形が `js/` にある。標準の見た目の窓で、FPS（値、表示の出し入れ、表示の位置）と、速度（`Engine.timeScale`）を変えられる。
  * 呼ぶ側が、自分の部品や自分のタブを雛形に足せる。雛形のファイルを書き換えなくてよい。
  * 雛形は、見本を消した後も残り、見本のコードがなくても動く。どこからも使わなければ、起動に影響しない。
  * 開発モードでなければ、雛形のパネルは開かない。
  * 土台の開発用パネルは、雛形に土台の項目を足したものになる。今のパネルでできること（FPS、スロー、情報の表示など）は、引き続きできる。
  * 土台では、FPS の表示のキー（`KeyF`）、スローのキー（`KeyS`）、メニューの項目「開発用パネル」は、開発モードのときだけ使える。開発モードでないときは、キーを押しても何も起きず、メニューに項目が出ない。操作の案内の文字にも、使えないキーが出ない。
  * メニューを開くキー（`KeyP`）と画面のボタン、メニューのほかの項目、設定画面は、開発モードかどうかにかかわらず、これまでどおり使える。
  * PC ではキーボードとマウスで、スマホでは指だけで、開発用パネルを開いて操作できる。
* **持ち越し事項**: なし
* **メモ**:
  * 開発モードは `Engine.debug` で読む（読めるのは `Engine.start` の後で、シーンの `init` からは読め、`Engine.start` の前に作るシーンの `constructor` からは読めない。`oz/ENGINE_API.md` 3章「開発モード」）。
  * 06-01 のテストプレイで1回だけ、`?debug` で開いた最初のときに FPS が出ず、`Engine.fpsVisible = true` で出たという報告があった（原因は特定できていない。新しいタブで開き直すと出て、再現していない）。06-02 のテストプレイの項目に「`?debug` で開いて FPS と開発用の入口が出る」ことを入れ、再び起きたら、そのときの URL と `Engine.debug` の値を記録してもらう（RES: `./_log/res/261124_1257_RES_Phase06-01_起動設定debugの意味.md` 5章）。
  * 雛形には目印を付けない。目印の付いていないファイルは、目印の付いたコードを import できないので、今の `fps.js`・`slow.js` のうち雛形に要る部分の移し方を REQ作成時に決める。
  * 手順書 6章の「残る6ファイル」、7-4 の「使わないゲームでは」の4ファイルの記述が変わる（直すのは 06-04。ファイル名と数を 06-04 のこの欄へ引き継ぐ）。
  * ヒットストップなどで `Engine.timeScale` を自分で変えるゲームとの関係（パネルで選んだ速度が、ゲームの書き込みで上書きされる）は、仕組みで解決せず、雛形のコメントに注意として書く（REQ作成時に確認済み）。
  * 速度は、停止・×0.25・×0.5・×1・×2 の選択肢の列に決めた。雛形は「基本」のタブ1つ（スクロールする領域）で、呼ぶ側は「基本」の下の部品と、右のタブ（`{ label, build }`）を足せる。土台の右上の「スロー」の文字は「速度 ×0.25」のような表示に変える（REQ: `./_log/req/261124_1405_Phase06-02_開発用パネルの雛形と開発用の入口.md`）。
  * バトリティアの DEBUG タブと見比べ済み（2026-11-24）。タブは `{ label, build }` の形で、共通する項目は FPS の表示の出し入れと FPS の値である。`Engine.timeScale` は使っていない。雛形の項目は FPS と速度から増やさない。
