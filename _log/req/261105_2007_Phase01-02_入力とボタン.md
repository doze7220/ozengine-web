## 【実装要件】
`oz/` にポインタとキーボードの入力、および Canvas 上のボタンの当たり判定を追加する。あわせて、`js/main.js` の確認用コードにタップとキーによる操作を作り、Phase 01-01 から先送りした `timeScale` の変更、シーンの切り替え、積む・戻すを画面で確認できるようにする。

*   **要件1: 入力の配信の順序（発注者の決定。開発資料3章を変更する）**
    *  入力は `timeScale` に関係なく、毎フレーム1回、固定ティックの前に配る。`timeScale` が `0` の間も入力は届き、ボタンやキーで再開できる。スロー中も反応は遅れない。
    *  1フレームの順序を次のように変更する。
        1. 開発資料3章の手順1のとおり `Time` を進める（フレームの外で起きたシーン操作の検知は従来どおりその前に行う）。
        2. ブラウザから受け取って溜めておいた入力を、届いた順に確定して配る。ポインタはボタン → 最前面のシーンの順に、キーは最前面のシーンに配る。
        3. 蓄積がティック長に達している間、最前面のシーンの `update(dt)` を呼ぶ。
        4. 描画とデバッグ表示は従来どおり。
    *  手順2でシーン操作が起きたら、そのフレームのティックを回さず、蓄積を捨て、次のフレームの `realDelta` も蓄積に入れない（ティックの中のシーン操作と同じ扱い）。そのフレームの残りの入力は、新しい最前面のシーンへ配る。
    *  ブラウザのイベントの中でシーンの処理を呼ばない。シーンの `onPointer`・`onKeyDown` とボタンの `onPress` は、必ず手順2の中から呼ぶ。
*   **要件2: ポインタ**
    *  マウス、タッチ、ペンを同じように扱う。Pointer Events を使い、canvas に登録する。
    *  シーンに `onPointer(pointer)` を追加する。`pointer` は `{ type, x, y }` で、`type` は `'down'`・`'move'`・`'up'` のいずれか、`x`・`y` は論理座標である。最前面のシーンだけに届く。
    *  論理座標への変換は `Screen` に追加する。ウィンドウの大きさを変えてもずれない。
    *  主ポインタの主ボタン（左クリック、タッチ、ペン）だけを扱う。マルチタッチ、右クリック、中クリックは扱わない。
    *  押さずにマウスを動かした場合も `'move'` を届ける。1フレームの間に連続した `'move'` は、最後の1つにまとめてよい。
    *  押したまま canvas の外へ出ても、離す操作が届くようにする（pointer capture）。このとき `x`・`y` は論理解像度の範囲外の値になることがある。
    *  タッチでページがスクロールや拡大をしないように、エンジンが canvas の `touch-action` を `none` に設定する。
    *  押下の中断（`pointercancel`）は、離す操作（`'up'`）として届ける。
*   **要件3: キーボード**
    *  キーは `KeyboardEvent.code` の文字列（`'Space'`、`'KeyA'`、`'Digit1'`、`'Escape'` など）で扱う。キー割り当ての固定値をエンジンに持たない。
    *  押している間の状態は `Engine.isKeyDown(code)` で取得する。どのメソッドの中からでも呼べる。値は入力を確定するときだけ変わり、1フレームの間は変わらない。
    *  押した瞬間は、シーンに追加する `onKeyDown(code)` で受け取る。最前面のシーンだけに届く。キーリピートでは呼ばない。
    *  短く押したキーを取りこぼさない。押してから離すまでが1フレームより短くても、`onKeyDown` は必ず呼ばれ、そのフレームの間は `isKeyDown` が `true` になり、次のフレームで `false` になる。
    *  ウィンドウからフォーカスが外れたら、押している状態をすべて解除する（キーが押されたままにならないようにする）。
    *  ブラウザの既定の動作（F5、F12 など）は止めない。
    *  入力は `window` に登録する。
*   **要件4: ボタン**
    *  `Engine.addButton(scene, { x, y, width, height, onPress })` でシーンごとに登録する。座標は論理座標とする。`init` の中で呼べる（`Engine.start` に渡した最初のシーンの `init` でも使える）。不正な引数はエラーにする。
    *  ポインタの `'down'` の位置が、最前面のシーンのボタンの矩形の内側なら `onPress()` を呼び、入力を消費する。消費した押下はそのシーンの `onPointer` に届かない。その押下を離すまでの `'move'` と `'up'` も、シーンの `onPointer` に届かない。
    *  矩形の内側とは、左端と上端を含み、右端と下端を含まない範囲とする。ボタンが重なっている場合は、後に登録したものだけが反応する。
    *  ボタンが反応するのは最前面のシーンだけとする。積まれて背面になったシーンのボタンは反応せず、戻ると再び反応する。スタックから外れたシーンのボタンは反応しない。
    *  ボタンの描画はエンジンに入れない。利用側がシーンの `draw` で描く。
*   **要件5: シーンの基底クラス**
    *  `Scene` に、中身のない `onPointer(pointer)` と `onKeyDown(code)` を追加する。`new Scene()` は従来どおり何もしないシーンとして使える。
    *  `onPointer` の戻り値は使わない。配信先の最後がシーンなので、消費の意味がないためである。開発資料2.3章の「`true` を返すと消費する」を削除する。
*   **要件6: 確認用コード（`js/main.js`）**
    *  確認用コードはすべて憲法3章の `ozengine sample` の目印で囲む。目印の付いた部分を消すと、従来どおり `new Scene()` とレイヤー1枚で、真っ黒な画面のままエラーなく起動すること。
    *  確認用コードは Phase 01-04 で置き換える仮のものである。開発資料4章は `js/main.js` に描画処理を置くことを禁じているが、Phase 01-01 と同じく確認用コードに限って例外とする（目印の中に限る）。
    *  レイヤー3枚と、赤・緑・青の図形が往復する既存の動きは残す。
    *  **操作の一覧:** 次の操作をボタンとキーの両方で実行できる。ボタンには操作名を文字で描き、対応するキーも分かるようにする。
        | ボタン | キー | 内容 |
        | --- | --- | --- |
        | `速さ` | `1` | `timeScale` を ×1 → ×0.25 → ×0 → ×1 の順に変える。ボタンに現在の倍率を表示する |
        | `切替` | `2` | `Engine.changeScene` で色違いのシーンへ切り替える。もう一度押すと元の色に戻る |
        | `積む` | `3` | `Engine.pushScene` で半透明の画面を積む |
        | `戻す`（積んだ画面にある） | `Escape` | `Engine.popScene` で積んだ画面を外す |
    *  **切り替え:** 2つのシーンは背景の色とボタンの位置が異なる。図形の位置と向きは新しいシーンに引き継ぎ、切り替えの直後に動きが飛ばないことを確かめられるようにする。切り替えの前のボタンがあった場所を押しても反応しないことを、次の「ボタンの外を押した回数」で確かめられるようにする。
    *  **積んだ画面:** 半透明の画面を最も手前のレイヤーに描き、背面の図形が透けて見えるようにする。`戻す` ボタンは、背面のシーンのどのボタンとも重ならない位置に置く。積んだ画面では `速さ`・`切替`・`積む` のキーとボタンは反応しない（シーンを積むと入力が最前面だけに届くことの確認）。`Escape` は積んだ画面でだけ働き、元のシーンでは何もしない。
    *  **ポインタの確認:** 押した位置に十字、移動の跡に小さな点、離した位置に丸を描く（直近のものだけでよい）。直近に押した位置の論理座標を文字で表示する。ボタンで消費された押下では、これらの印は出ない。
    *  **キーの確認:** `Space` を押している間だけ図形の色が変わる（`isKeyDown`）。キーを押した回数（`onKeyDown`）を文字で表示する。
    *  **回数の表示:** ボタンの外を押した回数（`onPointer` の `'down'`）を文字で表示する。シーンごとに数えてよい。
    *  URL の `?debug` は従来どおり。
    *  確認用コードにも憲法3章の `js/` のルールを適用する。`requestAnimationFrame`・`addEventListener`・`getContext` を書かない。更新と描画を分ける（`draw` の中で状態を変更しない）。
*   **要件7: `oz/ENGINE_API.md`**
    *  読むだけで入力とボタンの使い方が分かるようにする。`onPointer`・`pointer` の中身、`onKeyDown`・`isKeyDown` とキーの指定方法、`addButton`、ボタンの描画は利用側で行うこと、配信のタイミングと順序（`timeScale` が `0` でも届く、`draw` の中では呼ばれない）を書く。
    *  既存の章も実態に合わせて直す。少なくとも次の点を反映する。
        *  1章の「使えるもの」と `Engine` の説明、5章のメソッドの表。
        *  7章「操作を呼んでよい場所」に `onPointer`・`onKeyDown`・`onPress` を加える。
        *  8章「操作の直後の時間」に、入力の配信の中で操作した場合を加える。
        *  12章 `timeScale` に、`0` でも入力は届き、再開には `onPointer`・`onKeyDown`・`onPress` を使えることを書く。
        *  15章「例外」に、`onPointer`・`onKeyDown`・`onPress` の例外ではループが止まることを加える。
        *  `isKeyDown` は実時間のフレーム単位で変わるため、`timeScale` が小さいときは、ティックの間に押して離したキーが `update` から見えないことがある。取りこぼしたくない操作は `onKeyDown` を使う、と書く。
        *  押下を受けたシーンの操作で最前面のシーンが変わると、新しいシーンには `'down'` のない `'up'` が届くことがある、と書く。
    *  今回作っていない機能（アセット、サウンド、セーブ）は載せない。

### 画面での確認（発注者のテストプレイ。計画の参考）
*   押した位置とウィンドウの大きさの変更: 大きさを変えても印が押した場所に出る。
*   ボタンの内側で反応し、外側では回数だけが増える。
*   `timeScale` を ×0.25 にすると図形が遅く動く。×0 で止まり、ボタンとキーで再開できる。
*   シーンを切り替えた直後に動きが飛ばない。
*   シーンを積むと背面の動きが止まって表示は残り、戻すと再開する。
*   キーをごく短く押しても回数が必ず増える。

## 【計画立案時の絶対遵守ルール (Constraints)】
*   **依存の向き** : 開発資料3章の依存の向きを守る。`Input` が import してよいエンジンモジュールは `Screen` だけとする。`Buttons` は他のエンジンモジュールを import しない。`Input` がシーンやボタンへ配るために必要なものは、`Engine` が生成して引数で渡す。`GameLoop` はこれまでどおりモジュールを import しない。
*   **入口の一本化** : 利用側に公開するのは `Engine` と `Scene` だけとする。`Input`・`Buttons` のクラスは公開せず、`Engine.addButton`・`Engine.isKeyDown` で委譲する。
*   **責務の分離** : 責務の定義を超える処理を既存のファイルに足さない。ブラウザからの受信、確定、配信は `Input`、当たり判定は `Buttons`、座標変換は `Screen`、順序の呼び出しは `GameLoop`、委譲は `Engine` に置く。`Scenes` には最前面のシーンを参照する手段だけを足す。
*   **時間の受け渡し** : `Input`・`Buttons` は時間を取得しない。
*   **ロジックと描画の分離** : シーンの `onPointer`・`onKeyDown`・`onPress` が `draw` の中から呼ばれることがない設計にする。
*   **シーン操作の検知** : 配信の中のシーン操作は、既存の `Scenes` の変更フラグを `GameLoop` が見て `Time` に伝える形にする。`Input` は `Time` を知らない。
*   **先回り実装の禁止** : `Assets`・`Sound`・`Storage` のファイルや呼び出しの空枠を作らない。やらないことに挙げた機能を作らない。
*   **`js/` の実装** : `js/main.js` を実装するタスクでは `oz/src/` を読まず、`oz/ENGINE_API.md` だけを参照する（憲法3章）。そのため、`oz/ENGINE_API.md` が揃うタスクの後に置き、計画書に明記する。分からないことはRESに不足として記録する。
*   **公開APIとドキュメント** : 公開APIを追加するタスクと同じタスクで `oz/ENGINE_API.md` を更新する（憲法3章）。
*   **スコープの粒度** : タスクは1〜数ファイル単位に分ける。
