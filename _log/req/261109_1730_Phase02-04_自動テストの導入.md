## 【実装要件】
ブラウザなしで動くエンジンのモジュール（`Time`・`Scenes`・`Screen`・`Storage`）に、Node.js 標準の `node:test` による自動テストを入れ、`oz/` を直したときに壊れたことに気づけるようにする。テストはエンジンの配布単位（`oz/`）の外に置き、検証コマンドに加える。**エンジンのソース（`oz/` 以下）は一切変更しない。**

*   **要件1: テストの実行方法（決定事項）**
    *  リポジトリのルートで `node --test`（引数なし）を実行すると、すべてのテストが実行され、すべて成功する（`fail 0`）。
    *  `package.json` は作らない。npm パッケージ・外部ライブラリ・DOM の模擬ライブラリは使わない。使ってよいのは `node:test` と `node:assert/strict` だけとする。
    *  `package.json` がなくても `import`/`export` を含む `.js` が ES Modules として読み込まれ、警告も出ないことは、Node.js v24.15.0 で確認済みである。確認した Node.js の版を作業計画書と開発資料に書く。
    *  Node.js はテストの実行にのみ使う。ゲームの実行・配信には使わない。
*   **要件2: テストの置き場所と命名（決定事項）**
    *  テストはリポジトリのルートの `test/` に置く。ファイル名は `test/<対象モジュール名>[.<観点>].test.js` とする（例: `test/Time.test.js`）。1モジュールを複数ファイルに分けてよい。
    *  `node --test` は `test/` 以下の `.js` をすべてテストとして実行するため、`test/` には共有の補助モジュールを置かない。補助関数は各テストファイルの中に書く。テスト以外の `.js` を `test/` に置かない。
    *  `oz/`・`js/`・`assets/`・`index.html` は `test/` を参照しない（依存は `test/ → oz/src/` の一方向）。
    *  `test/` は新規プロジェクトにコピーされない（開発資料1章のコピー手順の対象は `index.html`・`oz/`・`js/`・`assets/` だけである）。
*   **要件3: テストからの import（決定事項）**
    *  テストは対象モジュールを `oz/src/` から相対パスで直接 import する（例: `import { Time } from '../oz/src/Time.js'`）。憲法3章「入口の一本化」は利用側（`index.html`・`js/`・`assets/`）の規則であり、テストは利用側ではない。`Time`・`Scenes`・`Screen` は `oz/index.js` から公開されていないため、直接 import 以外では試せない。
    *  テストは `oz/index.js` を import しない。
    *  テストは対象モジュールの公開されたもの（`export` されたクラス・オブジェクトと、その JSDoc にある公開メソッド・プロパティ）だけを通して確かめる。テストのためにソースへ `export` を足す、private を公開する、処理を切り出す、といった変更はしない。
*   **要件4: テストの対象と確かめる内容**
    *  対象は `oz/src/Time.js`・`oz/src/Scenes.js`・`oz/src/Screen.js`・`oz/src/Storage.js` の4つに絞る。ほかのモジュール（`Scene`・`Input`・`Sound`・`Assets`・`Layers`・`GameLoop`・`DebugOverlay`・`Engine`・`Buttons`）のテストは書かない。
    *  何を確かめるかは、各ファイルの JSDoc と開発資料（2.4章・3章・4章）に書かれた約束から計画立案で決める。少なくとも次を含める。
       *  `Time`: ティック長、固定ティックの蓄積と消費、1フレームの上限（5ティック分）、`timeScale` の適用と不正な値での `RangeError`、`gameTime` の加算、初回のフレームの扱い、`discardAccumulated` の後のフレームの扱い、`view` が読み取り専用で最新の値を返すこと。
       *  `Scenes`: `push`・`pop`・`change` のスタックの変化と `init`・`destroy` の呼ばれる順序、空のときの `pop`・`update`・`top`、`update` が最前面だけに届くこと、`forEachFromBottom` の順序、`consumeChanged` の値と戻り方。シーンはテストファイル内の素のオブジェクトの偽物で用意する（`Scene.js` は import しなくてよい）。
       *  `Screen`: 座標変換（`toLogical`）。表示サイズが論理解像度と違う場合、canvas の位置がずれている場合を含める。あわせて、構築時に canvas の `width`・`height` が論理解像度になり、`style` の幅と高さが縦横比を保ってウィンドウに収まる値になること。
       *  `Storage`: `open`・`get`・`set` の基本、引数の不正と2回目の `open` のエラー、`open` 前の `get`・`set` のエラー、未知の名前のエラー、JSON にできない値のエラー、`get` がコピーを返すこと、保存データの読み込み（版番号が同じ・違う・壊れている・`defaults` にない名前は捨てる・足りない名前は既定値）、`set` でその場で保存されること、`localStorage` が使えないときと保存に失敗したときに例外を投げず警告を出して続けること。
*   **要件5: ブラウザの代わりの用意（`window`・canvas）**
    *  `Screen` と `Storage` は `window` を参照する。テストでは、テストファイル内の素のオブジェクトで偽の `window`（`addEventListener`・`innerWidth`・`innerHeight`・`localStorage` のうち必要なもの）と偽の canvas（`width`・`height`・`style`・`getBoundingClientRect`）を用意する。
    *  偽の `window` は `globalThis.window` に置いてよいが、置いたテストの終了時に必ず元の状態（置く前に無かったなら削除）に戻す。`window` 以外のグローバルには代入しない。
    *  `console.warn` は、警告が出るテストでは `t.mock.method(console, 'warn', ...)` で抑止し、必要なら呼ばれた回数を確かめる。
    *  `Storage` はモジュール内に状態を持ち、`open` は1回しか呼べない。1つのテストファイルで複数の状態を試すときは、クエリ付きの動的 import（例: `await import('../oz/src/Storage.js?case=1')`）でモジュールを別々に読み込んでよい（Node.js v24.15.0 で別のモジュールとして読み込まれることを確認済み）。またはテストファイルを分けてもよい。どちらにするかは計画立案で決める。
*   **要件6: テストが不具合に気づけることの確認**
    *  各テストファイルを書くタスクの中で、対象モジュールにわざと不具合を1つ以上入れて `node --test` が失敗することを確かめ、**確認後は必ず元に戻す**（`git diff -- oz/` が空であることを確かめる）。入れた不具合と失敗したテスト名を、作業レポートの該当タスクに記録する。
*   **要件7: 検証コマンドへの追加（`PROJECT_CONSTITUTION.md` 1章）**
    *  1章の「検証コマンド」の項目に、リポジトリのルートでの `node --test`（引数なし）の実行を加える。既存の構文チェック（`node --input-type=module --check < <変更した .js ファイル>`）は残す。結果は `fail 0` で判定する旨を書く。
    *  憲法のほかの項目は変更しない。この変更は、全テストが揃った後のタスクで行う。
*   **要件8: 開発資料への記載（`PROJECT_ARCHITECTURE.md`）**
    *  1章のフォルダ構造に `test/` を加え、自動テストの置き場所であること（`node --test` でのみ実行、`oz/` の外に置き新規プロジェクトにはコピーしない）を書く。
    *  テストの規則（実行方法・確認した Node.js の版・置き場所と命名・import の規則・偽の `window` の扱い・対象の4モジュール・テストしないモジュール）を、開発資料のどこに書くかは計画立案で決めてよい（4章に行を加える、など）。ただし既存の章の記述は、`test/` の追加に必要な範囲を超えて変更しない。
    *  開発資料への反映は最終の固定タスクでのみ行う。

## 【計画書に必ず含めるべきタスクごとの作業】
AIが作成する計画書（RES）のタスクリストには、個別の実装タスクの後に、以下の作業を必ず含めること。
*   コード修正完了後、JSDocコメントの記載漏れがないことを確認する（テストファイルの先頭行の責務定義、補助関数の JSDoc を含む）。
*   リポジトリのルートで `node --test` を実行し、`fail 0` であることを確かめる。
*   タスク完了後、作業レポート（本RESファイル）の詳細作業内容を記載し完成させる。
*   開発資料（`PROJECT_ARCHITECTURE.md`）の記載に影響が出る場合は、資料本体は修正せず、その旨を『開発資料の更新予定』欄に追記する。

## 【計画書に必ず含めるべき固定タスク】
AIが作成する計画書（RES）のタスクリストには、全実装タスクの後に、以下のタスクを必ず含めること。
*   各タスクで記録した『開発資料の更新予定』を確認し、開発資料（`PROJECT_ARCHITECTURE.md`）へ反映する。開発資料に影響を与えない場合は、このタスクは不要とする。
    *   ※ 実装AIによる開発資料の書き換えは、本ワークフローにおいて原則禁止であるが、**この最終タスクのみ明示的な例外とする**。後続タスクが存在せず、資料の変更によって他タスクの前提が動く危険がないためである。個別の実装タスク内で資料を書き換えてはならない。

## 【計画立案時の絶対遵守ルール (Constraints)】
*   **エンジンのソースを変えない** : `oz/` 以下のファイル（`oz/index.js`・`oz/src/*.js`・`oz/ENGINE_API.md`・`oz/VERSION`）は一切変更しない。テストしやすくするための変更も行わない。要件6の一時的な不具合の挿入は、同じタスクの中で必ず元に戻す。
*   **変更してよいファイル** : 新規の `test/*.test.js`、`PROJECT_CONSTITUTION.md` 1章の検証コマンドの項目（要件7）、`PROJECT_ARCHITECTURE.md`（要件8。最終の固定タスクのみ）、作業計画書（本RES）に限る。`js/`・`assets/`・`index.html`・`_doc/` は変更しない。
*   **スコープの分割** : テストファイルを書くタスクは、対象モジュール1つにつき1タスク以上に分ける（1タスクで複数モジュールのテストを書かない）。
*   **外部依存の禁止** : `node:test`・`node:assert/strict` 以外を import しない（クエリ付きの動的 import で `oz/src/` を読み込むことは除く）。
*   **テストの書き方** : テストファイルの先頭行に、そのファイルの単一の責務を JSDoc で3行以内に書く（憲法3章）。補助関数にも JSDoc（`@param`・`@returns`）を書く。テストは実行順や他のテストファイルの結果に依存しない。
*   **持ち越し事項の扱い** : `oz/index.js` を import した時点で `window` が必要になる件（`Sound` が読み込み時にイベントを登録するため）は、テストが `oz/index.js` を import しないことで本作業では回避する。登録の時期の見直しは本作業では行わない（`Sound` をテストの対象にするときに検討する）。
