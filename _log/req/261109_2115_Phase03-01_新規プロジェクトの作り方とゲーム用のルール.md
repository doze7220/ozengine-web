本プロンプトは新規機能の「計画立案」のみを目的とする。**絶対にコードの修正（ファイルの書き換え）を行わないこと。** 計画立案のみに留めること。

## 【実装要件】
本リポジトリから新しいゲームのプロジェクト（以下「ゲームのプロジェクト」）を作る手順と、ゲーム側の AI が守るルールの文面をそろえる。ゲームのプロジェクトは、GitHub のテンプレートリポジトリ `doze7220/template-app`（AI駆動開発の汎用スターターキット。`.claude/`・`CLAUDE.md`・`PROJECT_CONSTITUTION.md`・`PROJECT_ARCHITECTURE.md`・`README.md`・`_doc/`・`_log/` を持ち、ゲームのコードは持たない）から「Use this template」で作り、本リポジトリの `index.html`・`oz/`・`js/`・`assets/` をコピーして作る。`template-app` は汎用のまま使い、本作業では変更しない（本リポジトリの外にあり、変更する手段もない）。

本作業の成果物は、主に文書（手順書・ルールの文面・設定例）と、`oz/` の改変を確かめるための指紋一覧である。ゲームのコード（`js/`）とエンジンのコード（`oz/index.js`・`oz/src/`）は変更しない。

*   **要件1: 置き場所（決定事項）**
    *  手順書・ゲームの憲法に貼り付けるルールの文面・Claude Code の設定例は、本リポジトリの新しいフォルダ `_doc/newgame/` に置く。ゲームのプロジェクトを作るときだけ使い、ゲームのプロジェクトへフォルダごとコピーはしない（ルールの文面は憲法に貼り付け、設定例は中身を `.claude/settings.json` に入れる）。
    *  ファイルは次の3つとする（名前は決定事項）。
       *  `_doc/newgame/NEW_GAME_GUIDE.md` : 新規プロジェクトの手順書（要件2〜5・8）
       *  `_doc/newgame/GAME_RULES.md` : ゲームの憲法に貼り付けるルールの文面（要件6）
       *  `_doc/newgame/settings.example.json` : ゲームのプロジェクトの `.claude/settings.json` に入れる Claude Code の設定例（要件7）
    *  `_doc/newgame/` の3ファイルは、本リポジトリの実装AIが変更してよい対象とする（本REQで明示する）。

*   **要件2: 新規プロジェクトの作り方（手順書）**
    *  手順書は、発注者（コードを読まない人間）と、ゲームのプロジェクトで立ち上げを先導する Claude Code の両方が読んで、そのとおりに進められる文書にする。`template-app` の `_doc/INITIAL_PROJECT_STARTUP.md`（立ち上げ手順）のどの段階で何をするかの対応が分かるように書く（例：Step 0 の準備でコピーと目印の削除を行い、Step 2 の憲法の最適化でルールの文面を組み込む）。
    *  少なくとも次の流れを含める。
       *  `doze7220/template-app` から「Use this template」で新しいリポジトリを作り、ローカルにクローンする。
       *  本リポジトリから `index.html`・`oz/`・`js/`・`assets/` をコピーする。`test/`・`_doc/`・`_log/`・`.claude/`・本リポジトリの `CLAUDE.md`・`PROJECT_*.md`・`README.md` はコピーしない（これらは `template-app` 側のものを使う）。
       *  `ozengine sample` で検索し、目印の付いたコードを消す（ファイル全体の目印 `/* ozengine sample */` のファイルは削除し、`/* ozengine sample: begin */`〜`/* ozengine sample: end */` の範囲は目印の行ごと消す。書き方は本リポジトリの憲法3章「サンプルコードの目印」）。消した後に `ozengine sample` が1件も残っていないことを確かめる。
       *  `assets/` の見本の素材（目印を消した後のコードから参照されない画像・音・スプライト）を消し、ゲームの素材に入れ替える。
       *  `index.html` の `<title>` など、ゲームごとに変える箇所。
       *  `.claude/settings.json` に設定例を入れる（要件7）。
       *  ゲームのプロジェクトの憲法・開発資料に、エンジンについて書くこと（ルールの文面の貼り付け場所、`oz/` をエンジン本体として扱い `oz/ENGINE_API.md` だけを参照することなど）。
       *  コピーしたエンジンの版（`oz/VERSION`）を確かめる方法。
       *  起動の確認（静的サーバで `index.html` を開き、エラーなく起動する。目印を消した直後は、`js/main.js` の既定の空の `Scene` が動くだけで画面は黒いままでよい）。
    *  目印の付いたコードを消す具体的な方法（手作業の手順、または外部ライブラリを使わないコマンド）は計画立案で決める。発注者は Windows で、Claude Code（PowerShell と Git Bash が使える）を使う。
    *  目印を消した後に残る `js/` のコードが、消したファイルを参照していないこと（エラーなく起動できること）は、本リポジトリの憲法3章で保証されている前提である。手順書を書くタスクとは別に、要件9の確認を行う。

*   **要件3: エンジンの更新方法（手順書）**
    *  エンジンの更新は、ゲームのプロジェクトの `oz/` を本リポジトリの `oz/` で丸ごと置き換えるだけで行う（`oz/` の外は触らない）ことを書く。置き換えの前後で `oz/VERSION` を確かめること、更新後は `oz/ENGINE_API.md` を読み直して変わった点に合わせて `js/` を直すこと、置き換え後に要件4の照合を行うことを書く。
    *  要件7の設定例で `oz/` の編集を Claude Code に禁止しているため、`oz/` の置き換えを誰がどう行うか（発注者が Claude Code の外でフォルダを置き換える、など）を書く。

*   **要件4: `oz/` の改変の確かめ方（指紋一覧。決定事項と計画で決めること）**
    *  決定事項：`oz/` の各ファイルの指紋（SHA-256 のハッシュ）の一覧ファイルを `oz/` の中に置き、エンジンと一緒にゲームのプロジェクトへ届ける。ゲームのプロジェクトでは、本リポジトリが手元になくても、外部ライブラリとビルドを使わない1行程度のコマンドで、`oz/` の中身が一覧と一致するか（改変・追加・削除がないか）を確かめられるようにする。
    *  決定事項：一覧が古くなっていないこと（`oz/` を変えたのに一覧を作り直し忘れていないこと）を、本リポジトリの自動テスト（`node --test`）で毎回確かめる。`oz/` のファイルを変えて一覧を作り直さなかった場合、ファイルを足した場合、消した場合に、テストが失敗するようにする。テストが一覧の不一致に気づけることを、実装タスクの中で一度わざと食い違いを作って確かめ、確認後は元に戻す（`git status` で変更が残っていないことを確かめる）。
    *  計画で決めること：一覧ファイルの名前と形式、一覧の作り方（作り直しのコマンド）、ゲームのプロジェクトでの照合のコマンド。照合は Windows の Git Bash または PowerShell で実行できるものにする。一覧ファイル自身は一覧に含めない。
    *  計画で決めること：改行コードの扱い。本リポジトリは `core.autocrlf=true` で運用しており、作業ツリーのファイルは改行が CRLF になっている可能性がある。ゲームのプロジェクトへのコピー・ゲームのリポジトリでの git の出し入れ・別の環境でのクローンで改行が変わったときに、改変していないのに照合が失敗する（または改変を見逃す）ことがないように設計する。避けられない場合は、照合が失敗する条件と対処を手順書に書く。
    *  一覧の作り直しは、`oz/` を変更するタスクの一部として行う運用にする。この運用（いつ作り直すか、作り直しのコマンド）を開発資料に書く（最終の固定タスクで反映）。本作業の中で `oz/ENGINE_API.md` を変更するので（要件5）、一覧はその変更の後の内容で作る。
    *  自動テストは開発資料4章「自動テスト（`test/`）の規則」に従う。ただし、この規則は現在「使ってよいのは `node:test` と `node:assert/strict` だけ」「対象は `Time`・`Scenes`・`Screen`・`Storage`」としているため、指紋一覧のテストに必要な Node.js 標準モジュール（`node:crypto`・`node:fs` など。npm パッケージは使わない）の使用と、テストの対象（指紋一覧）の追加を、この規則の改訂として開発資料の更新予定に挙げる。テストのファイル名は規則の命名（`test/<対象>[.<観点>].test.js`）に合わせて計画で決める。
    *  手順書には、照合のコマンド、照合が失敗したときの意味（`oz/` が改変された、または一覧と中身の版が合っていない）と対処（本リポジトリの `oz/` で置き換え直す）を書く。

*   **要件5: スプライトJSの約束を `oz/ENGINE_API.md` に移す（決定事項）**
    *  ゲーム側の AI が `oz/src/` を読まずにスプライトJSの約束を知ることができるように、開発資料 2.1章「スプライトJS」に書かれているエンジン側の約束（利用側は `import` して `draw(ctx)` を呼ぶだけであること、`draw` 以外のキーは読まないこと、`ctx` の状態を戻すこと、座標の単位・基準点・y 軸の向き、配置は呼ぶ側が `ctx` の変換で行うこと、スプライトは見た目だけを持つこと、つなぎのスプライトの形、組み立て用のJS（名前の頭に `_`）の扱い、形式の唯一の記載箇所がエディタのリポジトリであること）を、`oz/ENGINE_API.md` に新しい章として移す。
    *  移した後、開発資料 2.1章は、約束の唯一の記載箇所が `oz/ENGINE_API.md` の該当章であることを指すだけの短い記述にする（同じ内容を2か所に書かない）。本リポジトリの土台に固有の記述（例：土台の機体は前方を +X とする、現在の `ship.js` は手書きのつなぎのスプライトである）は、`oz/ENGINE_API.md`（ゲームに届く）に入れるか開発資料に残すかを計画で判断する。ゲームごとに変わる内容は `oz/ENGINE_API.md` に入れない（憲法3章「ゲーム固有知識の混入禁止」の趣旨）。
    *  `oz/ENGINE_API.md` の既存の章（1章〜22章）の内容は、新しい章を足すことと、章の追加に伴う最小限の参照の追記を超えて変更しない。章番号の付け方（末尾に足す、など）は計画で決める。
    *  `oz/ENGINE_API.md` の変更はエンジンの公開APIの変更ではない（コードは変えない）。憲法3章「公開APIとドキュメントの同時更新」の対象外である。

*   **要件6: ゲームの憲法に貼り付けるルールの文面（`GAME_RULES.md`）**
    *  ゲームのプロジェクトの `PROJECT_CONSTITUTION.md` の3章（絶対禁止事項）に、立ち上げの Step 2 でそのまま貼り付けられる文面にする。どこにどう貼るかを、文面の前に短く添える（貼り付ける部分と説明の部分の境目が分かるようにする）。
    *  文面には次を必ず含める（DIR の実装要件）。
       *  `oz/` を編集しない（追加・削除を含む）。
       *  `oz/src/` を読まない。エンジンについて知るには `oz/ENGINE_API.md` だけを読む。
       *  エンジンの機能が足りないときは、ゲーム側に回避策を書かない。不足を RES に記録し、本リポジトリへの連絡票（要件8）で伝え、エンジン側で直してから `oz/` を置き換える。
    *  本リポジトリの憲法3章のうち、ゲーム側（利用側）にも必要な規則を、ゲームのプロジェクトで通じる言葉に直して含めるかを計画で判断する。候補：利用側での基礎処理の直書き禁止（`js/` に `requestAnimationFrame`・`addEventListener`・`getContext` を書かない）、入口の一本化（`oz` からだけ import し `oz/src/` を import しない）、スプライトJSの手編集禁止とつなぎのスプライト、ロジックと描画の分離、時間の受け渡し、Canvas 状態の保護、グローバル汚染の禁止。本リポジトリの開発の手続き（DIR/REQ/RES の運用など）は `template-app` 側にあるので含めない。
    *  文面の中で本リポジトリの場所を示す必要があるときは、ローカルのパス `D:\ozlab\ozengine-web` と GitHub の `doze7220/ozengine-web` を使ってよい。

*   **要件7: Claude Code の設定例（`settings.example.json`）**
    *  ゲームのプロジェクトの `.claude/settings.json` に入れると、Claude Code が `oz/src/` のファイルを読むこと・書くことと、`oz/` 以下のファイルを編集・作成することを拒否する設定にする（`permissions` の `deny`）。
    *  規則の書式（パスの書き方、ワイルドカード）は、Claude Code の公式ドキュメント（`https://code.claude.com/docs/en/settings` および `https://code.claude.com/docs/en/iam` の permissions の項）で確かめてから書く。確かめた内容（参照した URL と、採用した書式の要点）を RES に記録する。
    *  ファイルを読むツール以外（シェルのコマンドで `oz/src/` のファイルを表示するなど）で読める場合があるかどうかを公式ドキュメントで確かめ、防げない経路があるなら、その旨と対策（追加の `deny` の規則、ルールの文面での禁止など）を手順書に書く。
    *  JSON の中にコメントは書けないので、設定の説明は手順書に書く。`template-app` に `.claude/settings.json` は無い（設定例をそのままコピーしてよい）が、すでにある場合は `permissions.deny` に足すことを手順書に書く。
    *  この設定が効いていること（`oz/src/` のファイルを読もうとすると拒否されること）の確かめ方を手順書に書く（発注者がテストプレイで確かめる）。

*   **要件8: エンジンの不足を本リポジトリへ伝える方法（手順書）**
    *  ゲームのプロジェクトで見つかったエンジンの不足は、本リポジトリの `_doc/BRIDGE_FROM_<ゲーム名>.md`（連絡票。例 `_doc/BRIDGE_FROM_VANGUARDRIFTER.md`）に書いて伝えることを手順書に書く。
    *  書く内容（何をしようとしたか、`oz/ENGINE_API.md` のどこが足りないか、ゲーム側の RES のパス、など）、書く人（ゲームのプロジェクトのセッション）、連絡票は本リポジトリのファイルであり、ゲーム側からはコミットしないこと（本リポジトリ側のセッションが取り込み、対応が済んだら削除する）を書く。
    *  本リポジトリ側では連絡票を受けて Interrupt で `oz/` と `oz/ENGINE_API.md` を直し、ゲーム側は直った `oz/` で置き換える（要件3）、という往復の流れを書く。

*   **要件9: 手順書どおりに作れることの確認**
    *  手順書を書き終えた後のタスクで、手順書のうちファイル操作で確かめられる部分（コピー、目印の削除、見本の素材の削除、設定例の配置、指紋一覧の照合）を、本リポジトリの外の一時フォルダで実際に行う。`template-app` のクローンは不要（コピーするのは本リポジトリの4つだけで足りる）。
    *  確かめること：`ozengine sample` が1件も残っていない。残った `.js` がすべて憲法1章の構文チェック（`node --input-type=module --check < <ファイル>`）を通る。残った `.js` の `import` が、存在するファイルか `oz` だけを指している。コピー直後の `oz/` で指紋一覧の照合が成功し、`oz/` のファイルを1つ書き換えると失敗する。
    *  ブラウザでの起動の確認と、Claude Code の設定が効くことの確認は、発注者のテストプレイで行うので、実装AIは行わない。
    *  確認に使った一時フォルダの場所と、確認の結果を RES に記録する。一時フォルダは、確認後に削除してよい。本リポジトリの中には何も作らない。
    *  確認で手順書の誤りや不足が見つかったら、同じタスクの中で手順書を直し、直した点を RES に記録する。

*   **要件10: 開発資料の見直し（持ち越し事項）**
    *  開発資料1章の「新規プロジェクトは、`template-app` を元にして…」の段落を、手順書（`_doc/newgame/NEW_GAME_GUIDE.md`）を指す記述に直す（手順の中身を開発資料に重ねて書かない）。1章のフォルダ構造に指紋一覧のファイルを加える。
    *  開発資料4章の `js/main.js` の行にある「見本の部分での最初のシーンへの解像度の受け渡しと `debug` の指定」は、目印を消した新規プロジェクトでは該当がなくなる。目印の有無にかかわらず通じる記述に直す。
    *  開発資料2.1章（要件5）、自動テストの規則（要件4）、指紋一覧の作り直しの運用（要件4）も、開発資料の更新予定に挙げる。
    *  開発資料への反映は最終の固定タスクでのみ行う。

## 【計画書に必ず含めるべきタスクごとの作業】
AIが作成する計画書（RES）のタスクリストには、個別の実装タスクの後に、以下の作業を必ず含めること。
*   コード修正完了後、JSDocコメントの記載漏れがないことを確認する（新しいテストファイルの先頭行の責務定義、補助関数の JSDoc を含む）。
*   `.js` を変更・作成したタスクでは、憲法1章の検証コマンド（構文チェックと、リポジトリのルートでの `node --test` の `fail 0`）を実行する。
*   タスク完了後、作業レポート（本RESファイル）の詳細作業内容を記載し完成させる。
*   開発資料（`PROJECT_ARCHITECTURE.md`）の記載に影響が出る場合は、資料本体は修正せず、その旨を『開発資料の更新予定』欄に追記する。

## 【計画書に必ず含めるべき固定タスク】
AIが作成する計画書（RES）のタスクリストには、全実装タスクの後に、以下のタスクを必ず含めること。
*   各タスクで記録した『開発資料の更新予定』を確認し、開発資料（`PROJECT_ARCHITECTURE.md`）へ反映する。開発資料に影響を与えない場合は、このタスクは不要とする。
    *   ※ 実装AIによる開発資料の書き換えは、本ワークフローにおいて原則禁止であるが、**この最終タスクのみ明示的な例外とする**。後続タスクが存在せず、資料の変更によって他タスクの前提が動く危険がないためである。個別の実装タスク内で資料を書き換えてはならない。
