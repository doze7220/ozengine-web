## 【実装要件】
エンジン（`oz/`）にマルチタッチの受信とバーチャルコントローラー（以下「バーチャルパッド」）の仕組みを入れ、土台（`js/`・`assets/`）の機体をスマートフォンで操作できるようにする。あわせて、スマートフォンでも一時停止・スロー・ミュートを操作できるように、土台のポーズを「プレイ中の汎用メニュー」に作り変える。

用語：本REQでは、画面のスティックとボタンをまとめて「バーチャルパッド」、スティックを「パッドのスティック」、バーチャルパッドのボタンを「パッドのボタン」と呼ぶ。既存の `Engine.addButton` で登録するボタン（エンジン 18章）は「画面のボタン」と呼んで区別する。

*   **要件1: 役割の分担（決定事項）**
    *  エンジン（`oz/`）が持つもの：マルチタッチの受信、指の追跡、パッドのスティックとパッドのボタンの当たり判定、押下状態（スティックの倒れ具合・押しているボタン）、キーへの変換、表示してよいかの判定（要件5）。
    *  利用側（土台の `js/`）が持つもの：配置（位置と大きさ）、キーの割り当て、画像のファイル名、画像の読み込みと描画。エンジンは `assets/` を参照せず、画像を読み込まず、描かない（憲法3章「依存方向は一方向のみ」「ゲーム固有知識の混入禁止」）。キーの割り当てや配置の既定値をエンジンに固定値で書かない。
    *  利用側が描画に必要な状態（表示するか、スティックのつまみの位置、各ボタンを押しているか）は、エンジンの公開APIから読めるようにする。公開APIの形（`Engine` の操作として足すか、起動設定 `Engine.start` の項目にするか、シーンごとの登録にするか、など）は計画で決める。

*   **要件2: バーチャルパッドの入力はキーボードと同じに見える**
    *  パッドのスティックを倒した方向とパッドのボタンに、利用側が `KeyboardEvent.code` の文字列（`'ArrowLeft'`・`'Space'` など）を割り当てる。押すと `Engine.isKeyDown` が `true` になり、押した瞬間にシーンの `onKeyDown` が呼ばれる。ゲームのロジックからは、キーボードで押したのと区別がつかない。
    *  スティックは、上下左右の4方向にそれぞれキーを割り当てられる（割り当てない方向があってよい）。中心付近の遊び（倒しても反応しない範囲）を設け、斜めに倒すと2方向のキーが同時に押される。倒し具合の数値（アナログ値）を読む API は作らない（DIR 2章「やらないこと」）。
    *  キーボードとバーチャルパッドで同じキーを押している場合、片方を離しても、もう片方を押している間は押したままとする。
    *  キーの確定と配信の時期は、キーボードの既存の規則（開発資料3章：毎フレーム1回の確定、1フレームより短い押下でも `onKeyDown` と1フレームの `isKeyDown`、フォーカスが外れたら解除）に合わせる。ブラウザのイベントの中からシーンの処理を呼ばない。
    *  土台のキーボードでの操作（左右キーで旋回、Space で加速、S でスロー、P でポーズ、M でミュート）は今までどおり動く（P の扱いは要件8）。

*   **要件3: マルチタッチと `onPointer`**
    *  複数の指を同時に扱い、スティックを動かしながら別の指でボタンを押せる。
    *  バーチャルパッドが処理した指（パッドのスティックかパッドのボタンの上で押し始めた指）は、離すまで、シーンの `onPointer` にも画面のボタンにも届かない。指を動かしてスティックやボタンの外へ出ても同じとする。
    *  それ以外の指の押下（バーチャルパッドの外で押し始めた指）は、今までどおり画面のボタン → 最前面のシーンの `onPointer` の順に届く。`onPointer` は単一ポインタのまま変えない（`pointer` の形 `{ type, x, y }` を変えない）。バーチャルパッドの外で押している指が同時に2本以上あるときの扱い（最初の1本だけを届ける、など）は計画で決め、`oz/ENGINE_API.md` 16章に書く。
    *  バーチャルパッドは指のタッチだけに反応し、マウスには反応しない（PC でのマウスの操作は今までと変わらない）。ペンの扱いは計画で決める。
    *  `oz/ENGINE_API.md` 16章の「マルチタッチは扱わない」の記述を、上の内容に合わせて直す。
    *  バーチャルパッドを使っていないとき（OFF のとき、または表示していないとき）の、ポインタ・ボタン・キーの動作は今までと変わらない。

*   **要件4: バーチャルパッドが反応するシーン**
    *  土台では、プレイのシーンでだけバーチャルパッドを表示し、反応させる。タイトルとロード中には表示しない。タイトルは今までどおり、画面のタップ（スタートボタンを含む）で開始できる。
    *  メニュー（要件8）を開いている間は、バーチャルパッドは反応せず、指はメニューのボタンに届く。メニューの暗幕の下にバーチャルパッドの絵が見えるかどうかは問わない。
    *  メニューを開いた時点で押していたパッドのキーの扱い（押したまま残すか、離した扱いにするか）は計画で決め、`oz/ENGINE_API.md` に書く。

*   **要件5: ON / OFF と表示の条件（決定事項）**
    *  `js/main.js` の設定でバーチャルパッドを ON / OFF できる。この設定は `ozengine sample` の目印の外に置く（新規プロジェクトにも残る）。
    *  OFF のときは、画面に何も表示されず、バーチャルパッドの画像も読み込まれず、今までの PC での操作だけが動く。
    *  ON のときも、ページを開いてから一度も指で画面に触れていない間は表示せず、反応もしない。指で触れたと分かった時点から表示する（以後、そのページを開いている間は表示したまま）。マウスとキーボードだけの PC では、ON でも表示されない。指で触れたかどうかの判定はエンジンが持ち、利用側が読めるようにする。

*   **要件6: 配置と見た目（決定事項）**
    *  パッドのスティックは画面の左下に固定する（触れた場所に現れる方式にはしない）。パッドのボタンは加速の1つだけを画面の右下に置き、`Space` を割り当てる。スティックの左右に `ArrowLeft`・`ArrowRight` を割り当てる（上下には割り当てない）。ポーズ・スロー・ミュートのパッドのボタンは置かない（要件8のメニューで操作する）。
    *  大きさと位置の具体的な値は、論理解像度 1280×720 の横向きのスマートフォンで親指で操作しやすい値を計画で決める。
    *  スティックのつまみは指に付いて動き（土台の円の外へは出ない）、指を離すと中央に戻る。パッドのボタンは押している間、見た目が変わる。
    *  画像は `assets/images/vpad/` に置く。ファイル名と形式（SVG / PNG など）は、利用側の定義（配置とキーの割り当てと同じ場所）で指定でき、既定では SVG を指定する。既定の SVG の絵柄は、半透明の白い円と線だけのシンプルなもの（スティックの土台とつまみ、加速のボタンは二重の矢印）とし、具体的なファイルの構成（押している間の見た目を別の画像にするか、など）は計画で決める。
    *  同じファイル名の画像に置き換えると見た目が変わる。定義のファイル名を書き換えれば、別の名前・別の形式（PNG など）の画像も使える。

*   **要件7: 目印と新規プロジェクトでの扱い**
    *  バーチャルパッドの定義（配置、キーの割り当て、画像のファイル名）、画像の読み込みと描画のコード、既定の画像には `ozengine sample` の目印を付けない（新規プロジェクトに残す）。
    *  土台のプレイのシーンでバーチャルパッドを使う部分など、土台のゲームに固有の部分には目印を付ける。
    *  目印の付いた部分をすべて消しても、ON と OFF の両方でエラーなく起動する（憲法3章「サンプルコードの目印」）。
    *  目印の付いていないコードが、目印の付いたコード（`js/scenes/uiText.js`・`js/scenes/mute.js` など、ファイル全体に目印のあるファイルを含む）を import してはならない。
    *  目印を消した後も、既定の画像が手順書 `_doc/newgame/NEW_GAME_GUIDE.md` 6-3（`index.html`・`js/` から参照されない `assets/` のファイルを消す）で消されない形にする。`js/` から参照される形にするか、6-3 の記述を直すかは計画で決める（DIR 持ち越し事項）。

*   **要件8: プレイ中の汎用メニュー（ポーズの作り変え。決定事項）**
    *  プレイ画面に、メニューを開く画面のボタン（`Engine.addButton`）を置く。PC でもスマートフォンでも常に表示し、マウスでも指でも押せる。位置は、右上の状態表示（ミュート・スロー）と重ならない場所を計画で決める。
    *  メニューを開いている間はゲームが一時停止する（今のポーズ用のシーンと同じく、プレイのシーンの上に積む）。キーボードの P でもメニューを開閉できる。
    *  メニューの項目は次の4つとし、それぞれ画面のボタンとして押せる。
       *  閉じる：メニューを閉じてプレイに戻る。
       *  スロー ON/OFF：スローを切り替える。今の状態が分かる表示にする。
       *  ミュート ON/OFF：ミュートを切り替える。今の状態が分かる表示にする（保存は今までどおり）。
       *  タイトルに戻る：タイトルへ切り替える。タイトルに戻ったらスローは解除する。
    *  メニューの中で、キーボードの M でミュート、S でスローを切り替えられる。メニューの項目のボタンの外を押しても何も起きない（今のポーズのように画面のどこを押しても再開する動作はやめる）。
    *  **新規プロジェクトで作り変えられる形にする：** メニューの画面の仕組み（項目の並べ方、項目ごとの画面のボタンの登録、暗幕と項目の描画、開閉による一時停止）は目印を付けずに新規プロジェクトに残し、項目の中身（上の4項目とその処理）は土台のゲームに固有の部分として目印を付ける。新規プロジェクトでは、残った仕組みに自分の項目を渡して使う。仕組みと項目の分け方、ファイルの置き場所と名前は計画で決める。
    *  今の `js/scenes/PauseScene.js` を作り変えるか、別のファイルに置き換えて削除するかは計画で決める。

*   **要件9: `oz/ENGINE_API.md`**
    *  `oz/ENGINE_API.md` だけを読んで、バーチャルパッドの ON / OFF、配置とキーの割り当ての設定、表示の条件（要件5）、描画に使う状態の読み方（見た目の描き方）、`onPointer` と画面のボタンとの関係が分かるようにする。画像の読み込みと描画は利用側が行うこと、その書き方の例を含める。
    *  1章の「利用側が使えるのは次の5つだけ」と `Engine` の説明、16章（ポインタ入力）、17章（キーボード入力）、19章（入力の届くタイミングと順序）など、既存の章で記述が変わる箇所を直す。章の追加の位置と番号の付け方は計画で決める。
    *  要件11で `index.html` を変える場合は、2章の `index.html` の例も同じに直す。
    *  公開APIを足すので、憲法3章「公開APIとドキュメントの同時更新」に従い、公開APIを足すタスクの中で `oz/ENGINE_API.md` を更新する。

*   **要件10: 新規プロジェクトの手順書（`_doc/newgame/NEW_GAME_GUIDE.md`）**
    *  バーチャルパッドの既定の画像は、新規プロジェクトで同じファイル名の画像で上書きして差し替えること（または定義のファイル名を書き換えて自分の画像を指すこと）を書く（DIR 実装要件）。
    *  要件7の結論に合わせて 6-3（見本の素材を消す）の記述を直す。6-3 の「現時点の土台での例」も、今回の変更後の土台に合わせて直す。
    *  目印を消した後に残るバーチャルパッドの定義・メニューの仕組みと、`js/main.js` の ON / OFF の設定について、新規プロジェクトでどう使うかを短く書く（7章「ゲームごとに変える箇所」など、置き場所は計画で決める）。
    *  手順書は、コードを読まない発注者にも分かる言葉で、操作と期待する結果の形で書く。

*   **要件11: スマートフォンでの表示の最小限の調整**
    *  スマートフォンの実機で、ページが縮小表示されず、指で押し続けたり2本の指で操作したりしても、ページの拡大・スクロール・文字の選択・長押しのメニューが起きずに遊べるようにする。そのために必要な最小限の変更（`index.html` の viewport の指定、エンジンが canvas に設定するスタイルなど）を計画で決める。
    *  高解像度への対応（`devicePixelRatio`）、iOS の音の再開、縦向きの画面への対応は、本作業では扱わない（Phase 03-03 以降）。土台は横向きで遊ぶ前提でよい。

*   **要件12: 公開先**
    *  テストプレイは、本リポジトリを GitHub Pages で公開したページ（`/ozengine-web/` の下）で行う。コードと定義の中のパスは `/` から始めない（相対パスにする）。

*   **要件13: 自動テストと指紋一覧**
    *  `oz/` を変更するタスクでは、最後に指紋一覧 `oz/FINGERPRINTS.txt` を作り直し、`node --test` が `fail 0` であることを確かめる（開発資料4章「指紋一覧の規則」）。
    *  バーチャルパッドの当たり判定やキーへの変換を、`window` に依存しない形に分けられる場合は、自動テスト（開発資料4章「自動テスト（`test/`）の規則」）を足すかを計画で判断する。足す場合は、テストの対象の追加を開発資料の更新予定に挙げる。

## 【計画書に必ず含めるべきタスクごとの作業】
AIが作成する計画書（RES）のタスクリストには、個別の実装タスクの後に、以下の作業を必ず含めること。
*   コード修正完了後、JSDocコメントの記載漏れがないことを確認する（新しいファイルの先頭行の責務定義を含む）。
*   `.js` を変更・作成したタスクでは、憲法1章の検証コマンド（構文チェックと、リポジトリのルートでの `node --test` の `fail 0`）を実行する。
*   `oz/` の中のファイルを変更・作成したタスクでは、指紋一覧を作り直す。
*   タスク完了後、作業レポート（本RESファイル）の詳細作業内容を記載し完成させる。
*   開発資料（`PROJECT_ARCHITECTURE.md`）の記載に影響が出る場合は、資料本体は修正せず、その旨を『開発資料の更新予定』欄に追記する。

## 【計画書に必ず含めるべき固定タスク】
AIが作成する計画書（RES）のタスクリストには、全実装タスクの後に、以下のタスクを必ず含めること。
*   各タスクで記録した『開発資料の更新予定』を確認し、開発資料（`PROJECT_ARCHITECTURE.md`）へ反映する。開発資料に影響を与えない場合は、このタスクは不要とする。
    *   ※ 実装AIによる開発資料の書き換えは、本ワークフローにおいて原則禁止であるが、**この最終タスクのみ明示的な例外とする**。後続タスクが存在せず、資料の変更によって他タスクの前提が動く危険がないためである。個別の実装タスク内で資料を書き換えてはならない。

## 【計画立案時の絶対遵守ルール (Constraints)】
*   **アーキテクチャの維持** : 憲法3章の絶対禁止事項に反する設計をしてはならない。特に、エンジンから `js/`・`assets/` を参照しない、エンジンにキー割り当て・配置・画像のファイル名を固定値で書かない、`js/` に `addEventListener` などを書かない、エンジンはページに要素を追加しない（バーチャルパッドは canvas に描く）、更新処理の中で描画しない・描画処理の中で状態を変えない。
*   **責務の分離** : 指の追跡とバーチャルパッドの判定を `Input` に詰め込んで肥大化させない。新しいモジュールに分けるかを計画で判断し、分ける場合は開発資料3章の依存の向き（`Engine` が生成して引数で渡す形）と4章の責務表に合わせ、更新予定に挙げる。
