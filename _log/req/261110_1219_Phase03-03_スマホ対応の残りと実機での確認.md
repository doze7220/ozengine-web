## 【実装要件】
スマートフォン、特に iPhone の Safari で土台を遊ぶときに残っている問題を片付ける。具体的には、割り込みで止まった音の再開、高解像度の画面への対応、最初の入力を受ける画面（以下「boot 画面」）の追加、`oz/ENGINE_API.md` 21章「タッチの最初の押下」の記述の見直しを行う。PC のブラウザでの土台の動作は今までと変えない。

*   **要件1: 割り込みで止まった音の再開（iPhone の Safari）**
    *  電話の着信、他のアプリへの切り替え、画面のロックなどでブラウザが音を止めたあと、土台に戻って画面に触れる（またはキーを押す）と、音がまた鳴る。BGM が流れていた場合は BGM が戻り、以後の `playSe` も鳴る。
    *  今の `oz/src/Sound.js` は、AudioContext が `running` になると再開用のイベントを解除するため、その後にブラウザが止めた場合は二度と再開しない。止まったことを検知して再開用のイベントを登録し直すなど、再開の仕組みを計画で決める。iOS の Safari は止めた状態を `suspended` ではなく `interrupted` とすることがある点に注意する。
    *  ユーザーの入力なしに再開を試みてよいか（画面に戻っただけで鳴り始めてよいか）は、ブラウザが許す範囲で計画で決める。入力のあとに鳴ることは必須とする。
    *  `Sound` の公開APIは増やさず、変えない。止まっている間に呼ばれた `playSe`・`playBgm` の扱い（捨てる、再開後に鳴る、など）は計画で決め、`oz/ENGINE_API.md` 21章に書く。
    *  `oz/ENGINE_API.md` 21章の「時間」節の「タブを裏に回しても止まらない」は、スマートフォンでは他のアプリへの切り替えなどでブラウザが音を止めることがある旨と、戻って画面に触れると再開する旨に合わせて直す。

*   **要件2: 高解像度の画面への対応（決定事項）**
    *  エンジンが常に自動で行い、起動設定（`Engine.start`）の項目は増やさない。
    *  Canvas の画素数（`canvas.width`・`canvas.height`）を、論理解像度ではなく、画面に表示している大きさ（CSS の画素数）に `devicePixelRatio` を掛けた大きさにする。倍率の上限は 2 とする（`devicePixelRatio` が 3 の iPhone でも 2 として扱う）。ウィンドウの大きさが変わったとき、表示の大きさと一緒に Canvas の画素数も追従する。
    *  シーンの `draw` に渡す `ctx` の座標は、今までどおり論理座標（`width`・`height`）のままにする。シーンの描画コードと `onPointer` の座標、画面のボタン・バーチャルパッドの当たり判定は変えなくてよい。
    *  Canvas の画素数を変えると `ctx` の状態が初期化される点、`Layers` の消去が `ctx.canvas.width` を使っている点に注意し、拡大の変換をどこで毎フレーム設定するかを、開発資料4章の責務表（`Screen`・`Layers`・`GameLoop`）に合わせて計画で決める。`DebugOverlay` の表示も論理座標のまま正しい位置に出る。
    *  `oz/ENGINE_API.md` 4章（画面）に、Canvas の画素数が論理解像度と一致しないこと、`ctx.canvas.width` を論理解像度として使わないこと、`ctx.setTransform` で変換を初期化すると論理座標が崩れること（変換を変えるときは `save`・`restore` の中で `translate`・`scale` などを使うこと）を書く。
    *  PC での動作（座標、操作、描画の位置と大きさ）は今までと変わらない。大きなモニターの PC では今までより線と文字がくっきりするが、これは意図した変化とする。
    *  バーチャルパッドの既定の画像（SVG）が iPhone の Safari でぼやけるかどうかは、テストプレイで確かめる（RES の懸念事項に挙げる）。本作業では画像の形式を変えない。
    *  高解像度への対応の結果（倍率の上限と、Canvas の画素数の決まり方）は、Phase 04（キャンバスキャッシュ）で焼き付ける解像度を決める前提になる。開発資料の更新予定に挙げる。倍率を利用側に公開する API は、本作業では作らない。
    *  `test/Screen.test.js` が今の `Screen` の動作（`canvas.width` が論理解像度になること など）を前提にしている場合は、新しい動作に合わせて直す。`devicePixelRatio` と上限の扱いのテストを足すかは計画で判断する。

*   **要件3: boot 画面（決定事項）**
    *  土台の最初に、真っ黒な背景に「TAP SCREEN」の文字だけを表示する画面を置く。この画面は、ブラウザに最初の入力を与えて音を鳴らせる状態にするためのものである。シーンとして、タイトルやプレイなどのゲーム本体のシーンとは分けて作る（ファイル名・クラス名は `BootScene` などを計画で決める）。
    *  進め方：指で押した場合とマウスで押した場合は、離したとき（`onPointer` の `'up'`）に次の画面へ進む。キーボードは、`Escape` 以外のキーを押したとき（`onKeyDown`）に進む（`Escape` はエンジンが最初の入力に数えないため）。
    *  boot 画面の後はタイトルへ進む。素材のロード（今の `LoadScene`）との順序（ロード → boot → タイトル、または boot → ロード → タイトル）は、要件4で boot 画面から SE を鳴らせることを条件に計画で決める。
    *  タイトルに入ったら、入力を待たずにすぐ BGM が流れる（boot 画面で最初の入力が済んでいるため）。今の `TitleScene` の、入力への反応の中で `playBgm` を呼ぶ処理を残すかは計画で決める。
    *  **新規プロジェクトで自由に作り変えられる形にする：** boot 画面の仕組み（「TAP SCREEN」の表示、入力で次の画面へ進むこと）には `ozengine sample` の目印を付けずに新規プロジェクトに残す。新規プロジェクトでは、表示の内容や次に進む画面を自分で書き換えて使う。次に進む画面をどう指定するか（`js/main.js` から渡す、など）は計画で決める。
    *  目印の付いた部分をすべて消しても、エラーなく起動し、boot 画面が表示され、押すと次の画面（目印を消した後に残る空のシーンなど）へ進む（憲法3章「サンプルコードの目印」）。目印の付いていないコードが、目印の付いたコード（`js/scenes/uiText.js` など、ファイル全体に目印のあるファイルを含む）を import してはならない。
    *  boot 画面にバーチャルパッドは表示しない（今までどおりプレイのシーンでだけ表示する）。

*   **要件4: タッチの最初の押下の実機での確認（boot 画面による簡易確認。決定事項）**
    *  確認用のページは作らない。代わりに、boot 画面で押した瞬間（`onPointer` の `'down'` と、`onKeyDown`）に短い SE（土台の既存の SE）を1回鳴らす。この SE を鳴らす部分は土台の見本として `ozengine sample` の目印を付ける。
    *  発注者がテストプレイで、iPhone の Safari を含むスマートフォンの実機で boot 画面を押し、SE が押した瞬間に鳴るか、指を離したときに鳴るかを耳で確かめる。押したままの間に何度も鳴らした SE がまとめて鳴る件（今の21章の2つ目の項目）は確かめない。
    *  実機での確認の結果は、テストプレイの後に発注者から受け取る。そのため、確認の結果を `oz/ENGINE_API.md` 21章「タッチの最初の押下」に反映するタスクを、ほかの実装タスクとは分けて置く（要件5）。このタスクは、テストプレイの結果を受け取った後に、結果を添えて実行を指示する。

*   **要件5: `oz/ENGINE_API.md` 21章「最初の入力まで」「タッチの最初の押下」**
    *  「タッチの最初の押下」の最後の項目（PC の Chrome のタッチの再現機能でだけ確認した、の記述）を、要件4の実機での確認の結果に合わせて直す。確かめていない項目（押したままの間の SE がまとめて鳴る件）は、確かめていないことが分かる書き方にする。
    *  最初の入力を受けるだけの画面（土台の boot 画面のようなもの）を置き、その画面を離れてから音を使えば、この節の影響を受けないことを書く。バーチャルパッドの指から生まれた `onKeyDown` が最初の入力になる場合も、この書き方で避けられる旨を書く（パッドの指が最初の入力になったときの鳴り方そのものは確かめない）。
    *  iPhone では本体の消音スイッチ（マナーモード）が入っていると音が鳴らないこと、エンジンはこれに対応しないことを書く（決定事項）。
    *  要件5のうち、実機での確認の結果に依存しない部分（boot 画面の書き方、消音スイッチ）を要件4のタスクより前のタスクで書くか、まとめて要件4のタスクで書くかは計画で決める。

*   **要件6: 公開先**
    *  テストプレイは、本リポジトリを GitHub Pages で公開したページ（`/ozengine-web/` の下）で行う。コードの中のパスは `/` から始めない（相対パスにする）。

*   **要件7: 新規プロジェクトの手順書（`_doc/newgame/NEW_GAME_GUIDE.md`）**
    *  目印を消した後に boot 画面が残ること、新規プロジェクトで表示の内容と次に進む画面を書き換えて使うことを、7章「ゲームごとに変える箇所」などに短く書く。置き場所は計画で決める。
    *  7-2「起動の確認」など、起動したときに見える画面の記述があれば、boot 画面が最初に表示される形に直す。6-3 の「現時点の土台での例」に影響があれば直す。
    *  手順書は、コードを読まない発注者にも分かる言葉で、操作と期待する結果の形で書く。

*   **要件8: 自動テストと指紋一覧**
    *  `oz/` を変更するタスクでは、最後に指紋一覧 `oz/FINGERPRINTS.txt` を作り直し、`node --test` が `fail 0` であることを確かめる（開発資料4章「指紋一覧の規則」）。

## 【計画書に必ず含めるべきタスクごとの作業】
AIが作成する計画書（RES）のタスクリストには、個別の実装タスクの後に、以下の作業を必ず含めること。
*   コード修正完了後、JSDocコメントの記載漏れがないことを確認する（新しいファイルの先頭行の責務定義を含む）。
*   `.js` を変更・作成したタスクでは、憲法1章の検証コマンド（構文チェックと、リポジトリのルートでの `node --test` の `fail 0`）を実行する。
*   `oz/` の中のファイルを変更・作成したタスクでは、指紋一覧を作り直す。
*   タスク完了後、作業レポート（本RESファイル）の詳細作業内容を記載し完成させる。
*   開発資料（`PROJECT_ARCHITECTURE.md`）の記載に影響が出る場合は、資料本体は修正せず、その旨を『開発資料の更新予定』欄に追記する。

## 【計画書に必ず含めるべき固定タスク】
AIが作成する計画書（RES）のタスクリストには、全実装タスクの後に、以下のタスクを必ず含めること。
*   各タスクで記録した『開発資料の更新予定』を確認し、開発資料（`PROJECT_ARCHITECTURE.md`）へ反映する。開発資料に影響を与えない場合は、このタスクは不要とする。
    *   ※ 実装AIによる開発資料の書き換えは、本ワークフローにおいて原則禁止であるが、**この最終タスクのみ明示的な例外とする**。後続タスクが存在せず、資料の変更によって他タスクの前提が動く危険がないためである。個別の実装タスク内で資料を書き換えてはならない。
    *   この固定タスクは、要件4の実機での確認の結果を21章に反映するタスクの後に置く。

## 【計画立案時の絶対遵守ルール (Constraints)】
*   **アーキテクチャの維持** : 憲法3章の絶対禁止事項に反する設計をしてはならない。特に、エンジンから `js/`・`assets/` を参照しない、エンジンに解像度・シーン名などを固定値で書かない（倍率の上限 2 はエンジンの仕様として持ってよい）、`js/` に `addEventListener`・`requestAnimationFrame`・`getContext` を書かない、エンジンはページに要素を追加しない、更新処理の中で描画しない・描画処理の中で状態を変えない、`Sound` 以外が独自に時間を取得しない。
*   **責務の分離** : 高解像度への対応を、`Screen`（表示サイズと画素数）、`Layers`（消去）、`GameLoop`（描画の呼び出し）の責務表に合わせて置く。特定のモジュールに詰め込まない。責務の範囲が変わるモジュールは、ファイル先頭の責務定義と開発資料4章の責務表の更新予定に挙げる。
*   **変更してよいファイル** : `oz/src/` のファイル（変更）、`oz/ENGINE_API.md`、`oz/FINGERPRINTS.txt`（作り直しのみ）、`js/` のファイル（変更・新規作成）、`test/Screen.test.js`（要件2の範囲のみ）、`test/` の新しいテストファイル（要件2で足す場合のみ）、`_doc/newgame/NEW_GAME_GUIDE.md`（要件7）、`PROJECT_ARCHITECTURE.md`（最終の固定タスクのみ）、作業計画書（本RES）に限る。`oz/index.js`・`oz/VERSION`・`index.html`・`PROJECT_CONSTITUTION.md`・`CLAUDE.md`・`README.md`・`test/Screen.test.js` 以外の既存の `test/*.test.js`・`assets/` の素材・`_doc/` の他のファイルは変更しない。公開APIを増やす必要が出た場合は、計画に書く前に疑問点として報告する。
*   **外部依存の禁止** : 外部ライブラリ・npm パッケージ・`package.json`・ビルドを使わない。
*   **スコープの分割** : エンジンの音の再開、エンジンの高解像度への対応、土台の boot 画面、手順書、21章への実機の確認結果の反映は、混同しない粒度のタスクに分ける。エンジンの動作を変えるタスクと、その動作の `oz/ENGINE_API.md` の更新は同じタスクにする（憲法3章）。利用側の `js/` を実装するタスクは `oz/src/` を読まず `oz/ENGINE_API.md` だけを参照するので（憲法3章）、エンジンと `oz/ENGINE_API.md` のタスクより後に置く。
*   **確認の範囲** : 実装AIはブラウザや実機での動作確認を行わない（発注者のテストプレイで行う）。テストプレイで確かめるべき点（割り込みのあとの音の再開、iPhone での線と文字のくっきり具合、バーチャルパッドの画像のぼやけ、boot 画面の SE が鳴る時期、boot 画面のタップ・クリック・キーで進むこと、タイトルですぐ BGM が流れること、PC での動作が変わらないこと、など）を、RES の懸念事項・目視確認推奨箇所に挙げる。
*   **先回りの禁止** : 倍率を公開する API、消音スイッチ中でも鳴らす対応、確認用のページ、フルスクリーン、縦向きの画面への対応は作らない。
