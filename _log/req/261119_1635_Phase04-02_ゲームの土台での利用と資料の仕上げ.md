## 【実装要件】
エンジンに入ったキャンバスキャッシュ（`oz/ENGINE_API.md` 25章の `CanvasCache`。描く処理を前もって Canvas に焼き付けておき、毎フレームはその画像を貼るだけにする仕組み）を使って、ゲームの土台の機体を描くように変える。あわせて、新しいゲームがキャンバスキャッシュを使い始められる状態に資料をそろえる。

*   **要件1: 土台の機体を焼き付けで描く**
    *  タイトルとプレイの両方で、機体（`assets/sprites/ship.js`）を、`CanvasCache` で焼き付けた絵で描く。範囲には `ship.js` の `bounds` をそのまま渡し、倍率（`scale`）は今の表示の大きさ（`1`）とする。機体の位置・回転の付け方は今と変えない。
    *  焼き付けはシーンが始まるときに作り、シーンが終わるとき（`destroy`）に手放す（`oz/ENGINE_API.md` 25章「作れる時期」）。タイトルからプレイ、プレイからタイトルへ切り替えたときに、手放した焼き付けを描いてエラーになることがないようにする。今のシーン（`FlightScene` とその派生の `TitleScene`・`PlayScene`）の `init` と `destroy` の持ち方を確かめ、どこで作ってどこで手放すかを計画で決める。
    *  星・トレイル・風・文字など、機体以外の描画は変えない（焼き付けにしない）。
    *  `js/` を実装するタスクでは、`oz/src/` を読まず `oz/ENGINE_API.md` だけを参照する（憲法3章）。`oz/ENGINE_API.md` 25章で分からないこと、例のとおりに書いて動かないことがあれば、RES に不足として記録し、要件4で直す。

*   **要件2: 見比べ用の一時的な切り替え（決定事項）**
    *  テストプレイで、機体を「直接描く（今までの描き方）」と「焼き付けで描く」で見比べられるように、プレイ中のメニュー（今の「閉じる」「スロー」「ミュート」「タイトルに戻る」の並び）に、一時的な項目「焼き付け: ON」／「焼き付け: OFF」を足す。選ぶたびに切り替わり、ON のときは焼き付けで、OFF のときは直接描く。既定は ON とする。
    *  PC では、メニューを開かなくてもキー1つで切り替えられるようにする（キーは既存のキー割り当てと重ならないものを計画で決め、RES の目視確認推奨箇所に書く）。スマートフォンでは、メニューの項目で切り替える。
    *  切り替えた状態は、タイトルとプレイの両方の機体に効く（タイトルへ戻っても状態が分かるようにするかは計画で決める）。状態の持ち方は、今の `js/scenes/slow.js`（スローの切り替え）のように、責務を分けて置く。
    *  **この切り替えは、テストプレイで発注者の OK が出たあとに消す。** 消したあとは、機体は常に焼き付けで描かれ、メニューは今の4項目に戻る。消すタスクは、ほかの実装タスクとは分けて最後の方に置き、テストプレイの結果を受け取った後に実行を指示する（実装セッションがテストプレイの OK を受けてから実行する）。消すタスクの後に、起動して機体が表示されることを確かめる短い確認を、目視確認推奨箇所に書く。
    *  切り替えを足すコードと消すコードに、`ozengine sample` の目印の扱いの崩れ（目印の無いコードが目印の付いたコードを import する、など）が起きないようにする（憲法3章「サンプルコードの目印」）。

*   **要件3: テストプレイで確かめること**
    *  次を、発注者が PC とスマートフォン（GitHub Pages で公開したページ）で確かめられるように、RES の目視確認推奨箇所に、操作と期待する結果の形で書く。
        *  機体が回転しながら飛んでいても、切り替えの ON と OFF で見た目の区別がつかない（位置・大きさ・くっきり具合。回転したときにギザギザが目立たず、ぼやけすぎない）。
        *  PC でウィンドウの大きさを変えたとき、スマートフォンで画面の向きを変えたとき、ブラウザの拡大率を変えたときに、焼き付けの機体がぼやけない（古い粗い絵が残らない）。
        *  機体の縁が欠けていない。
        *  ウィンドウの大きさを手で変えている間に、動きが重くならないか（大きさが変わるたびに焼き直しが起きるため。気になるかどうかを発注者が判断する）。
        *  タイトルとプレイを何度か行き来しても、エラーにならず機体が表示される。
    *  テストプレイの結果、見た目の区別がつく、ぼやける、などの問題が出た場合は、実装セッションは推測で直さず、状況を完了報告（未完了）で現場設計セッションに返す（エンジンの直し方は設計で判断する）。

*   **要件4: `oz/ENGINE_API.md` の仕上げ**
    *  25章（キャンバスキャッシュ）は前の作業で書かれている。要件1で土台に組み込んだ結果と照らし、使い方・使い方の例・焼き直しの扱い・注意点（表示する倍率と大きく違う倍率で描くと、拡大ではぼやけ、縮小では細い線が淡くなること）に、直すところがないかを確かめる。25章の使い方の例は、前の作業では実際に動かしていない。土台に組み込んだ書き方と食い違うところや、例のとおりに書いて動かないところがあれば直す。
    *  シーンの派生クラスで `init`・`destroy` を受け継ぐときの注意（派生クラスの `init` から基底クラスの `init` を呼ぶ、など）が要ると分かった場合は、25章の例に書き足すかを計画で判断する。
    *  23章（スプライトJS）から 25章へ、多数のスプライトを描くときにキャンバスキャッシュを使えることが分かる参照を足すかを計画で判断する。
    *  直すところが無ければ、`oz/ENGINE_API.md` は変えず、確かめた結果を RES に書く。

*   **要件5: 新規プロジェクトの手順書と指紋一覧**
    *  新規プロジェクトの手順書（`_doc/newgame/` の `NEW_GAME_GUIDE.md`・`GAME_RULES.md`・`settings.example.json`）を読み、`oz/` に `CanvasCache` が加わったこと、土台の機体が焼き付けで描かれるようになったことで、直す必要がある箇所が残っていないかを確かめる。直す必要があれば直す。直す必要が無ければ変えず、確かめた結果（どの節を見て、なぜ直さなくてよいか）を RES に書く。
    *  `oz/` の中のファイルを変更するタスクでは、最後に指紋一覧 `oz/FINGERPRINTS.txt` を作り直し、`node --test` が `fail 0` であることを確かめる（開発資料4章「指紋一覧の規則」）。`oz/` を変更しない場合も、作業の最後に `node --test` が `fail 0` であること（指紋一覧が `oz/` と合っていること）を確かめる。

*   **要件6: 公開先**
    *  テストプレイは、本リポジトリを GitHub Pages で公開したページ（`/ozengine-web/` の下）で行う。コードの中のパスは `/` から始めない（相対パスにする）。

## 【計画書に必ず含めるべきタスクごとの作業】
AIが作成する計画書（RES）のタスクリストには、個別の実装タスクの後に、以下の作業を必ず含めること。
*   コード修正完了後、JSDocコメントの記載漏れがないことを確認する（新しいファイルの先頭行の責務定義を含む）。
*   `.js` を変更・作成したタスクでは、憲法1章の検証コマンド（構文チェックと、リポジトリのルートでの `node --test` の `fail 0`）を実行する。
*   `oz/` の中のファイルを変更・作成したタスクでは、指紋一覧を作り直す。
*   タスク完了後、作業レポート（本RESファイル）の詳細作業内容を記載し完成させる。
*   開発資料（`PROJECT_ARCHITECTURE.md`）の記載に影響が出る場合は、資料本体は修正せず、その旨を『開発資料の更新予定』欄に追記する。

## 【計画書に必ず含めるべき固定タスク】
AIが作成する計画書（RES）のタスクリストには、全実装タスクの後に、以下のタスクを必ず含めること。
*   各タスクで記録した『開発資料の更新予定』を確認し、開発資料（`PROJECT_ARCHITECTURE.md`）へ反映する。開発資料に影響を与えない場合は、このタスクは不要とする。
    *   ※ 実装AIによる開発資料の書き換えは、本ワークフローにおいて原則禁止であるが、**この最終タスクのみ明示的な例外とする**。後続タスクが存在せず、資料の変更によって他タスクの前提が動く危険がないためである。個別の実装タスク内で資料を書き換えてはならない。
    *   この固定タスクは、要件2の切り替えを消すタスクの後に置く。開発資料には、切り替えを消した後の最終の形だけを書く（一時的な切り替えのことは書かない）。

## 【計画立案時の絶対遵守ルール (Constraints)】
*   **アーキテクチャの維持** : 憲法3章の絶対禁止事項に反する設計をしてはならない。特に、`js/` に `addEventListener`・`requestAnimationFrame`・`getContext` を書かない、`js/` から `oz/src/` を import しない（`'oz'` から import する）、更新処理の中で描画しない・描画処理の中で状態を変えない（焼き付けを作る・手放す・切り替えの状態を変えるのは `draw` の外で行う）、`ctx` の状態を外へ漏らさない、`window` にプロパティを足さない。
*   **責務の分離** : 開発資料4章の `js/` の責務表に合わせる。機体の配置（位置と回転の設定と `draw` の呼び出し）は `js/scenes/`、見た目は `assets/sprites/` のまま。`js/entities/Ship.js` に描画を持ち込まない。見比べ用の切り替えの状態は、シーンのファイルに詰め込まず、`slow.js` のように分けて置く。責務の範囲が変わるファイルは、ファイル先頭の責務定義と開発資料4章の責務表の更新予定に挙げる。
*   **変更してよいファイル** : `js/scenes/` のファイル（変更、見比べ用の切り替えのための新規作成と、その削除）、`oz/ENGINE_API.md`（要件4で直す場合のみ）、`oz/FINGERPRINTS.txt`（作り直しのみ）、`_doc/newgame/NEW_GAME_GUIDE.md`・`_doc/newgame/GAME_RULES.md`・`_doc/newgame/settings.example.json`（要件5で直す必要がある場合のみ）、`PROJECT_ARCHITECTURE.md`（最終の固定タスクのみ）、作業計画書（本RES）に限る。`oz/src/`・`oz/index.js`・`oz/VERSION`・`assets/`（`ship.js` を含む。エディタの書き出しファイルで手で編集しない）・`index.html`・`js/scenes/` 以外の `js/`・`test/`・`PROJECT_CONSTITUTION.md`・`CLAUDE.md`・`README.md`・`_doc/newgame/` 以外の `_doc/` は変更しない。エンジン（`oz/src/`）の変更が要ると分かった場合は、計画に書く前に疑問点として報告する。
*   **外部依存の禁止** : 外部ライブラリ・npm パッケージ・`package.json`・ビルドを使わない。
*   **スコープの分割** : 機体を焼き付けで描く変更、見比べ用の切り替えの追加、`oz/ENGINE_API.md` の仕上げ、手順書の確認、切り替えを消す変更は、混同しない粒度のタスクに分ける。`oz/ENGINE_API.md` を直すタスクは、土台に組み込んだ結果を踏まえるため、要件1のタスクより後に置く。
*   **確認の範囲** : 実装AIはブラウザや実機での動作確認を行わない（発注者のテストプレイで行う）。要件3の確認事項と、見比べ用の切り替えの操作方法（メニューの項目とキー）を、RES の懸念事項・目視確認推奨箇所に挙げる。
*   **今回やらないこと** : 次は作らない・変えない。エンジン（`oz/src/`）の変更。機体以外の描画（星・トレイル・風・文字）の焼き付け。多数のスプライトを描いて軽さを測る仕組み（軽くなるかの確認は、多数のスプライトを描くゲームの側で行う）。画素の加工、線の太さを倍率で割り戻す描き方、スプライトシート・アトラス、アニメーションの焼き付け。`oz/VERSION` の更新。見比べ用の切り替えを土台に残すこと。
