## 【実装要件】
画面に重ねて開く窓と、その中に並べる UI 部品の共通の仕組み（描き方の差し替え、値のつなぎ方、ポインタの受け方）をエンジンに入れ、最も単純な部品であるボタンと、数値・文字の表示で使えるようにする。エンジンは素っ気ない標準の見た目で描き、ゲームは部品の種類ごとに描く関数を渡して見た目を差し替えられる。ゲーム（バトリティア）が、開発用の調整パネル（標準の見た目）と遊ぶ人向けの設定画面（ゲームの絵柄）を作るために求めている。後の作業で、同じ仕組みの上にチェックボックス・スライダー・選択肢の列・タブ・スクロールする領域を足す（今回は作らない）ので、それらが無理なく乗る土台にする。

今のエンジンには、押した瞬間に反応する矩形（`Engine.addButton`、`oz/ENGINE_API.md` 18章）しかなく、エンジンは UI を描かない。開発資料4章の「エンジンに入れないもの」に「タブやスクロールなどのUI部品」があり、`Buttons` の責務外にも「ボタンの描画、タブやスクロールなどのUI部品」がある。今回、発注者の承認のもとでUI部品をエンジンに入れる（「エンジンに入れないもの」から外す）。`Buttons` と `Engine.addButton` の仕様は変えない。

*   **要件1: 置き場所と公開の形（決定事項）**
    *  UI 部品は、新しいモジュールとして `oz/src/` に置く（ファイルの分け方は、窓、部品の種類、標準の見た目、ポインタの扱いなどの責務ごとに計画で決める。1つのファイルに詰め込まない）。既存の `Buttons`・`Input`・`Scenes` には UI 部品の処理を足さない。
    *  利用側には、`oz/index.js` から新しく `Ui` という1つの名前で公開する（`import { Ui } from 'oz';`）。窓を作る操作と部品を足す操作の形（関数の名前・引数）は計画で決め、`oz/ENGINE_API.md` に書く。
    *  新しいモジュールは、ほかのエンジンモジュールを import しない（開発資料3章の依存の向き。`Engine` を呼んでシーンを外すことなどもしない）。暗幕を描くのに論理解像度が要る場合の受け取り方（呼ぶ側が渡す、または `Engine` が起動時に渡す。後者は今の `CanvasCache` への画素の倍率の受け渡しが例になる）は計画で決める。呼ぶ側が窓を作るたびに画面の大きさを渡さなくて済む形が望ましい。

*   **要件2: 窓をシーンの中に置く形（決定事項）**
    *  窓は、シーンが持つ。シーン（多くは `Engine.pushScene` で積むシーン）が、窓を作り（`init` の中など）、`onPointer` で受けたポインタを窓に渡し、`draw` の中で選んだレイヤーに窓を描かせる。窓は、`Engine.addButton` やエンジンの入力の仕組みには登録しない（ポインタはシーンから渡されたものだけで動く）。
    *  そのため、窓を開いている間に背面のシーンへ入力が届かないことは、窓を置いたシーンを積むことで成り立つ（最前面のシーンにだけ入力が届く。16章）。窓を置いたシーンが `Engine.addButton` で窓と重なる位置にボタンを登録すると、そのボタンが押下を独占して窓に届かない（18章）。このことを `oz/ENGINE_API.md` に注意として書く。
    *  バーチャルパッド（24章）が処理した指は `onPointer` に届かないので、部品にも届かない。今の作りのままで成り立つことを確かめ、`oz/ENGINE_API.md` に書く。
    *  シーンへ渡す手間（`onPointer` と `draw` からそれぞれ1行で呼べること）を、`oz/ENGINE_API.md` の使い方の例で示す。窓を置くだけのシーンを毎回書かずに済む仕組み（窓を置いた `Scene` の派生クラスをエンジンが用意するなど）を足すかは、計画で判断してよい（足す場合も、ゲーム自身のシーンの中に窓を置ける形は残す）。

*   **要件3: 窓**
    *  窓には、タイトルバー（タイトルの文字）、閉じるボタン（タイトルバーの右端）、背面の暗幕（論理解像度の全体を覆う半透明の暗い色）がある。窓の大きさは呼ぶ側が論理座標で渡す。位置は渡せ、省略すると画面の中央に置く。
    *  窓の中の部品の位置は、窓の内側（タイトルバーの下）の左上を原点とする論理座標で渡す。窓の外へはみ出した部品の扱い（描かない・切り取るなど）は計画で決め、`oz/ENGINE_API.md` に書く。
    *  閉じるボタンを押すと（要件5の、離したときに反応する形）、窓は呼ぶ側から受け取った「閉じるときの関数」を呼ぶ。窓を置いたシーンを外す（`Engine.popScene()`）のは、その関数の中で呼ぶ側が行う。
    *  **窓の外を押したら閉じるかを、呼ぶ側が選べる。何も指定しないときは閉じる（発注者の決定）。** 閉じる設定のときは、窓の外（暗幕の上）で押して、窓の外で離したときに閉じる（窓の中で押してから外で離したとき、外で押してから中で離したときは閉じない）。閉じない設定のときは、窓の外を押しても何も起きない。どちらの設定でも、窓の外を押した入力は、窓の中の部品にも背面のシーンにも届かない。
    *  窓の中の、部品の無いところを押しても何も起きない。

*   **要件4: ボタンと、数値・文字の表示**
    *  **ボタン:** 文字（決まった文字、または描くたびに呼ぶ関数で今の状態を表す文字）を持ち、押されたときの関数を呼ぶ。押せるかどうかを、呼ぶ側が関数で渡せる（描くたび・押すたびに呼び、偽なら押せない。押せないときは、押せないと分かる見た目になり、押しても何も起きない）。省略すると常に押せる。
    *  **数値・文字の表示:** 押せないラベル（項目名）と、いまの値を並べて表示する。値は、呼ぶ側から受け取った「値を読む関数」を描くたびに呼んで表示する（`null` などの扱いと、数値の表示の整え方を呼ぶ側が決められるようにするか（例: 整える関数を渡せる）は計画で決める）。押しても何も起きない。
    *  文字が部品の幅に収まらないときの扱い（縮める、切る、はみ出すまま、など）は計画で決め、`oz/ENGINE_API.md` に書く。

*   **要件5: ポインタの受け方（決定事項）**
    *  部品は、シーンから渡されたポインタ（16章の `'down'`・`'move'`・`'up'`）で動く。
    *  **ボタン（閉じるボタンを含む）は、離したときに反応する（発注者の決定）。** ボタンの上で押すと押されている見た目になり、押したままボタンの上で離すと、押されたときの関数が呼ばれる。押したままボタンの外へずらすと押されている見た目が消え、そのまま離すと何も起きない（取り消し）。外へずらしてからボタンの上へ戻して離すと反応する。
    *  押し始めた部品が、離すまでの `'move'`・`'up'` を受け取る（ほかの部品は、その間の入力に反応しない）。後の作業で、スライダーをドラッグして動かす・スクロールする領域をドラッグしてずらす・ずらそうとしたときに中のボタンが押されないようにする、を同じ仕組みの上に足すので、押し始めの部品が離すまでの入力を持つ形と、取り消しの仕組みを、それらが乗る形にしておく（今回は作らない）。
    *  `'down'` の無い `'move'`・`'up'`（16章の最後の項目。シーンが変わった直後などに届く）では、どの部品も反応しない。
    *  押されている見た目などの状態の変更は、ポインタを受けたときに行い、描画（`draw`）の中では状態を変えない（憲法3章「ロジックと描画の分離」）。

*   **要件6: 値のつなぎ方（決定事項）**
    *  値を持つ部品は、呼ぶ側から「値を読む関数」と「値を書く関数」を受け取る。部品は値を直接は書き換えず、操作で値を変えたら書く関数を呼ぶ（その場で反映される）。描くたびに読む関数を呼んで表示を合わせるので、値が外から変わっても表示が追従する。保存（22章 `Storage`）は、ゲームが書く関数の中で行う（部品は `Storage` を使わない）。
    *  今回の部品で値を使うのは、数値・文字の表示（読む関数だけ）である。書く関数を使う部品（チェックボックス・スライダー・選択肢の列）は後の作業で足すので、読む関数と書く関数の受け取り方・呼び方を、それらにも同じ形で使える共通の仕組みとして決めておく（今回は作らない）。
    *  ボタンの文字や押せるかどうかを関数で受け取ることも、同じ「描くたびに読む」考え方にそろえる。

*   **要件7: 見た目の差し替え（決定事項）**
    *  エンジンは、窓とすべての部品を、素っ気ない標準の見た目（単色の塗り・枠・文字。画像を使わない）で描く。文字は Canvas の既定のフォントの指定（`sans-serif` など）で描き、フォントは読み込まない。
    *  呼ぶ側は、部品の種類ごと（窓、ボタン、数値・文字の表示。閉じるボタンやタイトルバーを窓と分けるかは計画で決める）に描く関数を渡せる。渡した種類はその関数で描かれ、渡さなかった種類は標準の見た目で描かれる。描く関数を渡す単位（窓ごとにまとめて渡す、部品ごとに渡す、など）は計画で決める。描く関数には、描くのに必要な情報（矩形、文字、値、押されているか、押せるか、など）が渡される。描く関数は、受け取った ctx の状態を変えても外へ漏れないように、エンジンが `save` / `restore` で囲んで呼ぶ。
    *  見た目を差し替えても、押したと判定される範囲（部品の矩形）は変わらない。
    *  標準の見た目を描く関数を、差し替える側から呼べるようにする（標準の見た目に少し足すだけの差し替えを書けるように）かは、計画で判断してよい。

*   **要件8: 既定の大きさ**
    *  タイトルバーの高さ、閉じるボタンの大きさ、文字の大きさ、部品の高さ（省略できるものにするかは計画で決める）などの既定の値は、論理解像度の短い辺が 720 のゲーム（バトリティアは縦長の 720×1280、土台は横長の 1280×720）を縦長のスマートフォンで表示したときに、指で押しやすい大きさ（目安として、押せる部品の高さが画面の上で約 44 CSS 画素以上）になるように決める。決めた値と、その考え方（論理解像度の短い辺が違うゲームでは呼ぶ側が大きさを渡すこと）を `oz/ENGINE_API.md` に書く。
    *  既定の値は論理座標の数値としてエンジンに置き、論理解像度や画素の倍率から自動では変えない。

*   **要件9: 引数が正しくないとき**
    *  窓を作る操作と部品を足す操作は、引数が正しくないとき（必要な項目が無い、大きさが正の有限数でない、関数のはずのものが関数でない、描く関数の種類の名前が知らないもの、など）に、ほかの API と同じ形のエラー（先頭に `[oz]` と API 名、項目名を含む）になる。知らない項目を渡したときの扱いは、`Engine.addVirtualPad`（知らない項目をエラーにする）と `CanvasCache.create`（無視する）で扱いが違う（開発資料・`_doc/COWORK_STATUS.md` の懸念）ので、どちらに合わせるかを計画で決め、理由を RES に書く。
    *  エラーの種類（`Error`・`TypeError`・`RangeError`）は既存の API の扱いに合わせ、`oz/ENGINE_API.md` に書く。

*   **要件10: 資料**
    *  `oz/ENGINE_API.md` に、UI 部品の章を新しく足す（今の最後の 25章の後の 26章。ほかの章の番号は変えない）。窓の作り方とシーンへの置き方、ボタンと数値・文字の表示の使い方、ポインタの受け方（離したときに反応する、取り消し、押し始めた部品が離すまで受け取る）、値のつなぎ方、見た目の差し替え方（描く関数に渡される情報）、既定の大きさ、注意（`Engine.addButton` との重なり、バーチャルパッド）、エラー、使い方の例（標準の見た目の窓と、見た目を差し替えた窓）を書く。1章の「使えるもの」の一覧と import の例に `Ui` を足す。18章（ボタン）に、描く・押せなくするなどは 26章の部品のボタンで行えることの参照を足す。
    *  `PROJECT_ARCHITECTURE.md` の1章（フォルダ構造に変化があれば）、3章（依存の向き、`Engine` からの受け渡しがあればその説明）、4章（新しいモジュールの責務の行、`index.js` の再export、「エンジンに入れないもの」から「タブやスクロールなどのUI部品」を外すこと、自動テストの対象）への影響を、『開発資料の更新予定』に挙げる。
    *  新規プロジェクトの手順書（`_doc/newgame/` の `NEW_GAME_GUIDE.md`・`GAME_RULES.md`・`settings.example.json`）を読み、今回の変更（`oz/` に `Ui` が加わったこと、土台のメニューの項目と見本の窓が増えたこと。特に `NEW_GAME_GUIDE.md` 6章の土台の見本を消す手順と、7-4 の土台のメニューの項目の列挙）で直す必要がある箇所を確かめ、直す必要があれば直す。直す必要が無ければ変えず、確かめた結果（どの節を見て、なぜ直さなくてよいか）を RES に書く。

*   **要件11: 自動テスト**
    *  Canvas を使わない部分（引数の検証、部品の当たり判定、窓の中の座標の扱い、押す・ずらす・離す・取り消しの流れと押されたときの関数の呼び出し、押せないボタン、窓の外で閉じる・閉じない、`'down'` の無い入力の扱い、読む関数の呼び出し）を、`test/` の自動テストの対象にする。テストの置き場所と名前は開発資料4章「自動テスト（`test/`）の規則」に従う（`test/<対象モジュール名>[.<観点>].test.js`）。描画と、標準の見た目の中身はテストしない。
    *  テストにするために、Canvas を使う部分と使わない部分の分け方を計画で決める（テストのためだけの公開の口を足さない。公開されたものだけで確かめられる形にする）。新しいモジュールは `window` を使わない。

*   **要件12: ゲームの土台で確かめられるようにする（決定事項）**
    *  プレイ中のメニュー（今の「閉じる」「スロー」「ミュート」「FPS」「タイトルに戻る」の並び）の「タイトルに戻る」の上に、「UI の見本」の項目を足す。選ぶと、メニューを閉じて見本の窓を開く。見本の窓を閉じると、プレイの画面に戻る（プレイは窓を開いている間止まり、閉じると続きから動く）。
    *  見本の窓は2種類あり、中の部品の並びと位置は同じで、見た目と「外を押したら閉じるか」だけが違う。
        *  **標準の見た目の窓:** エンジンの標準の見た目で描く。外を押すと閉じる（既定のまま）。タイトルは「UI の見本（標準）」など、どちらの窓か分かるものにする。
        *  **見た目を差し替えた窓:** 窓・ボタン・数値・文字の表示・閉じるボタンなど、今回の部品の種類すべてを、土台が渡す描く関数で描く。標準の見た目と一目で区別がつく見た目（色、角の丸み、文字の大きさなど）にし、部品の矩形の内側に描く。外を押しても閉じない設定にする。
    *  中の部品（どちらの窓も同じ）:
        *  数値・文字の表示「FPS」: `Engine.fps` を読む（`null` の間は `--`）。約1秒ごとに値が変わり、表示が追従する。
        *  数値・文字の表示「スロー」: 今のスローの状態（ON・OFF）を読む。
        *  ボタン「スローを切り替える」: 押すとスローが切り替わり、上の「スロー」の表示が追従する。
        *  ボタン「等速に戻す」: スローのときだけ押せる（押せるかどうかを関数で渡す）。押すと等速に戻る。等速のときは押せない見た目になり、押しても何も起きない。
        *  ボタン「見た目を切り替える」: 押すと、今の窓を閉じて、もう一方の見本の窓を開く（標準 ⇔ 差し替え）。
    *  部品の位置と大きさは、土台の画面（1280×720）に収まり、指で押しやすいように計画で決める（エンジンの既定の大きさを使ってよい）。メニューの項目が6つになっても画面に収まり、重ならないことを確かめる（今の項目の高さと間隔のままで収まる見込み。収まらない場合は計画の前に疑問点として報告する）。
    *  見本の窓と、その中身を作る処理は、シーンのファイル（`PlayScene` など）に詰め込まず、責務ごとに分けて `js/scenes/` に置く（今の `slow.js`・`fps.js` のように）。スローの状態は、今の `js/scenes/slow.js` の関数を使う。見本の窓は 05-05 で本番の開発用パネルと設定画面に作り替える予定だが、今回は見本として完成させ、テストプレイの後も残す。
    *  `js/` を実装するタスクでは、`oz/src/` を読まず `oz/ENGINE_API.md` だけを参照する（憲法3章）。26章で分からないこと、例のとおりに書いて動かないことがあれば、RES に不足として記録し、26章を直す。そのため、土台を変えるタスクは、`oz/ENGINE_API.md` に 26章を書くタスクより後に置く。

*   **要件13: テストプレイで確かめること**
    *  次を、発注者が PC（マウス）とスマートフォン（指。GitHub Pages で公開したページ）で確かめられるように、RES の目視確認推奨箇所に、操作と期待する結果の形で書く。
        *  プレイ中のメニューの「UI の見本」で、標準の見た目の窓が開く。タイトルバー・閉じるボタン・暗幕があり、背面のプレイが止まって暗く見える。
        *  ボタンを押すと押されている見た目になり、離すと反応する。押したまま外へずらすと押されている見た目が消え、離しても反応しない。戻して離すと反応する。
        *  「スローを切り替える」で「スロー」の表示が追従する。「FPS」の表示が約1秒ごとに変わる。「等速に戻す」は、等速のときは押せない見た目で押しても何も起きず、スローのときは押せて、押すと等速に戻る。
        *  標準の見た目の窓は、閉じるボタンでも、窓の外を押して離しても閉じ、プレイが続きから動く。窓の外を押した入力で、背面のプレイの画面の「メニュー」のボタンなどが反応しない。窓の中で押して外で離したとき、外で押して中で離したときは閉じない。
        *  「見た目を切り替える」で、見た目を差し替えた窓に替わる。部品の並びと押して反応する範囲は標準の見た目の窓と同じで、見た目だけが違う。窓の外を押しても閉じず、閉じるボタンでだけ閉じる。
        *  スマートフォンで、すべてのボタンと閉じるボタンが指で押しやすい大きさである。バーチャルパッドのスティックやボタンの位置（窓の暗幕の下になる）を押しても、窓の部品が反応したり、窓が閉じたりしない（パッドの指は窓に届かない。窓を開いている間にパッドのキーがどう扱われるかを含めて、実際の動きを RES の懸念事項に書く）。
        *  PC でウィンドウの大きさを変えたとき、スマートフォンで画面の向きを変えたときも、窓の表示と押して反応する位置がずれない。
        *  タイトルに戻る・プレイを始める・窓を開いて閉じる、を何度か繰り返してもエラーにならない。
    *  テストプレイの結果、部品の作り（反応の仕方、大きさ、見た目の差し替えの仕組み）に問題が出た場合は、実装セッションは推測で直さず、状況を完了報告（未完了）で現場設計セッションに返す（エンジンの直し方は設計で判断する）。土台の見本の窓の配置や文言の細かい直しは、実装セッションで直してよい。

*   **要件14: 公開先**
    *  テストプレイは、本リポジトリを GitHub Pages で公開したページ（`/ozengine-web/` の下）で行う。コードの中のパスは `/` から始めない（相対パスにする）。

## 【計画書に必ず含めるべきタスクごとの作業】
AIが作成する計画書（RES）のタスクリストには、個別の実装タスクの後に、以下の作業を必ず含めること。
*   コード修正完了後、JSDocコメントの記載漏れがないことを確認する（新しいファイルの先頭行の責務定義を含む）。
*   `.js` を変更・作成したタスクでは、憲法1章の検証コマンド（構文チェックと、リポジトリのルートでの `node --test` の `fail 0`）を実行する。
*   `oz/` の中のファイルを変更・作成したタスクでは、指紋一覧を作り直す。
*   タスク完了後、作業レポート（本RESファイル）の詳細作業内容を記載し完成させる。
*   開発資料（`PROJECT_ARCHITECTURE.md`）の記載に影響が出る場合は、資料本体は修正せず、その旨を『開発資料の更新予定』欄に追記する。

## 【計画書に必ず含めるべき固定タスク】
AIが作成する計画書（RES）のタスクリストには、全実装タスクの後に、以下のタスクを必ず含めること。
*   各タスクで記録した『開発資料の更新予定』を確認し、開発資料（`PROJECT_ARCHITECTURE.md`）へ反映する。開発資料に影響を与えない場合は、このタスクは不要とする。
    *   ※ 実装AIによる開発資料の書き換えは、本ワークフローにおいて原則禁止であるが、**この最終タスクのみ明示的な例外とする**。後続タスクが存在せず、資料の変更によって他タスクの前提が動く危険がないためである。個別の実装タスク内で資料を書き換えてはならない。

## 【計画立案時の絶対遵守ルール (Constraints)】
*   **アーキテクチャの維持** : 憲法3章の絶対禁止事項に反する設計をしてはならない。特に、エンジンから `js/` を import しない、エンジンにゲーム固有の値（土台の見本の文言・色・レイアウト、レイヤー名など）を書かない、公開APIは `oz/index.js` からだけ出す、公開APIを足すタスクの中で `oz/ENGINE_API.md` にも使い方を書く、エンジンは渡された canvas の操作と入力・リサイズのイベント登録以外のDOM操作をしない（新しいモジュールは `addEventListener` を使わない。ポインタはシーンから渡されたものだけで動く）、`performance.now()` などで時間を取らない、描画処理の中で状態を変えない、`ctx` の状態を外へ漏らさない（呼ぶ側の描く関数も `save` / `restore` で囲む）、`window` にプロパティを足さない。`js/` に `addEventListener`・`requestAnimationFrame`・`getContext` を書かない、`js/` から `oz/src/` を import しない。
*   **責務の分離** : 新しいモジュールは、責務（窓、部品の種類、標準の見た目、ポインタの扱いなど）ごとにファイルを分け、それぞれのファイル先頭に責務定義を書く。標準の見た目を描く処理と、当たり判定・押下の状態などの Canvas を使わない処理を分ける。`Engine` に UI 部品の処理を持ち込まない（`Engine` に足すのは、要件1で必要と判断した場合の論理解像度の受け渡しだけ）。`Buttons`・`Input`・`Scenes`・`GameLoop` は変えない（変える必要があると分かった場合は、計画に書く前に疑問点として報告する）。新しいモジュールと責務の範囲が変わるファイルは、開発資料4章の責務表の更新予定に挙げる。
*   **後の作業への備え** : 要件5・6で、後の作業（チェックボックス・スライダー・選択肢の列・タブ・スクロールする領域）が乗る形にすることを求めているが、それらの部品そのものや、使われない予備の口（例: 今回の部品が使わないドラッグの距離の判定、書く関数を呼ぶ処理の実体）を先回りで作らない（憲法3章「先回り実装の禁止」）。後の作業がどう乗る見込みかは、RES のアーキテクチャ設計に書くだけにする。
*   **サンプルコードの目印** : 要件12で `js/` に足すコードは、土台の見本なので `ozengine sample` の目印を付ける（新しいファイルなら責務定義の直後に `/* ozengine sample */`）。目印の付いた部分をすべて消してもエラーなく起動できる状態を保ち、目印の無いコードが目印の付いたコードを import しない（憲法3章「サンプルコードの目印」）。
*   **変更してよいファイル** : `oz/src/` の新規ファイル（UI 部品）、`oz/src/Engine.js`（要件1で論理解像度を渡す場合のみ）、`oz/index.js`（`Ui` の再export のみ）、`oz/ENGINE_API.md`、`oz/FINGERPRINTS.txt`（作り直しのみ）、`js/scenes/` のファイル（変更と、要件12のための新規作成）、`test/` の新規ファイル（UI 部品のテスト）、`_doc/newgame/NEW_GAME_GUIDE.md`・`_doc/newgame/GAME_RULES.md`・`_doc/newgame/settings.example.json`（要件10で直す必要がある場合のみ）、`PROJECT_ARCHITECTURE.md`（最終の固定タスクのみ）、作業計画書（本RES）に限る。上に挙げていない `oz/src/` の既存ファイル・`oz/VERSION`・`assets/`・`index.html`・`js/main.js`・`js/scenes/` 以外の `js/`・既存の `test/` のファイル・`PROJECT_CONSTITUTION.md`・`CLAUDE.md`・`README.md`・`_doc/newgame/` 以外の `_doc/`・phaseout のファイルは変更しない。これら以外の変更が要ると分かった場合は、計画に書く前に疑問点として報告する。
*   **外部依存の禁止** : 外部ライブラリ・npm パッケージ・`package.json`・ビルドを使わない。
*   **スコープの分割** : エンジンの新しいモジュール（Canvas を使わない部分、標準の見た目、公開の口）、自動テスト、`oz/ENGINE_API.md` の 26章、土台の見本の窓、手順書の確認は、混同しない粒度のタスクに分ける。1タスクで変える `oz/src/` のファイルは、できるだけ1つか2つにする。
*   **確認の範囲** : 実装AIはブラウザや実機での動作確認を行わない（発注者のテストプレイで行う）。要件13の確認事項を、RES の懸念事項・目視確認推奨箇所に挙げる。
*   **今回やらないこと** : 次は作らない・変えない。チェックボックス、スライダー、選択肢の列、タブ、スクロールする領域（後の作業で足す）。文字を入力する欄、キーボード・ゲームパッドでの部品の操作（フォーカスの移動、`Escape` で閉じるなど）。マウスを乗せたときの見た目（ホバー）。部品の自動の並べ方（縦に積む、折り返すなどのレイアウトの計算）。窓の移動（タイトルバーをドラッグして動かす）、大きさの変更。窓や部品の開閉・切り替えの演出（フェード、スライドなど）。フォントの読み込み、画像を使う標準の見た目。`Engine.addButton`・`Buttons`・`Input` の仕様の変更。土台の既存のメニュー（`MenuScene`）を新しい部品で作り直すこと。本番の開発用パネルと設定画面（後の作業で、見本の窓を作り替える）。`oz/VERSION` の更新。
