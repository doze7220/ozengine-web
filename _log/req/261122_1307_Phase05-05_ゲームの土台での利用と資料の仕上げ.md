## 【実装要件】
これまでの作業（Phase 05-01〜05-04）で、エンジンに FPS の表示の出し入れ（`oz/ENGINE_API.md` 14章）と UI 部品（`Ui`。26章。窓、ボタン、数値・文字の表示、チェックボックス、スライダー、選択肢の列、タブ、スクロールする領域）が入った。土台のプレイ中のメニューには、確かめ用の「FPS」の項目と「UI の見本」の項目（3組の見本の窓）がある。今回、確かめ用の見本を、ゲームで実際に使う形の2つの窓、**開発用パネル**（標準の見た目）と**設定画面**（見た目を差し替えた窓）に置き換える。あわせて、新しいゲームが UI 部品を使い始められるように、資料を仕上げる。ゲーム（バトリティア）が、開発用の調整パネルと、遊ぶ人向けの設定画面を作るために求めている。

今回はエンジン（`oz/src/`）の動きを変えない。土台の窓を作っていて、エンジンを変えないと要件を満たせないと分かった場合は、計画に書く前に疑問点として報告する。

*   **要件1: プレイ中のメニュー（決定事項）**
    *  プレイ中のメニュー（`js/scenes/playMenu.js`）の項目を、上から「閉じる」「開発用パネル」「設定」「タイトルに戻る」の4つにする（発注者の決定）。
    *  今の「スロー」「ミュート」「FPS」「UI の見本」の項目はなくす。スローと FPS の表示は開発用パネルで、ミュートは設定画面で変える。
    *  メニューの項目を選ぶキーは「閉じる」の P キーだけ残す（今の S・M・F キーの割り当ては、項目と一緒になくなる）。プレイ画面の S キー（スロー）・F キー（FPS の表示の切り替え）・P キー（メニューを開く）は、今までどおり効く（`PlayScene.js` は変えない）。
    *  「開発用パネル」「設定」を選ぶと、メニューを閉じて、それぞれの窓を開く。窓を閉じると、プレイ画面に戻る（メニューには戻らない）。
    *  「開発用パネル」は、いつでもメニューに出す（起動の設定 `?debug` に関係なく。発注者の決定）。
    *  6項目のときに、いちばん上の項目が背面の「メニュー」ボタンと暗幕の下で少し重なって見えていた件は、4項目にすることで重ならなくなる（計画で、項目の位置と「メニュー」ボタンの矩形が重ならないことを確かめる）。
    *  タイトル画面は変えない（設定画面はプレイ中のメニューからだけ開く。発注者の決定）。

*   **要件2: 開発用パネル（決定事項）**
    *  標準の見た目（`look` を渡さない）の窓で、タイトルは「開発用パネル」。窓の外を押して外で離すと閉じる（`closeOnOutside` の既定）。閉じるボタンでも閉じる。
    *  タブを3つ置く: 「FPS」「時間」「情報」。
        *  タブ「FPS」:
            *  チェックボックス「FPS を表示する」: `Engine.fpsVisible` を読み書きする（入れると画面の隅に FPS の表示が出て、切ると消える。その場で反映する）。
            *  選択肢の列（横）「表示の位置」: 左上・右上・右下・左下。`Engine.fpsPosition` を読み書きする（FPS の表示を消している間も、位置は選べる）。
            *  数値・文字の表示「FPS」: `Engine.fps` を表示する（`null` の間は `--`）。窓を開いている間も値が更新される。
        *  タブ「時間」:
            *  チェックボックス「スロー」: `js/scenes/slow.js` のスローを読み書きする。
            *  数値・文字の表示「timeScale」: 今の `Engine.timeScale` を表示する。
            *  ボタン「等速に戻す」: スローを切る（`resetSlow`）。
        *  タブ「情報」: スクロールする領域を1つ置き、その中に、数値・文字の表示を上から並べる。少なくとも「FPS」「FPS の表示」（OFF か位置）「スロー」「timeScale」「ミュート」「BGM の音量」「効果音の音量」「画面の大きさ」（論理解像度。例: `1280 × 720`）を出す。中身の高さが領域の高さを超え、スクロールしないと見えない表示があるようにする（足りなければ、ほかの読み取りだけの情報を足してよい。ゲームの状態を変える処理は足さない）。
    *  PC でプレイ画面の F キー・S キーで FPS の表示やスローを変えたとき、開発用パネルを開くと、その状態が表示に合っている（部品は描くたびに `read` で読むので、外から変わった値に追従する）。
    *  窓の位置と大きさは、背面のプレイ画面のバーチャルパッドの円（x ≤ 330、x ≥ 990）と重ならないようにする（これまでの見本の窓は x 340〜940 に置いていた）。土台の画面（1280×720）に収め、エンジンの既定の大きさを使う。収まらない場合は、計画の前に疑問点として報告する。

        *  スライダー「BGM の音量」: `Sound.bgmVolume` を読み書きする。最小 0・最大 1・刻み 0.1、値の文字は百分率（`0%`〜`100%`）。動かすとその場で BGM の音量が変わる。

        *  ボタン「初期値に戻す」: BGM の音量・効果音の音量を 1（100%）に、ミュートを切った状態にする。
    *  **保存:** BGM の音量・効果音の音量・ミュートは、変えるたびに `Storage` に保存する（22章）。次に起動したとき、ロード画面でセーブを開いた時点で保存した値を `Sound` に反映し、タイトル画面の BGM から保存した音量で鳴る。

        *  音量とミュートの保存と反映を、どのファイルに置くか（今の `mute.js` を広げて、音の設定の保存の責務にするか、など）は計画で決める。

    *  **見た目の差し替え:** 設定画面の部品の種類（窓・暗幕・タイトルバー・閉じるボタン・スライダー・チェックボックス・ボタン）を、土台が渡す描く関数で描く。今の `js/scenes/uiSampleLook.js` の描き方（淡い茶色・橙など）を使い、標準の見た目と一目で区別がつき、部品の矩形の内側に描く。設定画面が使わない種類の描く関数を残すかは計画で決める（26章の `look` は、渡さなかった種類は標準の見た目で描く）。
    *  窓の位置と大きさは、要件2と同じく、パッドの円と重ならず、画面に収まるようにする。

        *  設定画面: 見た目が差し替わっている。BGM の音量を変えるとその場で音量が変わる。効果音の音量を変えて窓を閉じ、ブーストを鳴らすと音量が変わっている。ミュートを入れると音が消え、右上に「ミュート中」が出る。「初期値に戻す」で 100%・100%・ミュートなしに戻る。窓の外を押しても閉じず、閉じるボタンで閉じる。
        *  保存: 設定画面で音量とミュートを変えてから、ページを読み込み直す → 設定画面の表示と実際の音量・ミュートが、変えたときのままになっている。
        *  右上の FPS の表示（開発用パネルで位置を右上にする）と、「ミュート中」「スロー」の表示が重ならない。
        *  2つの窓を開いた状態で、パッドの位置を押しても、部品は反応せず、開発用パネルも閉じない。
        *  スマートフォンで、2つの窓の部品が指で操作できる（タブ、チェックボックス、選択肢、スライダー、スクロール、ボタン）。
        *  PC でウィンドウの大きさを変えたとき、スマートフォンで画面の向きを変えたときも、部品の表示と押して反応する位置がずれない。
        *  2つの窓を開いて閉じる、を何度か繰り返しても、開発者ツールのコンソールにエラーが出ない。
    *  テストプレイの結果、エンジンの部品の作りに問題が出た場合は、実装セッションは推測で直さず、状況を完了報告（未完了）で現場設計セッションに返す（エンジンの直し方は設計で判断する）。土台の窓の配置や文言の細かい直しは、実装セッションで直してよい。

*   **要件13: 公開先**
    *  テストプレイは、本リポジトリを GitHub Pages で公開したページ（`/ozengine-web/` の下）で行う。コードの中のパスは `/` から始めない（相対パスにする）。

## 【計画書に必ず含めるべきタスクごとの作業】
AIが作成する計画書（RES）のタスクリストには、個別の実装タスクの後に、以下の作業を必ず含めること。
*   コード修正完了後、JSDocコメントの記載漏れがないことを確認する（新しいファイルの先頭行の責務定義を含む）。
*   `.js` を変更・作成・削除したタスクでは、憲法1章の検証コマンド（構文チェックと、リポジトリのルートでの `node --test` の `fail 0`）を実行する。
*   `oz/` の中のファイルを変更・作成したタスクでは、指紋一覧を作り直す。
*   タスク完了後、作業レポート（本RESファイル）の詳細作業内容を記載し完成させる。
*   開発資料（`PROJECT_ARCHITECTURE.md`）の記載に影響が出る場合は、資料本体は修正せず、その旨を『開発資料の更新予定』欄に追記する。

## 【計画書に必ず含めるべき固定タスク】
AIが作成する計画書（RES）のタスクリストには、全実装タスクの後に、以下のタスクを必ず含めること。
*   各タスクで記録した『開発資料の更新予定』を確認し、開発資料（`PROJECT_ARCHITECTURE.md`）へ反映する。開発資料に影響を与えない場合は、このタスクは不要とする。
    *   ※ 実装AIによる開発資料の書き換えは、本ワークフローにおいて原則禁止であるが、**この最終タスクのみ明示的な例外とする**。後続タスクが存在せず、資料の変更によって他タスクの前提が動く危険がないためである。個別の実装タスク内で資料を書き換えてはならない。

## 【計画立案時の絶対遵守ルール (Constraints)】
*   **アーキテクチャの維持** : 憲法3章の絶対禁止事項に反する設計をしてはならない。特に、エンジンから `js/` を import しない、エンジンにゲーム固有の値（土台の窓の文言・色・レイアウトなど）を書かない、公開APIは `oz/index.js` からだけ出す、描画処理の中で状態を変えない（部品の `read`・`format`・`label` と描く関数の中で、値を書き換えない・保存しない）、`ctx` の状態を外へ漏らさない（土台の描く関数も `save` / `restore` で囲む）、`window` にプロパティを足さない。`js/` に `addEventListener`・`requestAnimationFrame`・`getContext` を書かない、`js/` から `oz/src/` を import しない。
*   **責務の分離** : 開発用パネル・設定画面・見た目の描き方・窓を置くシーン・音の設定の保存は、責務ごとにファイルを分け、それぞれのファイル先頭に責務定義を書く。メニューの項目の定義（`playMenu.js`）に、窓の中身を書かない。窓の部品の `write` の中で行う保存は、音の設定の保存の責務のファイルの関数を呼ぶ形にし、窓の中身のファイルで `Storage` を直接扱わない。責務の範囲が変わるファイル・消えるファイル・増えるファイルは、開発資料4章の責務表の更新予定に挙げる。
*   **先回り実装の禁止** : 土台の2つの窓が使わない予備の口や設定（例: 使わない種類の描く関数を新たに作ること、窓の中で効果音を試しに鳴らす処理、要件2・3に無い調整の項目）を作らない（憲法3章「先回り実装の禁止」）。
*   **サンプルコードの目印** : 開発用パネル・設定画面・その見た目・音の設定の保存・メニューの項目は、土台の見本なので `ozengine sample` の目印を付ける（新しいファイルなら責務定義の直後に `/* ozengine sample */`）。要件5の窓を置くシーンは目印を付けない。目印の付いた部分をすべて消してもエラーなく起動できる状態を保ち、目印の無いコードが目印の付いたコードを import しない（憲法3章「サンプルコードの目印」）。
*   **変更してよいファイル** : `js/scenes/` のファイル（変更・新規作成・削除）、`oz/ENGINE_API.md`（要件8・10の記述の直しのみ。エンジンの仕様は変えない）、`oz/FINGERPRINTS.txt`（作り直しのみ）、`test/` の UI 部品のテスト（要件7の新規ファイルか追記）、`_doc/newgame/NEW_GAME_GUIDE.md`・`_doc/newgame/GAME_RULES.md`・`_doc/newgame/settings.example.json`（要件9で直す必要がある場合のみ）、`PROJECT_ARCHITECTURE.md`（最終の固定タスクのみ）、作業計画書（本RES）に限る。`oz/src/`・`oz/index.js`・`oz/VERSION`・`assets/`・`index.html`・`js/main.js`・`js/scenes/` 以外の `js/`（`js/ui/` を含む）・UI 部品以外の `test/` のファイル・`PROJECT_CONSTITUTION.md`・`CLAUDE.md`・`README.md`・`_doc/newgame/` 以外の `_doc/` は変更しない。これら以外の変更が要ると分かった場合は、計画に書く前に疑問点として報告する。
*   **外部依存の禁止** : 外部ライブラリ・npm パッケージ・`package.json`・ビルドを使わない。
*   **スコープの分割** : 26章の確かめと書き足し、自動テスト（要件7）、音の設定の保存、窓を置くシーン、開発用パネル、設定画面の中身、設定画面の見た目、メニューの項目、見本の窓の削除、状態表示の位置、手順書は、混同しない粒度のタスクに分ける。
*   **確認の範囲** : 実装AIはブラウザや実機での動作確認を行わない（発注者のテストプレイで行う）。要件12の確認事項を、RES の懸念事項・目視確認推奨箇所に挙げる。
*   **今回やらないこと** : 次は作らない・変えない。エンジン（`oz/src/`）の動きと公開API（スクロールする領域の中身の高さを指定する項目なども足さない）。`oz/VERSION` の更新。タイトル画面の変更（設定の入口を足すことを含む）。キーボード・ゲームパッドでの部品の操作。窓の中で効果音を試しに鳴らすこと。音量・ミュート以外の設定の保存（FPS の表示・スローは保存しない）。プレイ画面の S・F・P キーの変更。バーチャルパッドの配置の変更。演出（窓のフェードなど）。
