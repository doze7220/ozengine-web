## 【実装要件】
前の作業（Phase 05-02）で、エンジンに UI 部品の土台（`Ui`。`oz/ENGINE_API.md` 26章）が入った。窓（タイトルバー・閉じるボタン・暗幕）、ボタン、数値・文字の表示があり、描き方の差し替え（`look`）、描くたびに読む値のつなぎ方（`read`）、押し始めた部品が離すまでポインタを受け取る仕組みがある。今回、その上に、値を変える3種類の部品（チェックボックス、スライダー、選択肢の列）を足す。ゲーム（バトリティア）が、開発用の調整パネル（標準の見た目）と遊ぶ人向けの設定画面（ゲームの絵柄。音量のスライダーなど）を作るために求めている。

05-02 では、値を読む関数（`read`）だけを使い、値を書く関数は「後の作業で同じ形で足す」としていた。今回、書く関数を初めて使う。

*   **要件1: 部品の足し方（決定事項）**
    *  3種類の部品は、窓の操作のオブジェクト（26章「窓の4つの操作」）に、部品ごとの足す操作を加えて足す（`addButton`・`addValue` と同じ形。名前は計画で決める。例: `addCheckbox`・`addSlider`・`addChoices`）。位置と大きさの渡し方（窓の内側の左上が原点の論理座標、`x`・`y`・`width` は必須、`height` は省略できる）は、`addButton`・`addValue` にそろえる。
    *  部品の処理は、部品の種類ごとに `oz/src/` の新しいファイルに置く（今の `UiButton.js`・`UiValue.js` と同じ分け方）。`UiWindow.js` には、部品を足す操作と、ポインタの振り分け・描くための情報の組み立てに必要な最小限だけを足す。新しいファイルは、UI 部品のファイルどうし以外のエンジンモジュールを import しない（開発資料3章の依存の向き）。

*   **要件2: 値のつなぎ方（決定事項）**
    *  3種類とも、呼ぶ側から値を読む関数 `read` と、値を書く関数 `write` を受け取る（`read` は 05-02 の `addValue` と同じ名前・同じ呼ばれ方にする。`write` は値1つを引数に受け取る関数で、戻り値は使わない）。
    *  部品は値を自分で持たない。描くたびに `read` を呼んで表示を合わせるので、値が外から変わっても（ほかの部品や、ゲームの処理で変わっても）次の描画で表示が追従する。
    *  操作で値を変えたときは、その場で `write(新しい値)` を呼ぶ。`write` を呼ぶのはポインタを受けたとき（窓の `onPointer` の中）だけで、描画（`draw`）の中では呼ばない（憲法3章「ロジックと描画の分離」）。今の値（`read` の戻り値）と同じ値になる操作では `write` を呼ばない。
    *  保存（22章 `Storage`）は、ゲームが `write` の中で行う（部品は `Storage` を使わない）。`write` の中で投げられた例外は、包み直さずに伝わる（`onPress` と同じ）。
    *  ポインタを受けたときに今の値を知るために `read` を呼んでよい（その場合は 26章の「`addButton`・`addValue`・`onPointer` は `label`・`read`・`format` を呼ばない」という記述を、正しい形に直す）。

*   **要件3: チェックボックス**
    *  入りと切りの2つの状態を持つ。部品の矩形の中に、四角い箱（入りのときは印が付く）と、項目名（`label`。文字列か、描くたびに呼ぶ関数。`addButton` の `label` と同じ形）を並べて描く。押して反応する範囲は、箱だけでなく部品の矩形の全体とする。
    *  押し方はボタン（26章「ポインタの受け方」）と同じにする。押すと押されている見た目になり、押したまま部品の上で離すと、入りと切りが切り替わる（`write(!今の値)`。今の値は `read` の戻り値を真偽として扱ったもの）。押したまま外へずらして離すと何も起きない（取り消し）。外へずらしてから戻して離すと反応する。

*   **要件4: スライダー（発注者の決定を含む）**
    *  呼ぶ側は、最小 `min`・最大 `max`・刻み `step` を渡せる。`step` を省略したときの扱い（刻みなしで連続した値にするか、必須にするか）、`max - min` が `step` の整数倍でないときの扱い（エラーにするか、最後の刻みを `max` にするか、など）は計画で決め、`oz/ENGINE_API.md` に書く。
    *  部品の矩形の中に、項目名（`label`。チェックボックスと同じ形）と、今の値の文字と、溝（つまみが左右に動く帯）とつまみを描く。並べ方（例: 上の段の左に項目名・右に値の文字、下の段に溝）は計画で決めるが、溝は部品の幅のほぼ全体を使い、つまみの位置と値の対応を、見た目を差し替えても変わらない形でエンジンが決めて描く関数に渡す（描く関数は、渡された溝の位置とつまみの位置のとおりに描けばよい）。値の文字は、`addValue` の `format` と同じ形の整える関数を渡せる（省略したときは `String(値)`）。
    *  **溝のどこかを押すと、値がその位置へ飛び、そのままドラッグで追う（発注者の決定）。** 押して反応する範囲は部品の矩形の全体とし、押した位置の横の位置（`x`）から値を求める（縦の位置は使わない）。溝の端より外の位置は、`min`・`max` に寄せる。
    *  **指が少しずれても意図しない値にならないようにする（DIR の要件）。** 少なくとも次を満たす。
        *  値は刻みに合わせて止まる（`min + 刻み × 整数` の値だけを `write` に渡す）。刻みの計算で `0.1 + 0.2` のような小数の誤差が値に出ないようにする（例: 刻みの数から毎回 `min + k × step` で求める。方法は計画で決める）。
        *  押している間に指が部品の外（上下や左右）へずれても、ドラッグは取り消されず、離すまで横の位置で値を追う（ボタンの取り消しとは違う）。
        *  離したときの位置では値を変えない（最後の `'move'` までで決まった値のまま）。離す瞬間に指がずれて値が1刻み動くことを防ぐため。
        *  刻みの境目の近くで指が細かく揺れたときに値が行き来しないための遊び（ヒステリシス）を入れるかは、計画で判断してよい（入れる場合は、遊びの幅をエンジンの固定の論理座標の数値として決め、`oz/ENGINE_API.md` に書く）。
    *  `read` の戻り値が `min`〜`max` の外のとき、刻みに合っていないとき、数でないときに、つまみをどこに描き、値の文字に何を出すかは計画で決め、`oz/ENGINE_API.md` に書く（操作するまでは `write` を呼ばない）。
    *  溝の向きは横だけにする（縦のスライダーは作らない）。

*   **要件5: 選択肢の列（発注者の決定を含む）**
    *  呼ぶ側は、選択肢の一覧（選択肢ごとにラベルと値。ラベルは文字列か、描くたびに呼ぶ関数）を渡す。部品の矩形を選択肢の数で等分し、それぞれを押せるボタンのように描く。`read` の戻り値と値が同じ（`===`）選択肢が、選ばれていると分かる見た目になる。同じものが無ければ、どれも選ばれていない見た目になる。
    *  **並べる向きを、横（矩形の幅を等分して横に並べる）と縦（矩形の高さを等分して縦に並べる）から、呼ぶ側が選べる（発注者の決定）。** 省略したときは横。省略したときの `height` の既定（横なら部品の高さの既定、縦なら「部品の高さの既定 × 選択肢の数」など）と、選択肢どうしの間を空けるかは計画で決める。
    *  押し方はボタンと同じにする。押し始めた選択肢が押されている見た目になり、その選択肢の上で離すと、その選択肢の値を `write` する（すでに選ばれている選択肢なら `write` を呼ばない）。押したまま外へずらして離すと何も起きない（ほかの選択肢の上で離しても、それは選ばれない）。
    *  選択肢の一覧は、足した時点でコピーして持つ（後から元の配列を変えても影響しない）。選択肢が0個のときはエラーにする。値が重なる選択肢の扱い（エラーにするか）は計画で決める。

*   **要件6: 見た目の差し替え**
    *  26章の `look` に、3種類の部品の種類の名前を足す（名前は計画で決める）。渡した種類はその関数で、渡さなかった種類は標準の見た目で描く。描く関数は 05-02 と同じく `save` / `restore` で囲んで呼ぶ。描く関数に渡す情報（`info`）は、少なくとも次を含む。座標はすべて画面の論理座標にする。
        *  チェックボックス: 矩形、項目名の文字、入りか（真偽）、押されているか、文字の大きさ。
        *  スライダー: 矩形、項目名の文字、値の文字、今の値・`min`・`max`、溝の位置（矩形など）とつまみの位置、押されているか（ドラッグ中か）、文字の大きさ。
        *  選択肢の列: 矩形、向き、選択肢ごとの矩形・ラベルの文字・選ばれているか・押されているか、文字の大きさ。選択肢の列を1回の呼び出しで描くか、選択肢ごとに呼ぶかは計画で決める。
    *  見た目を差し替えても、押して反応する範囲と、位置と値の対応（スライダー）は変わらない。
    *  標準の見た目（単色の塗り・枠・文字。フォントは `sans-serif` などの既定の指定）は、05-02 の部品と同じ調子で、3種類を描き足す。押せる状態・選ばれている状態・入りの状態が、色だけに頼らずに分かる（印・枠の太さなど）ようにするかは計画で判断してよい。

*   **要件7: 既定の大きさ**
    *  3種類の部品の既定の高さ（スライダーのつまみの大きさなどを含む）は、05-02 と同じ前提（論理解像度の短い辺が 720 のゲームを、スマートフォンで短い辺を画面の短い辺に合わせて表示したとき、指で押しやすい約 44 CSS 画素以上。26章「既定の大きさ」）で決める。既定の値は `UiMetrics.js` の論理座標の数値として置き、論理解像度や画素の倍率から自動では変えない。決めた値を `oz/ENGINE_API.md` に書く。

*   **要件8: ポインタの受け方**
    *  3種類とも、05-02 の仕組み（押し始めた部品が離すまでポインタを受け取る。`'down'` の無い `'move'`・`'up'` には反応しない。押している間の別の `'down'` は無視する。窓の外の押下は部品に届かない）の上で動かす。部品が窓の内側で切り取られるとき（26章）は、切り取られた残りの部分だけが押せる。スライダーのドラッグ中は、窓の内側の外や窓の外へ指がずれても、離すまでそのスライダーが受け取る（要件4）。
    *  状態の変更（押されているか、ドラッグ中か）と `write` の呼び出しは、ポインタを受けたときに行い、描画の中では状態を変えない。

*   **要件9: 引数が正しくないとき**
    *  3種類の足す操作は、05-02 の `addButton`・`addValue` と同じ形のエラー（`Error`。先頭に `[oz] 窓の <操作名>:`、項目名を含む。知らない項目はエラー。上から順に調べ、最初に当たったものを投げる。エラーのときは部品は足されない）になる。
    *  スライダーの `min`・`max`・`step` の検証（有限の数値か、`min < max` か、`step` が正か、`step` が `max - min` より大きいときなど）、選択肢の一覧の検証（配列か、選択肢が0個、ラベルが無い、など）、選択肢の向きの値の検証を、計画で一覧にし、`oz/ENGINE_API.md` 26章のエラーの一覧に足す。

*   **要件10: 資料**
    *  `oz/ENGINE_API.md` 26章に、3種類の部品の使い方（足す操作の項目の表、ポインタの受け方、値のつなぎ方（`write` の呼ばれ方）、見た目の差し替えの `info` の表、既定の大きさ、エラー）を足す。章の見出し（今は「UI 部品（窓、ボタン、数値・文字の表示）」）を、部品が増えたことに合わせて直す。使い方の例に、3種類を使う例（`read` と `write` で値をつなぎ、`write` の中で保存する例を含む）を足す。1章の「使えるもの」の一覧の `Ui` の説明に影響があれば直す。ほかの章の番号は変えない。
    *  `PROJECT_ARCHITECTURE.md` の3章（UI 部品のファイルどうしの依存の向き）と4章（新しいファイルの責務の行、`UiWindow` などの責務の変わる行、自動テストの対象）への影響を、『開発資料の更新予定』に挙げる。

*   **要件11: 自動テスト**

    *  新しい見本の窓の中の部品（どちらの窓も同じ）:

## 【計画書に必ず含めるべきタスクごとの作業】

## 【計画立案時の絶対遵守ルール (Constraints)】
*   **アーキテクチャの維持** : 憲法3章の絶対禁止事項に反する設計をしてはならない。特に、エンジンから `js/` を import しない、エンジンにゲーム固有の値（土台の見本の文言・色・レイアウト、音量の刻みなど）を書かない、公開APIは `oz/index.js` からだけ出す、公開APIを足すタスクの中で `oz/ENGINE_API.md` にも使い方を書く、エンジンは渡された canvas の操作と入力・リサイズのイベント登録以外のDOM操作をしない（UI 部品のファイルは `addEventListener` を使わない。ポインタはシーンから渡されたものだけで動く）、`performance.now()` などで時間を取らない、描画処理の中で状態を変えない（`write` を呼ばない）、`ctx` の状態を外へ漏らさない（呼ぶ側の描く関数も `save` / `restore` で囲む）、`window` にプロパティを足さない。`js/` に `addEventListener`・`requestAnimationFrame`・`getContext` を書かない、`js/` から `oz/src/` を import しない。
*   **責務の分離** : 3種類の部品は、種類ごとにファイルを分け、それぞれのファイル先頭に責務定義を書く。標準の見た目を描く処理（`UiStandardLook.js`）と、当たり判定・押下の状態・値の計算などの Canvas を使わない処理を分ける。`UiWindow.js` を肥大化させない（部品ごとの押下・ドラッグ・値の計算の中身は、部品のファイルに置く）。`Engine`・`Buttons`・`Input`・`Scenes`・`GameLoop`・`Sound` は変えない（変える必要があると分かった場合は、計画に書く前に疑問点として報告する）。責務の範囲が変わるファイルは、開発資料4章の責務表の更新予定に挙げる。
*   **後の作業への備え** : 後の作業（タブ、スクロールする領域。スクロールの中でのタップとドラッグの区別、領域の中のスライダーとの取り合い）が今回の部品の上に乗ることを考えた形にしてよいが、それらの部品そのものや、今回の部品が使わない予備の口（例: タップとドラッグを分ける距離の判定、スクロールの量、部品の削除・押せなくする `enabled`）を先回りで作らない（憲法3章「先回り実装の禁止」）。後の作業がどう乗る見込みかは、RES のアーキテクチャ設計に書くだけにする。
*   **05-02 の仕様を変えない** : 26章に書かれた窓・ボタン・数値・文字の表示の動き（要件2の最後の記述の直しを除く）と、既存の `look` の種類・`info` の項目を変えない。直す必要があると分かった場合は、計画に書く前に疑問点として報告する。
