## 【実装要件】
これまでの作業（Phase 05-02・05-03）で、エンジンに UI 部品（`Ui`。`oz/ENGINE_API.md` 26章）が入った。窓（タイトルバー・閉じるボタン・暗幕）の中に、ボタン、数値・文字の表示、チェックボックス、スライダー、選択肢の列を置ける。描き方の差し替え（`look`）、`read`・`write` による値のつなぎ方、押し始めた部品が離すまでポインタを受け取る仕組みがある。今回、窓の中の部品をまとめる2種類の仕組み、タブとスクロールする領域を足す。ゲーム（バトリティア）の開発用の調整パネルは項目が多く、窓の中に収めるために求めている。

*   **要件1: 置き場所と足し方（決定事項）**
    *  タブとスクロールする領域の処理は、種類ごとに `oz/src/` の新しいファイルに置く（今の `UiCheckbox.js`・`UiSlider.js` などと同じ分け方）。`UiWindow.js` には、それらを足す操作と、ポインタの振り分け・描くための情報の組み立てに必要な最小限だけを足す。新しいファイルは、UI 部品のファイルどうし以外のエンジンモジュールを import しない（開発資料3章の依存の向き）。
    *  タブの列とスクロールする領域の位置と大きさは、ほかの部品と同じく呼ぶ側が論理座標で渡す（窓の内側の左上が原点。`x`・`y`・`width` は必須、`height` の扱いは計画で決める）。部品の自動の並べ方（レイアウトの計算）はしない。
    *  部品をどのタブに入れるか、どのスクロールする領域に入れるかの渡し方（例: タブやスクロールする領域のオブジェクトが `addButton` などの足す操作を持つ。部品の設定にタブを指定する項目を足す）は計画で決め、`oz/ENGINE_API.md` に書く。今ある部品の足す操作（`addButton`・`addValue`・`addCheckbox`・`addSlider`・`addChoices`）の動きと項目は、窓に直接足すときは変えない。

*   **要件2: タブ**
    *  タブの列は、タブの名前（文字列か、描くたびに呼ぶ関数。ほかの部品の `label` と同じ形）の一覧を受け取り、列の矩形をタブの数で等分して並べる（横に並べるだけ。選択肢の列の横と同じ等分の考え方にそろえてよい）。今選ばれているタブが、選ばれていると分かる見た目になる。
    *  部品（スクロールする領域を含む）を、どれか1つのタブに入れられる。選ばれているタブの部品だけが描かれ、押せる。選ばれていないタブの部品は描かれず、押しても反応しない（その位置にある、ほかのタブの部品やタブに入れていない部品が反応する）。
    *  どのタブにも入れない部品は、どのタブが選ばれていても描かれ、押せる（見本の窓の「見た目を切り替える」など、タブに関係なく置きたいボタンのため）。
    *  タブを押すと、そのタブに切り替わる。押し方はボタン（26章「ポインタの受け方」）と同じにする（離したときに切り替わる。押したまま外へずらして離すと切り替わらない。押し始めたタブの上で離したときだけ反応する）。
    *  どのタブが選ばれているかは、窓（またはタブの列）が持つ。ゲームの値ではないので `read`・`write` は使わない。最初は先頭のタブが選ばれている。窓を作り直すと先頭に戻る（シーンを積むたびに新しい窓を作る、26章「シーンへの置き方」のとおり）。ゲームから今のタブを読む・変える口は作らない。
    *  1つの窓に置けるタブの列は1つとする（2つ目を足そうとしたときはエラー）。タブの数が0のときはエラー。タブの列そのものをタブに入れること、スクロールする領域に入れることはできない（エラー）。

*   **要件3: スクロールする領域（発注者の決定を含む）**
    *  スクロールする領域は、窓の内側の矩形を1つ持ち、その中に部品を並べられる。領域の中の部品の位置は、領域の中身の左上（スクロールしていないとき、領域の左上と同じ）を原点とする論理座標で渡す。中身の高さ（どこまでスクロールできるか）は、領域の中の部品の下端から求めるか、呼ぶ側が渡すかを計画で決める。
    *  縦にだけスクロールする（横のスクロールは作らない）。中身が領域の高さに収まるときは、スクロールしない。
    *  領域の中身は、領域の矩形で切り取って描く。領域の外にはみ出した部分は描かれず、押せない（部品の矩形のうち、領域と窓の内側の両方に入っている部分だけが押せる）。全部が外にある部品は、描かれず押せない。
    *  指やマウスを領域の中で押して縦にずらすと、中身がずれる（指に付いて動く）。上端・下端より先へはずれない（引っ張って戻る動きはしない）。部品の無いところを押しても、部品の上を押しても、ずらせる。
    *  **指を離したら、その位置で止まる。はじいたときに慣性で流れる動きは作らない（発注者の決定）。**
    *  **マウスのホイールでのスクロールは作らない（発注者の決定）。** エンジンの入力の仕組み（`Input`）は変えない。
    *  スクロールできるとき、今の位置と中身の量が分かる表示（スクロールバーのような目印。押して動かすことはできない）を領域の中に描く。表示の形は計画で決める。
    *  領域のずれ（スクロールの位置）は、領域が持つ（タブを切り替えて戻っても、窓を開いている間は保たれる）。ゲームから読む・変える口は作らない。
    *  スクロールする領域の中に、スクロールする領域とタブの列は入れられない（エラー）。スクロールする領域はタブに入れられる。

*   **要件4: タップとドラッグの区別**
    *  スクロールする領域の中で押した指は、押した位置から決まった距離（エンジンの固定の論理座標の数値。値は計画で決め、05-03 のスライダーの遊び（幅 8）との関係も考えて理由を RES に書く）より遠くへ動くまでは、タップ（部品を押す）として扱う。その距離を越えて動いたら、ドラッグとして扱う。
    *  ドラッグになったら、押されていた部品（ボタン・チェックボックス・選択肢の列）は押されている状態が消え、離しても反応しない（取り消し）。押されている見た目を押した瞬間から出すか、ドラッグにならないと分かるまで遅らせるかは、計画で決める。
    *  距離を越えなかったときは、今までどおりの部品の動き（離したときに反応する、外へずらすと取り消し）になる。
    *  **スクロールする領域の中のスライダーは、動かした向きで決める（発注者の決定）。** スライダーの上で押しただけでは値を変えない。決まった距離を越えて動いたとき、その向きが横寄りならスライダーの操作（値がその位置へ飛び、離すまで横の位置で追う。05-03 の遊び・端の外・離したときの扱いのまま）、縦寄りならスクロールになる。距離を越えずに離したときは、押した位置へ値が飛ぶ（離したときに1回だけ `write` する）。「横寄り」「縦寄り」の分け方（例: 横の動きと縦の動きの大きいほう）は計画で決める。
    *  スクロールする領域の外（窓に直接置いた部品）のスライダー・ボタンなどの動きは、05-03 までのまま変えない。
    *  ドラッグ中に指が領域の外・窓の外へ出ても、離すまでそのドラッグが続く（スクロールは縦の位置で追う）。離したときに窓は閉じない。
    *  状態の変更（押されているか、ドラッグ中か、スクロールの位置、選ばれているタブ）と `write`・`onPress` の呼び出しは、ポインタを受けたとき（窓の `onPointer` の中）に行い、描画の中では状態を変えない（憲法3章「ロジックと描画の分離」）。

*   **要件5: 見た目の差し替え**
    *  26章の `look` に、タブの列と、スクロールする領域（地・枠と、位置の表示。分けるかは計画で決める）の種類の名前を足す（名前は計画で決める）。渡した種類はその関数で、渡さなかった種類は標準の見た目で描く。描く関数は `save` / `restore` で囲んで呼ぶ。描く関数に渡す情報（`info`）は、少なくとも次を含む。座標はすべて画面の論理座標にする。
        *  タブの列: 列の矩形、タブごとの矩形・名前の文字・選ばれているか・押されているか、文字の大きさ。
        *  スクロールする領域: 領域の矩形、スクロールの位置、中身の高さ（または位置の表示の矩形）、スクロールできるか、ドラッグ中か。
    *  スクロールする領域の中の部品は、今までの種類（`button` など）の描く関数で、スクロールした位置の矩形を渡して描く。描く順序（領域の地 → 中の部品 → 位置の表示、など）は計画で決め、`oz/ENGINE_API.md` に書く。
    *  見た目を差し替えても、押して反応する範囲、タブの等分、スクロールの動きは変わらない。
    *  標準の見た目（単色の塗り・枠・文字）で、2種類を描き足す。

*   **要件6: 既定の大きさ**
    *  タブの列の既定の高さ、位置の表示の太さなどは、05-02 と同じ前提（論理解像度の短い辺が 720 のゲームを、スマートフォンで短い辺を画面の短い辺に合わせて表示したとき、指で押しやすい約 44 CSS 画素以上。26章「既定の大きさ」）で決める。既定の値と、タップとドラッグを分ける距離は `UiMetrics.js` の論理座標の数値として置き、論理解像度や画素の倍率から自動では変えない。決めた値を `oz/ENGINE_API.md` に書く。

*   **要件7: 引数が正しくないとき**
    *  タブの列とスクロールする領域を足す操作、それらに部品を足す操作は、今までの足す操作と同じ形のエラー（`Error`。先頭に `[oz]` と操作名、項目名を含む。知らない項目はエラー。上から順に調べ、最初に当たったものを投げる。エラーのときは何も足されない）になる。要件2・3のエラー（タブの列の2つ目、タブが0個、入れられない組み合わせ、など）を含め、計画で一覧にし、`oz/ENGINE_API.md` 26章のエラーの一覧に足す。

*   **要件8: 05-03 から持ち越した軽微な点**
    *  `oz/ENGINE_API.md` 26章の「スライダーの値の決まり方」の、刻みの値を小数の桁数で丸める説明に、どの桁数でも表せない数（`1e-7` のような指数の形になる数など）のときの扱いが書かれていない。実装を読んで、実際の扱いを書き足す（実装の動きは変えない）。
    *  `step ≤ max - min` の判定が小数のまま比べられていて、`min 0.1・max 0.3・step 0.2` のように、丸めの誤差でエラーになりうる。直すか（整数倍の判定と同じく誤差を見込むなど）、26章に注意として書くかを計画で決め、理由を RES に書く。直す場合は自動テストを足す。

*   **要件9: 05-02・05-03 の仕様を変えない**
    *  26章に書かれた窓と5種類の部品の動き、既存の `look` の種類と `info` の項目は、スクロールする領域の中に置いたときの動き（要件4）を除いて変えない。窓に直接置いた部品は、今までどおりに動く（既存の自動テストが通ったまま）。直す必要があると分かった場合は、計画に書く前に疑問点として報告する。

    *  `PROJECT_ARCHITECTURE.md` の3章（UI 部品のファイルどうしの依存の向き）と4章（新しいファイルの責務の行、`UiWindow` などの責務の変わる行、自動テストの対象）への影響を、『開発資料の更新予定』に挙げる。

*   **要件12: ゲームの土台で確かめられるようにする（決定事項）**

    *  開き方: 05-02 の見本の窓（「UI の見本（標準）」「UI の見本（差し替え）」）に、ボタン「タブとスクロールへ」を足す。押すと、今の窓を閉じて、同じ見た目の新しい見本の窓を開く。05-02 の見本の窓は今でも高さが 640 あり、1行足すと画面に収まらないので、ボタン「値を変える部品へ」と「タブとスクロールへ」を横に並べるなど、配置を直してよい（ほかの部品の動きは変えない）。新しい見本の窓には、ボタン「最初の見本へ」（同じ見た目の 05-02 の見本の窓に替える）と、ボタン「見た目を切り替える」（標準 ⇔ 差し替え）を、どのタブにも入れずに置く。プレイ中のメニュー（`MenuScene`・`playMenu.js`）の項目は変えない。
    *  新しい見本の窓の中の部品（どちらの窓も同じ）:
        *  タブの列: 「スクロール」「表示」の2つ（3つ目を足すかは計画で判断してよい）。
        *  タブ「スクロール」: スクロールする領域を1つ置く。中身は、領域の高さの2倍以上になるようにし、上から次を並べる。

            *  スライダー「BGM の音量」（`Sound.bgmVolume`）、スライダー「効果音の音量」（`Sound.seVolume`）。どちらも最小 0・最大 1・刻み 0.1、値の文字は百分率。保存はしない（音量の保存は後の作業の設定画面で行う）。

            *  ボタン「1 足す」「10 足す」「0 に戻す」（見本の中だけで持つ数を変える。数は窓を開き直しても保たれてよい）。領域のいちばん下に置き、スクロールしないと届かないようにする。
            *  そのほか、中身の高さを稼ぐための部品を足してよい（例: 番号の付いた数値・文字の表示）。
        *  タブ「表示」: 数値・文字の表示「FPS」「スロー」「BGM の音量」「効果音の音量」（タブ「スクロール」で変えた値が、タブを切り替えると合っていることを確かめるため）。
        *  どのタブにも入れない部品: 数値・文字の表示「押した数」（上の数）、ボタン「最初の見本へ」「見た目を切り替える」。
    *  部品の位置と大きさは、土台の画面（1280×720）に収まり、指で押しやすいように計画で決める（エンジンの既定の大きさを使う）。窓は、背面のプレイ画面のバーチャルパッドの円と重ならない位置と幅にする（これまでの見本の窓は x 340〜940 に置き、パッドの円（x ≤ 330、x ≥ 990）を避けている）。収まらない場合は、計画の前に疑問点として報告する。
    *  見本の窓を置くシーンは、05-02 の `UiSampleScene`（背面と同じ配置のバーチャルパッドを登録し、パッドの位置の押下で窓が閉じないようにしている。26章「注意」）を使うか、同じ扱いにする。
    *  見た目を差し替えた窓では、今回の2種類を含め、窓の中のすべての部品の種類を、土台が渡す描く関数で描く（`js/scenes/uiSampleLook.js` に描き足す）。標準の見た目と一目で区別がつき、部品の矩形の内側に描く。
    *  見本の窓と、その中身を作る処理は、責務ごとに分けて `js/scenes/` に置く（今の `uiSample.js`・`uiValueSample.js` のように）。新しい見本の窓は、テストプレイの後も残す（後の作業で、本番の開発用パネルと設定画面に作り替える）。
    *  `js/` を実装するタスクでは、`oz/src/` を読まず `oz/ENGINE_API.md` だけを参照する（憲法3章）。26章で分からないこと、例のとおりに書いて動かないことがあれば、RES に不足として記録し、26章を直す。そのため、土台を変えるタスクは、`oz/ENGINE_API.md` 26章に2種類を書くタスクより後に置く。

*   **要件13: テストプレイで確かめること**
    *  次を、発注者が PC（マウス）とスマートフォン（指。横に持つ。GitHub Pages で公開したページ）で確かめられるように、RES の目視確認推奨箇所に、操作と期待する結果の形で書く。
        *  プレイ中のメニューの「UI の見本」で開く窓の「タブとスクロールへ」で、新しい見本の窓が開く。「最初の見本へ」で戻れる。「見た目を切り替える」で、見た目を差し替えた窓に替わる。05-02 の見本の窓の「値を変える部品へ」も今までどおり使える。
        *  タブ: 「表示」を押して離すと、タブが切り替わり、スクロールする領域が消えて表示の部品が出る。押したまま外へずらして離すと切り替わらない。選ばれていないタブの部品があった位置を押しても何も起きない。どのタブでも「押した数」「最初の見本へ」「見た目を切り替える」は出ていて押せる。
        *  スクロール: 領域の中を押して上下にずらすと中身が指に付いて動き、上端・下端で止まる。離すとその位置で止まる（流れない）。位置の表示が今の位置に合っている。領域の外にはみ出した部品は見えず、押せない。いちばん下の「1 足す」などは、スクロールして押すと「押した数」が増える。
        *  タップとドラッグ: 領域の中のボタンやチェックボックスの上で押して、少しだけ動かして離すと反応する。大きく上下にずらすとスクロールになり、離しても反応しない。
        *  領域の中のスライダー: 押しただけでは値が変わらない。横に動かすと値が追従し、BGM・効果音の音量がその場で変わる。縦に動かすとスクロールになり、値は変わらない。動かさずに離すと、押した位置へ値が飛ぶ。
        *  「スクロール」で変えた値が、「表示」に切り替えると合っている。「スクロール」に戻ると、スクロールの位置が保たれている。
        *  見た目を差し替えた窓で、タブとスクロールする領域が標準の見た目と区別のつく見た目で描かれ、押して反応する範囲とスクロールの動きは、標準の見た目の窓と同じである。
        *  スマートフォンで、タブが指で押しやすく、スクロールとスライダーの操作が意図どおりに分かれる。
        *  PC でウィンドウの大きさを変えたとき、スマートフォンで画面の向きを変えたときも、部品の表示と押して反応する位置がずれない。
        *  窓を開いて閉じる・見本の窓を切り替える、を何度か繰り返しても、開発者ツールのコンソールにエラーが出ない。
    *  テストプレイの結果、部品の作り（タップとドラッグを分ける距離、スライダーの向きの判定、スクロールの感触、見た目の差し替えの仕組み）に問題が出た場合は、実装セッションは推測で直さず、状況を完了報告（未完了）で現場設計セッションに返す（エンジンの直し方は設計で判断する）。土台の見本の窓の配置や文言の細かい直しは、実装セッションで直してよい。

    *  テストプレイは、本リポジトリを GitHub Pages で公開したページ（`/ozengine-web/` の下）で行う。コードの中のパスは `/` から始めない（相対パスにする）。

## 【計画書に必ず含めるべきタスクごとの作業】
AIが作成する計画書（RES）のタスクリストには、個別の実装タスクの後に、以下の作業を必ず含めること。
*   コード修正完了後、JSDocコメントの記載漏れがないことを確認する（新しいファイルの先頭行の責務定義を含む）。
*   `.js` を変更・作成したタスクでは、憲法1章の検証コマンド（構文チェックと、リポジトリのルートでの `node --test` の `fail 0`）を実行する。
*   `oz/` の中のファイルを変更・作成したタスクでは、指紋一覧を作り直す。
*   タスク完了後、作業レポート（本RESファイル）の詳細作業内容を記載し完成させる。
*   開発資料（`PROJECT_ARCHITECTURE.md`）の記載に影響が出る場合は、資料本体は修正せず、その旨を『開発資料の更新予定』欄に追記する。

## 【計画書に必ず含めるべき固定タスク】
AIが作成する計画書（RES）のタスクリストには、全実装タスクの後に、以下のタスクを必ず含めること。
*   各タスクで記録した『開発資料の更新予定』を確認し、開発資料（`PROJECT_ARCHITECTURE.md`）へ反映する。開発資料に影響を与えない場合は、このタスクは不要とする。
    *   ※ 実装AIによる開発資料の書き換えは、本ワークフローにおいて原則禁止であるが、**この最終タスクのみ明示的な例外とする**。後続タスクが存在せず、資料の変更によって他タスクの前提が動く危険がないためである。個別の実装タスク内で資料を書き換えてはならない。

## 【計画立案時の絶対遵守ルール (Constraints)】
*   **アーキテクチャの維持** : 憲法3章の絶対禁止事項に反する設計をしてはならない。特に、エンジンから `js/` を import しない、エンジンにゲーム固有の値（土台の見本の文言・色・レイアウトなど）を書かない、公開APIは `oz/index.js` からだけ出す、公開APIを足すタスクの中で `oz/ENGINE_API.md` にも使い方を書く、エンジンは渡された canvas の操作と入力・リサイズのイベント登録以外のDOM操作をしない（UI 部品のファイルは `addEventListener` を使わない。ポインタはシーンから渡されたものだけで動く）、`performance.now()` などで時間を取らない（慣性を作らないので、時間は使わない）、描画処理の中で状態を変えない、`ctx` の状態を外へ漏らさない（呼ぶ側の描く関数も `save` / `restore` で囲む）、`window` にプロパティを足さない。`js/` に `addEventListener`・`requestAnimationFrame`・`getContext` を書かない、`js/` から `oz/src/` を import しない。
*   **責務の分離** : タブとスクロールする領域は、種類ごとにファイルを分け、それぞれのファイル先頭に責務定義を書く。タップとドラッグの区別の処理をどこに置くか（スクロールする領域のファイルか、別のファイルか）は計画で決めるが、部品ごとのファイル（`UiButton.js` など）にスクロールの知識を散らさない。標準の見た目を描く処理（`UiStandardLook.js`）と、当たり判定・押下の状態・スクロールの計算などの Canvas を使わない処理を分ける。`UiWindow.js` を肥大化させない（部品をまとめる処理の中身は、新しいファイルに置く）。`Engine`・`Buttons`・`Input`・`Scenes`・`GameLoop`・`Sound` は変えない（変える必要があると分かった場合は、計画に書く前に疑問点として報告する）。責務の範囲が変わるファイルは、開発資料4章の責務表の更新予定に挙げる。
*   **先回り実装の禁止** : 今回の部品が使わない予備の口（例: ゲームから今のタブ・スクロールの位置を読む・変える口、横のスクロール、慣性、ホイール、部品の削除・押せなくする `enabled`）を作らない（憲法3章「先回り実装の禁止」）。
*   **サンプルコードの目印** : 要件12で `js/` に足すコードは、土台の見本なので `ozengine sample` の目印を付ける（新しいファイルなら責務定義の直後に `/* ozengine sample */`）。目印の付いた部分をすべて消してもエラーなく起動できる状態を保ち、目印の無いコードが目印の付いたコードを import しない（憲法3章「サンプルコードの目印」）。
*   **変更してよいファイル** : `oz/src/` の UI 部品のファイル（`Ui.js`・`UiWindow.js`・`UiSpec.js`・`UiRect.js`・`UiMetrics.js`・`UiRenderer.js`・`UiStandardLook.js`・`UiSlider.js` の変更（`UiSlider.js` は要件4・8のためのみ）と、タブ・スクロールする領域などの新規ファイル。`UiButton.js`・`UiValue.js`・`UiCheckbox.js`・`UiChoices.js` は、スクロールする領域の中での取り消しに最小限の口が要る場合のみ）、`oz/ENGINE_API.md`、`oz/FINGERPRINTS.txt`（作り直しのみ）、`js/scenes/` のファイル（変更と、要件12のための新規作成）、`test/` の UI 部品のテスト（新規ファイルと、要件11で理由を書いた既存ファイルの直し）、`_doc/newgame/NEW_GAME_GUIDE.md`・`_doc/newgame/GAME_RULES.md`・`_doc/newgame/settings.example.json`（要件10で直す必要がある場合のみ）、`PROJECT_ARCHITECTURE.md`（最終の固定タスクのみ）、作業計画書（本RES）に限る。上に挙げていない `oz/src/` の既存ファイル・`oz/index.js`・`oz/VERSION`・`assets/`・`index.html`・`js/main.js`・`js/scenes/` 以外の `js/`・UI 部品以外の `test/` のファイル・`PROJECT_CONSTITUTION.md`・`CLAUDE.md`・`README.md`・`_doc/newgame/` 以外の `_doc/` は変更しない。これら以外の変更が要ると分かった場合は、計画に書く前に疑問点として報告する。

*   **スコープの分割** : タブのエンジンの処理、スクロールする領域のエンジンの処理（スクロールの計算、タップとドラッグの区別、領域の中のスライダー）、標準の見た目、`UiWindow` への組み込み、自動テスト、`oz/ENGINE_API.md` 26章、要件8の軽微な点、土台の見本の窓、手順書の確認は、混同しない粒度のタスクに分ける。1タスクで変える `oz/src/` のファイルは、できるだけ1つか2つにする。
