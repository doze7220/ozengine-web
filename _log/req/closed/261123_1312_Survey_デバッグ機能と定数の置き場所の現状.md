* ルール: `./PROJECT_CONSTITUTION.md`

## 【作業手順（厳守事項）】
本プロンプトは調査の「計画立案」のみを目的とする。
**本作業および以後のタスク実行を通じて、いかなる理由があってもソースコードおよび資料ファイルの修正・作成を行ってはならない（RESファイルの出力を除く）。** 本工程では調査そのものも行わず、計画の立案のみに留めること。

1. ルール（`PROJECT_CONSTITUTION.md`）および開発資料（`PROJECT_ARCHITECTURE.md`）を熟読・把握すること。
2. 以下の【調査要件】を明らかにするための調査計画を立案し、AIがハルシネーションを起こさない適切なスコープを持つ細かなタスクリストを構築すること。またその際に、調査対象に関連するフォルダ/クラスの責務を開発資料から抜粋し、作成する調査計画書（RES）内の『参照する責務』項目に明記しておくこと（以後のタスク実行チャットは、この項目のみを責務情報源とするため）。
3. 計画を出力する前に内部で自己監査を行い、調査範囲の重複・漏れ、および1タスクあたりのスコープが過大になっていないかを確認して計画を純化すること。（※監査プロセスのテキスト出力は不要）
4. 監査を通過した計画を、調査計画書テンプレート（`./_log/TEMPLATE_RES_SurveyPlan.md`）に完全に準拠したフォーマットで、調査計画書（`./_log/res/YYMMDD_HHMM_RES_Survey_デバッグ機能と定数の置き場所の現状.md`）として新規作成し出力すること。
5. チャットにて「調査計画書の作成が完了しました。タスクを実行するための新しいチャットへ移行してください」と報告すること。

## 【調査要件】
デバッグ機能と定数の置き場所を整理する Phase の範囲をリード設計で決めるために、現状を洗い出す。問題の大きさが分かるように、件数と代表例（`ファイル:行` を付ける）でまとめる。

*   **要件1: デバッグ機能の現状**
    *   エンジン（`oz/`）とゲームの土台（`js/`・`index.html`）にある開発用の機能を一覧にする（FPS の計算と表示、開発用パネル、スローなど開発時の確かめに使われている操作、開発用のキー、コンソール出力など）。一覧には、ファイル、使い方（キー・メニュー・URL など）、エンジンか土台か、目印（`/* ozengine sample */`、`begin`・`end`）の有無、利用側から呼べる API の有無を書く。開発用なのかゲームの機能なのかコードから決められないもの（スローなど）は、決めずにその旨を書く。
    *   コンソール出力（`console.*`）を、出る条件と目的とともにすべて挙げる。開発用の出力か、公開後も要る警告かを区別できる材料を書く。
    *   起動設定 `debug` が、どこで設定され、どこで読まれ、何に効き、何に効かないかを、`js/main.js` から順に追う（URL の `?debug` を含む）。
    *   公開時に開発用の機能を隠す手段があるかを、機能ごとに「ある（手段）／ない」で書く。隠したあとも残るもの（毎フレームの計算、キーの反応、読み込まれるファイルなど）も書く。
    *   新規プロジェクトの手順（`_doc/newgame/NEW_GAME_GUIDE.md` 6章）を行った後に残る開発用の機能を、ファイルと行の単位で示す。目印とファイルの中身から机上で確かめ、コマンドを実際に作業ツリーに対して実行しない（ファイルを消すため）。`js/main.js` の `debug` の行など、目印の中と外の区別を必ず書く。手順書の「残るもの」の記述と食い違いがあれば『開発資料との相違』に書く。

*   **要件2: 定数の現状**
    *   `oz/src/` と `js/` の全ファイルについて、数値・文字列・色・フォントなどの値を次の3つに分けて数える。
        *   (a) 名前の付いた定数（モジュールの先頭の `const` など）になっている値
        *   (b) 処理の中に直接書かれていて、名前の付いた定数にしたほうがよいと考えられる値
        *   (c) 同じ値が複数の場所にあるもの（名前が付いているかどうかを問わない。`js/` と `oz/` にまたがるものを含む）
    *   数え方をそろえる：`0`・`1`・`-1`、半分にするための `2`、配列の添字、`Math.PI` を使った角度の一周などの自明な値、エラー文・JSDoc の文章、イベント名・型の判定に使う言語やブラウザ側で決まっている文字列は (b) に数えない。迷う値の種類は、数えたか数えなかったかを RES に書く。
    *   (c) は「偶然同じ値」と「一緒に変えないと壊れる（または見た目がずれる）値」を分けて書く。後者はそう判断した根拠（コードの上のつながり）を書き、つながりがコードに無いものは『推測・所見』に書く。
    *   資料に値が書き写されているものを挙げる。対象の資料は `oz/ENGINE_API.md`・`PROJECT_ARCHITECTURE.md`・`README.md`・`_doc/newgame/NEW_GAME_GUIDE.md`・`_doc/newgame/GAME_RULES.md`・`_doc/newgame/settings.example.json` と、`js/`・`oz/src/` の JSDoc・コメントの文章。値ごとに、元の値の場所（`ファイル:行`）、書き写しの場所（`ファイル:章または行`）、今の値が一致しているかを書く。一致していないものは『開発資料との相違』にも書く。書き写しが「利用側が知る必要のある公開の値」か「エンジンの中だけの値」かも区別する。
    *   見つかった値を、次の3つに分けて件数を出す。
        *   **エンジンの内部の値**: `oz/` の中にあり、ゲームごとに変える必要がないと考えられる値
        *   **ゲームごとに変えたい値**: `oz/` と `js/` のどちらにあっても、ゲームによって変えたくなると考えられる値（既に起動設定や引数で変えられるものは、そのことも書く）
        *   **ゲームの土台の値**: `js/` の値で、土台の動き・見た目のためのもの。新規プロジェクトの手順の後に消えるもの（目印あり）と残るもの（目印なし）を分けて数える
    *   分け方が1つに決まらない値は、両方の候補を書いて別に数える。
    *   `index.html` の値（CSS の色など）は数えないが、`oz/`・`js/` の値と一緒に変えないと壊れるもの（背景色など）があれば (c) に書く。`assets/` の素材の中身は数えない。

*   **要件3: すでに定数がまとまっている場所と、その書き方の違い**
    *   `oz/src/UiMetrics.js`、`oz/src/UiStandardLook.js`、`js/ui/virtualPadConfig.js`、`js/scenes/settingsLook.js`、`js/main.js` の設定、各ファイルの先頭の `const` の並びなど、値がまとまっている場所を洗い出す。
    *   場所ごとに、書き方の違いを表で比べる（1つの値に1つの `const` か、オブジェクトにまとめるか、`Object.freeze` の有無、`export` の有無、命名、JSDoc の付け方（型・単位・決めた理由）、値の決め方の説明の有無、どこから読まれるか、ゲームが値を変える手段）。
    *   同じ役割の値（部品の大きさ、色、文字の大きさ、レイヤー名、キーの名前など）が、場所によって違う形で書かれている例を挙げる。

*   **要件4: 定数を外に出すときにぶつかる点**
    *   次のそれぞれについて、要件2で分けた値の種類ごとに、どの決まりのどの文とぶつかるか、またはぶつからないかを書く。
        *   `PROJECT_ARCHITECTURE.md` 3章の依存の向き（「他のエンジンモジュールに依存しない」モジュールの一覧、UI 部品のファイルの中の向き、`UiMetrics` が何も import しないこと、`Engine` が引数や関数で値を渡す形）と、4章の各モジュールの責務（`UiMetrics` に見た目の値を書かない、など）
        *   `PROJECT_CONSTITUTION.md` 3章（ゲーム固有知識の混入禁止、入口の一本化、公開APIとドキュメントの同時更新、サンプルコードの目印、責務定義の記述、先回り実装の禁止など）。目印の付いたファイルと付いていないファイルで同じ値を使うとき、どちらに置けるか（目印の付いていないファイルから目印の付いたコードを import できない）も確かめる
        *   自動テスト（`test/`）。値を直接書いているテストと、定数を import しているテストをファイルごとに挙げ、値を変える・動かすと変更が要るテストを示す。テストが確かめている定数（`DEFAULT_*`・`SLIDER_*`・`SCROLL_*`・`LOOK_KINDS` など）の場所が変わると直す必要がある箇所を含む
        *   指紋一覧（`oz/FINGERPRINTS.txt`）。`oz/` の定数を外に出す・動かすと、作り直しとゲーム側のエンジンの更新（`NEW_GAME_GUIDE.md` 5章・9章）にどう効くか。`oz/` にゲームごとに変える値の置き場所を作った場合に、指紋の照合と、`oz/` を丸ごと置き換える更新でどうなるか
        *   新規プロジェクトの手順（`NEW_GAME_GUIDE.md` 6章・7章）。ファイルの数やファイル名が書かれている箇所（残るファイルの数など）と、ゲームごとに変える箇所の一覧
    *   `js/` から `oz/src/` の値を使いたいときの経路（`oz/index.js` から公開されているもの、されていないもの）も示す。

## 【計画書に必ず含めるべきタスクごとの作業】
AIが作成する調査計画書（RES）のタスクリストには、個別の調査タスクごとに、以下の作業を必ず含めること。
*   実コードから読み取れる事実のみを抽出し、推測を含める場合はどこまでが事実でどこからが推測かを明示して、調査計画書の『事実』『推測・所見』欄にそれぞれ記載する。
*   件数は、対象のファイルを実際に読んで数える。コマンドで数えた場合はそのコマンドも書く（検索だけで済ませず、代表例は必ず該当行を読んで確かめる）。
*   『参照する責務』の記述と実コードに相違があった場合は、調査計画書の『開発資料との相違』欄に記載する（作業は中断しない）。

## 【計画書に必ず含めるべき固定タスク】
AIが作成する調査計画書（RES）のタスクリストには、全調査タスクの後に、以下のタスクを必ずこの順に含めること。
*   **まとめのタスク**: 全タスクの調査結果を読み、次を1つの節にまとめる。コードを読まない発注者が読む前提で、コードの言葉は最小限にする。
    *   問題の大きさ：要件1〜4の件数の一覧と、種類ごとの代表例（それぞれ数件）
    *   直し方の案：デバッグ機能の扱いと、定数の置き場所のそれぞれについて2つ以上の案を挙げる。案ごとに、長所、短所、変わるファイルのおおよその数、ぶつかる決まり（要件4）と、その決まりを変える必要があるか、ゲーム側（既にエンジンをコピーしているゲーム）への影響を書く。「今のまま何もしない」も案として比べる
    *   **どの案がよいかの結論・推奨は書かない。** 決めるのはリード設計で行う
    *   リード設計で決める必要がある論点の一覧
*   『開発資料との相違』欄を確認し、相違が一件もなかった場合は「相違なし」と明記する（未確認と区別するため）。
