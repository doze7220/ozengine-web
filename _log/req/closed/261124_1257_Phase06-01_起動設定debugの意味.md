## 【実装要件】
いまの起動設定 `debug` は、FPS の表示の起動時の値（`Engine.fpsVisible`）を決めるだけで、ゲームからは読めない。これを「開発モードで起動したか」を表すものにし、ゲームが読めるようにする。公開するゲームで、開発用の入口をゲームが隠せるようにするための土台である。あわせて、土台の `js/main.js` の URL の `?debug` を読む行を、新規プロジェクトで見本を消した後も使えるようにする。

*   **要件1: 開発モードの読み取り（決定事項）**
    *  `Engine.debug` で、開発モードで起動したかどうかを読めるようにする（読み取り専用。`true` か `false`）。値は、起動設定 `debug` を `Boolean(...)` で解釈した真偽で、`Engine.start` のときに決まり、その後は変わらない。`debug` を省くと `false`。
    *  `Engine.start` の後から使える。最初のシーンの `init` の中でも読める。`Engine.start` の前に読むと、ほかの API と同じ形のエラー（`[oz] Engine.debug: Engine.start の前には使えません`）になる。
    *  代入したときの扱いは、既存の読み取り専用の値（`Engine.fps`。`oz/ENGINE_API.md` 14章「エラー」）とそろえる。値を変える口は作らない。
    *  起動設定 `debug` の解釈（`Boolean(...)`。型の検証はしない）は変えない。

*   **要件2: FPS の表示との関係（決定事項）**
    *  `debug` が真なら、これまでどおり FPS を表示した状態（左上）で始まる。偽なら表示しない状態で始まる。
    *  起動した後の `Engine.fpsVisible` と `Engine.debug` は互いに影響しない。FPS の表示を消しても `Engine.debug` は変わらず、開発モードでなくても `Engine.fpsVisible` で FPS を表示できる。
    *  エンジンは、開発モードかどうかで、起動時の FPS の表示のほかの動きを変えない（FPS の計算、警告、`timeScale`、入力、描画など）。何を隠すかはゲームが決める。
    *  起動設定を変えていない既存のゲームが、新しい `oz/` に置き換えても、これまでと同じに動く（`debug` を渡していないゲーム、渡しているゲームのどちらも）。

*   **要件3: 土台の URL の指定（決定事項）**
    *  土台（`js/main.js`）を、URL に `?debug` を付けて開くと開発モードになる。付けない場合と、`?debug=0` の場合は、開発モードにならない。

       | URL の末尾 | 開発モード |
       | --- | --- |
       | 付けない | ならない |
       | `?debug` | なる |
       | `?debug=0` | ならない |
       | `?debug=1` など、`0` 以外の値 | なる |

    *  ほかの指定と並べたとき（`?a=1&debug` など）も同じに判定する。大文字の `?DEBUG` は指定とみなさない。
    *  今は `js/main.js` の `ozengine sample` の範囲の中にある、URL を読んで `debug` を決める処理を、目印の外へ移す。レイヤーと最初のシーンの書き換え（見本）は、目印の中に残す。
    *  `js/main.js` を読んだ人が、`debug` の意味と、URL のどの指定で真になるかを、ファイルの中のコメントで分かるようにする。
    *  ゲームが `debug` を偽に固定したいときは、`js/main.js` の1か所の書き換えで済む形にする（固定の仕組みや切り替えの設定は作らない）。

*   **要件4: 見本を消した後の確認**
    *  本リポジトリの外の一時フォルダに、`index.html`・`oz/`・`js/`・`assets/` の写しを作り、`_doc/newgame/NEW_GAME_GUIDE.md` 6-2 のコマンドをその写しで実行して、次を確かめる。確かめた結果を RES に書き、写しは残さない。
        *  `js/main.js` に、URL の指定で `debug` を決める処理が残り、目印とエラーになる import・未定義の名前が残っていない（構文チェックを含む）。
        *  残る `.js` のファイルが、今の手順書 6-2 に書かれた6ファイルと同じである（この作業でファイルは増減しない）。
    *  本リポジトリの土台の見本は消さない。
    *  手順書の `debug` に関する書き足し（公開するときの扱いなど）は、この作業ではしない。

*   **要件5: 資料**
    *  `oz/ENGINE_API.md` に、開発モード（起動設定 `debug` と `Engine.debug`）の節を、章の番号を変えずに置く（置き場所は 3章の中を見込む。計画で決める）。書くこと: `debug` の意味、`Engine.debug` の使い方と値、読める時期（`Engine.start` の前に作るシーンの `constructor` では読めず、`init` の中からは読める）、起動後に変わらないこと、エラー、FPS の表示との関係（要件2）、エンジンがほかの動きを変えないこと（開発用の入口を隠すのはゲームである）、ゲームで開発用の入口を分ける短い使い方の例。
    *  3章の起動設定の表の `debug` の行、1章の `Engine` でできることの一覧、14章の `debug` に触れている箇所を、新しい意味に合わせて直す。ほかの章に `debug` の古い意味が残っていないかも確かめる。
    *  `PROJECT_ARCHITECTURE.md` の 2.2章（`debug` の行）、3章（`Engine` が各モジュールを生成する段落の `debug` の記述）、4章の `Engine`・`js/main.js` の責務に影響が出るので、『開発資料の更新予定』に挙げる。
    *  `oz/` の中のファイルを変更するタスクでは、最後に指紋一覧 `oz/FINGERPRINTS.txt` を作り直し、`node --test` が `fail 0` であることを確かめる（開発資料4章「指紋一覧の規則」）。

*   **要件6: 自動テスト**
    *  `Engine` は今も自動テストの対象にしていない（開発資料4章「自動テスト（`test/`）の規則」）。今回も対象に加えない。既存のテストは変えない。

*   **要件7: テストプレイで確かめること**
    *  次を、発注者が PC とスマートフォン（GitHub Pages で公開したページ）で確かめられるように、RES の目視確認推奨箇所に、操作と期待する結果の形で書く。
        *  `?debug` を付けて開くと、これまでどおり左上に FPS が出る。付けないと出ない。`?debug=0` では出ない。`?debug=1` では出る。
        *  どの開き方でも、ゲームの動き（boot 画面、タイトル、プレイ、メニュー、開発用パネル、設定、`F`・`S`・`P` などのキー）が今までと変わらない（この作業では、開発モードでないときも開発用の入口はこれまでどおり使える）。
        *  `?debug` なしで開いたときも、`F` キーや開発用パネルで FPS を出せる。
    *  `Engine.debug` の値は土台の画面では確かめられない。PC のブラウザの開発者ツールのコンソールで確かめる手順を、目視確認推奨箇所に書く（例: `const { Engine } = await import('oz');` のあとに `Engine.debug`。`?debug` のとき `true`、なし・`?debug=0` のとき `false`。FPS の表示を消しても `true` のまま。代入しても値が変わらない）。

*   **要件8: 公開先**

## 【計画書に必ず含めるべきタスクごとの作業】
AIが作成する計画書（RES）のタスクリストには、個別の実装タスクの後に、以下の作業を必ず含めること。
*   コード修正完了後、JSDocコメントの記載漏れがないことを確認する（ファイル先頭の責務定義を含む）。
*   `.js` を変更・作成したタスクでは、憲法1章の検証コマンド（構文チェックと、リポジトリのルートでの `node --test` の `fail 0`）を実行する。
*   `oz/` の中のファイルを変更・作成したタスクでは、指紋一覧を作り直す。
*   タスク完了後、作業レポート（本RESファイル）の詳細作業内容を記載し完成させる。
*   開発資料（`PROJECT_ARCHITECTURE.md`）の記載に影響が出る場合は、資料本体は修正せず、その旨を『開発資料の更新予定』欄に追記する。

## 【計画立案時の絶対遵守ルール (Constraints)】
*   **アーキテクチャの維持** : 憲法3章の絶対禁止事項に反する設計をしてはならない。特に、エンジンから `js/` を import しない、エンジンに `?debug` などの URL の知識を書かない（URL を読むのは `js/main.js` だけ）、公開APIを変えるタスクの中で `oz/ENGINE_API.md` も直す、`window` にプロパティを足さない、エンジンがページの DOM や URL を参照しない。`Engine` のプロパティを足すので、`oz/index.js` の再export は変わらない。
*   **責務の分離** : 開発資料4章の責務表に合わせる。開発モードの値は起動設定として `Engine` が持つ。`DebugOverlay` は FPS の計算と表示だけのままにし、開発モードを知らせない（起動時の `visible` の設定は今の形のまま）。責務の文が変わるファイル（`Engine.js`・`js/main.js`）は、ファイル先頭の責務定義（3行以内）と開発資料4章の責務表の更新予定に挙げる。
*   **`oz/src/` の閲覧** : `js/main.js` を変えるタスクでは、`oz/src/` を読まず `oz/ENGINE_API.md` だけを参照する（憲法3章）。書き直した `oz/ENGINE_API.md` で分からないことがあれば、RES に不足として記録する。そのため、土台を変えるタスクは、`oz/ENGINE_API.md` を直すタスクより後に置く。
*   **変更してよいファイル** : `oz/src/Engine.js`、`oz/ENGINE_API.md`、`oz/FINGERPRINTS.txt`（作り直しのみ）、`js/main.js`、`PROJECT_ARCHITECTURE.md`（最終の固定タスクのみ）、作業計画書（本RES）に限る。これら以外の変更が要ると分かった場合は、計画に書く前に疑問点として報告する。
*   **外部依存の禁止** : 外部ライブラリ・npm パッケージ・`package.json`・ビルドを使わない。
*   **スコープの分割** : エンジンの変更（公開APIと `oz/ENGINE_API.md`）、土台の `js/main.js` の変更、見本を消した写しでの確認は、混同しない粒度のタスクに分ける。
*   **確認の範囲** : 実装AIはブラウザや実機での動作確認を行わない（発注者のテストプレイで行う）。要件7の確認事項を、RES の懸念事項・目視確認推奨箇所に挙げる。
*   **今回やらないこと** : 次は作らない・変えない。
    *  開発用の入口（`F`・`S` のキー、メニューの項目「開発用パネル」）を開発モードで出し分けること、`js/scenes/` などの変更、開発用パネルの作り直し。
    *  新しいデバッグ機能。FPS の計算を止めること、コンソールの警告を条件によって止めること。開発用のコードを公開時に取り除く仕組み。
    *  `_doc/newgame/` の手順書の変更。
    *  起動設定の項目を増やすこと、`Engine.fpsVisible`・`Engine.fpsPosition`・`Engine.fps` の仕様の変更。
    *  `oz/src/Engine.js` の既存の重複（`requireStarted`・`requireScenes`・`requireOverlay`）の整理。
    *  `oz/VERSION` の更新。
