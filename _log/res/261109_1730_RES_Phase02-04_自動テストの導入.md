# RES: 作業計画・作業レポート Phase 02-04 : 自動テストの導入
* 参照元REQ: `./_log/req/261109_1730_Phase02-04_自動テストの導入.md`

## 1. 作業目的
ブラウザなしで動くエンジンのモジュール（`Time`・`Scenes`・`Screen`・`Storage`）に、Node.js 標準の `node:test` による自動テストを入れ、`oz/` を直したときに壊れたことに気づけるようにする。テストはエンジンの配布単位（`oz/`）の外の `test/` に置き、憲法1章の検証コマンドに `node --test` を加える。**エンジンのソース（`oz/` 以下）は一切変更しない。**

## 2. アーキテクチャ設計
### 要件1: テストの実行方法
*   リポジトリのルートで `node --test`（引数なし）を実行すると、すべてのテストが実行され、すべて成功する（結果の `fail 0` で判定する）。
*   `package.json` は作らない。import してよいのは `node:test` と `node:assert/strict` だけである（例外は要件5の、`oz/src/` のクエリ付きの動的 import）。npm パッケージ・外部ライブラリ・DOM の模擬ライブラリは使わない。
*   確認した Node.js の版は **v24.15.0** である（`package.json` がなくても `import`/`export` を含む `.js` が ES Modules として警告なしに読み込まれること、クエリ付きの動的 import が別のモジュールになることを、この版で確認済み）。
*   Node.js はテストの実行にのみ使う。ゲームの実行・配信には使わない。
*   `node --test` を引数なしで実行すると、Node.js は既定のパターン（`**/*.test.js`・`**/*-test.js`・`**/*_test.js`・`**/test-*.js`・`**/test.js`・`**/test/**/*.js` など。`node_modules` を除く）に合うファイルをすべて実行する。計画立案の時点では、`test/` 以外にこれに合うファイルはない。

### 要件2: テストの置き場所と命名
*   テストはリポジトリのルートの `test/` に置く。ファイル名は `test/<対象モジュール名>[.<観点>].test.js` とする。本作業で作るファイルは次の5つである。

| ファイル | 対象 | 確かめる観点 |
| --- | --- | --- |
| `test/Time.test.js` | `oz/src/Time.js` | ティック長、蓄積と消費、上限、`timeScale`、`gameTime`、初回、`discardAccumulated`、`view` |
| `test/Scenes.test.js` | `oz/src/Scenes.js` | `push`・`pop`・`change`、`init`・`destroy` の順序、空のとき、`update`、`forEachFromBottom`、`consumeChanged` |
| `test/Screen.test.js` | `oz/src/Screen.js` | 構築時の canvas の大きさと表示サイズ、リサイズ、`toLogical` |
| `test/Storage.test.js` | `oz/src/Storage.js` | `open`・`get`・`set` の基本、引数とAPIのエラー、コピー、`set` のその場の保存 |
| `test/Storage.load.test.js` | `oz/src/Storage.js` | 保存データの読み込み（版番号・壊れたデータ・名前の過不足）、`localStorage` が使えないとき、保存に失敗したとき |

*   `test/` には共有の補助モジュールを置かない（`node --test` が `test/` 以下の `.js` をすべてテストとして実行するため）。補助関数（偽の `window` を作る関数など）は各テストファイルの中に書く。補助関数が複数のファイルで重複してもよい。
*   依存は `test/ → oz/src/` の一方向である。`oz/`・`js/`・`assets/`・`index.html` は `test/` を参照しない。
*   `test/` は新規プロジェクトにコピーしない（開発資料1章のコピー手順の対象は `index.html`・`oz/`・`js/`・`assets/` だけで、変更しない）。

### 要件3: テストからの import
*   テストは対象モジュールを `oz/src/` から相対パスで直接 import する（例: `import { Time } from '../oz/src/Time.js';`）。テストは利用側ではないので、憲法3章「入口の一本化」の対象外である。
*   テストは `oz/index.js` を import しない（`oz/index.js` を import すると、`Sound` が読み込み時に `window` へイベントを登録するため `window` が必要になる。この件は本作業では見直さず、`Sound` をテストの対象にするときに検討する）。
*   テストは、対象モジュールの公開されたもの（`export` されたクラス・オブジェクトと、その JSDoc にある公開メソッド・プロパティ）だけを通して確かめる。`Screen` の `_fit`・`_canvas`・`_width`・`_height`（`@private`）や、`Time`・`Scenes` の `#` で始まるフィールドには触れない。`Screen` の表示サイズの再調整は、偽の `window` に登録された `resize` のリスナーを呼んで確かめる。
*   テストのためにソースへ `export` を足す、private を公開する、処理を切り出す、といった変更はしない。

### 要件4: テストの対象と確かめる内容
対象は `Time`・`Scenes`・`Screen`・`Storage` の4つに限る。`Scene`・`Input`・`Sound`・`Assets`・`Layers`・`GameLoop`・`DebugOverlay`・`Engine`・`Buttons` のテストは書かない。確かめる内容は、各ファイルの JSDoc、開発資料 2.4章・3章・4章、`oz/ENGINE_API.md` 22章（`Storage`）に書かれた約束から決めた。各タスクの「作業内容」に、確かめる項目を列挙する。JSDoc や資料に書かれていない内部の処理（`Time` の `now` が戻ったときの扱い、`forEachFromBottom` の中でスタックを変えたときの扱いなど）はテストしない。

### 要件5: ブラウザの代わりの用意（`window`・canvas）と `Storage` の読み込み方
*   `Time`・`Scenes` は `window` を使わないので、偽物を用意しない。
*   `Screen`・`Storage` のテストでは、テストファイル内の素のオブジェクトで偽の `window` と偽の canvas を作る。
    *   偽の `window`（`Screen`）: `innerWidth`・`innerHeight` と、`addEventListener(type, listener)`（登録されたリスナーを記録し、テストから呼べるようにする）。
    *   偽の `window`（`Storage`）: `localStorage`。偽の `localStorage` は `Map` に値を持ち、`getItem(key)`（なければ `null`）・`setItem(key, value)`（文字列で保持し、呼ばれた回数を記録する）を持つ。使えない場合は、`localStorage` の getter が例外を投げる偽の `window` を使う。保存に失敗する場合は、`setItem` が例外を投げる偽の `localStorage` を使う。
    *   偽の canvas（`Screen`）: `width`・`height`・`style`（空のオブジェクト）・`getBoundingClientRect()`（テストが決めた `{ left, top, width, height }` を返す。差し替えられるようにする）。
*   偽の `window` は `globalThis.window` に置く。置く補助関数は、置く前の `globalThis` の `window` のプロパティ記述子を覚え、`t.after` でテストの終了時に元に戻す（置く前に無かったなら `delete globalThis.window`）。`window` 以外のグローバルには代入しない。
*   `console.warn` は、警告が出るテストでだけ `t.mock.method(console, 'warn', () => {})` で抑止し、呼ばれた回数と第1引数の先頭（`[oz] Storage.open:`／`[oz] Storage.set:`）を確かめる。`t.mock` はテストの終了時に自動で戻る。
*   `Storage` の読み込み方（決定）: **テストごとにクエリ付きの動的 import で新しいモジュールを読み込む**。各ファイルに補助関数（例: `loadFreshStorage()`）を書き、ファイル内の連番を付けた `import(\`../oz/src/Storage.js?case=${n}\`)` から `Storage` を取り出す。テストごとに独立したモジュール（未 `open` の状態）になるので、実行順に依存しない。観点が多いため、テストファイルは `Storage.test.js` と `Storage.load.test.js` の2つに分ける（それぞれ別タスク）。`Storage` は `window` を `open`・`set` の呼び出し時に参照するので、偽の `window` は `open` の前に置けばよい。

*   [x] タスク1: `Time` の自動テスト
    *   **対象ファイル** :
        *   `./test/Time.test.js` : 新規
        *   `./oz/src/Time.js` : 閲覧のみ（共通手順Bで一時的に不具合を入れ、同じタスク内で元に戻す）
    *   **作業内容** :
        *   `import { Time } from '../oz/src/Time.js';` で読み込む。偽の `window` は使わない。ティック長が割り切れる `tickRate`（例: 50 → 20ミリ秒）を主に使う。
        *   確かめる項目:
            *   `tickLength` が `1000 / tickRate` であること（例: 50 → 20、60 → `1000 / 60`）。`timeScale` の初期値が `1` であること。
            *   初回のフレーム: 最初の `beginFrame(now)` では `realDelta` が `0` で、`gameTime` が進まず、`consumeTick()` が `false` であること（`now` が大きな値でも）。
            *   蓄積と消費: 2回目以降の `beginFrame` で `realDelta` が `now` の差になり、蓄積がティック長に達している間だけ `consumeTick()` が `true` を返すこと（例: 20ミリ秒のティックで50ミリ秒経過 → 2回 `true`、3回目 `false`）。残り（10ミリ秒）が次のフレームに持ち越されること（次に10ミリ秒経過 → 1回 `true`）。
            *   ティック長ちょうど: `tickRate` 60 で `now` を `i * 1000 / 60` と進めたとき、各フレームでちょうど1回 `true` になること（浮動小数点の誤差でティックを落とさない）。
            *   1フレームの上限: 大きく経過した（例: 1000ミリ秒）フレームでも、消費できるのは5ティック分までで6回目は `false`、`gameTime` の増加も5ティック分であること。`realDelta` は上限で切られず実際の差になること。
            *   `timeScale` の適用: `0.5` で40ミリ秒経過 → `gameTime` が20増え1ティック分。`0` → `realDelta` は進むが `gameTime` と蓄積は進まない。`2` のときも上限（5ティック分）が `realDelta × timeScale` に掛かること。
            *   不正な値: `-1`・`NaN`・`Infinity`・`'1'`・`null`・`undefined` の代入が `RangeError` になり、`timeScale` が変わらないこと。`0` は代入できること。
            *   `gameTime` の加算: 複数フレームにわたり、`realDelta × timeScale`（上限付き）の合計になること。
            *   `discardAccumulated`: 呼んだ直後は残っていた蓄積が消えて `consumeTick()` が `false` になること。次の `beginFrame` では `realDelta` は更新されるが、蓄積と `gameTime` が進まないこと。その次のフレームからは通常どおり進むこと。
            *   `view`: 毎回同じオブジェクトで、`Object.isFrozen` が `true` であること。`realDelta`・`gameTime`・`timeScale` への代入が `TypeError` になること（ES Modules は strict モード）。`beginFrame` や `timeScale` の変更の後に、同じ `view` から最新の値が読めること。
        *   共通手順Bの不具合の例: `MAX_TICKS_PER_FRAME` を `6` にする（上限のテストが失敗するはず）。
        *   共通手順A・C・Dを行う。

## 5. 懸念事項・要確認ポイント
* `node --test` を引数なしで実行すると、`test/` の外でも既定のパターン（`*.test.js`・`*-test.js`・`*_test.js`・`test-*.js`・`test.js`）に合うファイルがテストとして実行される。計画立案の時点ではそのようなファイルはない。将来 `js/`・`assets/`・`_doc/` などにこれらの名前のファイルを置くと誤って実行されるため、開発資料4章の規則に書く予定である。
* `Storage` のテストは、テストごとにクエリ付きの動的 import で別のモジュールを読み込む。読み込んだモジュールはプロセスの終了まで残るが、`node --test` はテストファイルごとに別のプロセスで実行する（Node.js v24 の既定）ので、ファイルをまたいだ影響はない。
* `Screen` は構築時に `window` へ `resize` のリスナーを登録し、解除する手段を公開していない。テストでは偽の `window` に登録されるだけで、テストの終了時に偽の `window` ごと外すので問題はない。
* `installWindow` は `t.after` が登録順（先入れ先出し）に動くため、1つの `t` に対して偽の `window` を2回以上置くと元に戻らない。`loadFreshStorage` 等は1つの `t` につき1回だけ呼び、繰り返すときはサブテストに分けること。
* `Storage` の保存データの読み込みでは、版番号が同じなら保存値をそのまま使い、値の型や JSON にできるかは確かめない（`ENGINE_API.md` 22章にも記載がない）。この挙動はテストで固定しない。
