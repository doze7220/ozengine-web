### 要件4: `oz/` の改変の確かめ方（指紋一覧）
*   **一覧ファイル:** `oz/FINGERPRINTS.txt`。
*   **形式:** 1行に1ファイル。`<SHA-256 の16進64文字（小文字）><空白2つ><oz/ からの相対パス>` の形（`sha256sum` の出力と同じ形）。パスの区切りは `/`（例 `src/Assets.js`）。行はパスのバイト順（`LC_ALL=C sort` の順。Node.js では UTF-8 のバイト列の比較）に並べ、各行（最後の行を含む）は LF で終わる。見出しやコメントの行は持たない。一覧ファイル自身は一覧に含めない。それ以外の `oz/` 以下のすべてのファイル（`ENGINE_API.md`・`VERSION`・`index.js`・`src/*.js`、および将来足されるファイル。隠しファイルを含む。シンボリックリンクは含めない）を含める。
*   **指紋の求め方（改行コードの扱い）:** ファイルの中身から CR（`\r`、0x0D）のバイトをすべて取り除いてから SHA-256 を求める。一覧ファイルを読むときも CR を取り除いてから比べる。
    *   理由: 本リポジトリは `core.autocrlf=true`（Git for Windows の既定）で運用しており、作業ツリーの改行は git の記録（LF）と違うことがある。実際に、計画立案時点の作業ツリーでは `oz/ENGINE_API.md` だけが CRLF で、ほかは LF だった。ゲームのプロジェクトへのコピー、ゲームのリポジトリでの出し入れ、別の環境でのクローンで改行が LF と CRLF の間で変わっても、CR を取り除けば同じ指紋になるので、改変していないのに照合が失敗することはない（計画立案時に、CR を取り除いた作業ツリーの `ENGINE_API.md` の指紋が、git の記録の `git show HEAD:oz/ENGINE_API.md` の指紋と一致することを確かめた）。
    *   見逃す変更: CR だけを足した・消した変更は検出しない。改行コードの違いはブラウザでの動作に影響しないので、許容する。CR 以外の変更（1文字の書き換え、BOM の付加、文字コードの変換など）はすべて検出する。
    *   `.gitattributes` で改行を固定する案は採らない（本REQで `.gitattributes` を作ることは許されておらず、ゲームのプロジェクトにも届かないため）。
*   **作り直しのコマンド（本リポジトリ、Git Bash、リポジトリのルートで実行）:**
    ```bash
    (cd oz && find . -type f ! -path ./FINGERPRINTS.txt | sed 's|^\./||' | LC_ALL=C sort | while IFS= read -r f; do printf '%s  %s\n' "$(tr -d '\r' < "$f" | sha256sum | cut -c1-64)" "$f"; done > FINGERPRINTS.txt)
    ```
    *   作り直しに Node.js は使わない（照合のコマンドと同じ計算を同じ道具で行い、食い違いを避けるため）。作り直した後に `node --test` を実行し、自動テスト（Node.js で同じ計算をする）と一致することを確かめる。
*   **照合のコマンド（ゲームのプロジェクト、Git Bash、ゲームのフォルダのルートで実行）:**
    ```bash
    (cd oz && find . -type f ! -path ./FINGERPRINTS.txt | sed 's|^\./||' | LC_ALL=C sort | while IFS= read -r f; do printf '%s  %s\n' "$(tr -d '\r' < "$f" | sha256sum | cut -c1-64)" "$f"; done | diff <(tr -d '\r' < FINGERPRINTS.txt) -) && echo "OK: oz/ matches FINGERPRINTS.txt" || echo "NG: oz/ does not match FINGERPRINTS.txt"
    ```
    *   改変・追加・削除を1回の比較で見つける。結果の読み方: `OK` なら一致。`NG` のときは、その上に差分の行が出る。行頭が `<` の行は一覧に書かれた内容、`>` の行は実際の `oz/` の内容である。同じパスが `<` と `>` の両方に出たら「改変」、`<` だけなら「削除」、`>` だけなら「追加」。
    *   計画立案時に、本リポジトリの外の一時フォルダで、作り直しと照合が成功し、1ファイルの改変・1ファイルの追加・1ファイルの削除がそれぞれ差分として出ることを確かめた。
    *   使うのは `find`・`sed`・`sort`・`tr`・`sha256sum`・`cut`・`diff`（すべて Git for Windows の Git Bash に入っている）。メッセージは文字化けを避けるため英語にする。
*   **照合に Node.js を必須にしない（判断と理由）:** ゲームのプロジェクトには Node.js が入っていない場合がある（Node.js は本リポジトリのテストと指紋一覧の確認にだけ使う）。一方、Git for Windows はゲームのリポジトリのクローンに必要なので、Git Bash は必ずある。そのため照合は Git Bash だけで行えるコマンドにする。PowerShell 版は用意しない（`Get-FileHash` は CR を取り除けず、取り除く版は1行に収まらず、検証する対象が2つに増えるため）。
*   **照合は発注者が行う:** 照合のコマンドは `oz/src/` のファイルの中身を（指紋を求めるために）開く。ゲームのプロジェクトでは、Claude Code の設定で `oz/src/` を読む操作を拒否し、ルールの文面で AI が `oz/src/` を開くコマンドを実行することを禁止するので、照合は発注者が Git Bash（エクスプローラーでゲームのフォルダを右クリック →「その他のオプションを確認」→「Open Git Bash here」）で実行する。
*   **照合が失敗したときの意味と対処（手順書に書く）:** 意味は「`oz/` が改変された」または「`oz/` の中身と一覧の版が合っていない（一部のファイルだけ古い・新しい）」のどちらか。対処は、本リポジトリの `oz/` で置き換え直す（9章の手順3）。ゲーム側で `oz/` の中身や一覧を直してはならない。心当たりのない追加のファイル（エクスプローラーが作る `desktop.ini`・`Thumbs.db` など）が `>` に出たら、そのファイルを消せば一致する。BOM の付加や文字コードの変換をするエディタで `oz/` のファイルを開いて保存すると失敗する（置き換え直す）。
*   **ゲームのリポジトリでの補助の目印:** ふだんは `git status` に `oz/` の変更が出ないことも確かめられる（エンジンの更新のとき以外に出たら、照合を行う）。
*   **自動テスト（`test/FINGERPRINTS.test.js`）:** 規則の命名 `test/<対象>[.<観点>].test.js` の対象を、一覧ファイルの名前 `FINGERPRINTS` とする。
    *   import するのは `node:test`・`node:assert/strict`・`node:crypto`（`createHash`）・`node:fs`（`readdirSync`・`readFileSync`）・`node:path`（`join`）・`node:url`（`fileURLToPath`）だけ。`oz/src/`・`oz/index.js` は import しない（`oz/` のファイルはデータとして読むだけ）。`oz/` のパスは `fileURLToPath(new URL('../oz/', import.meta.url))` で求め、実行時のカレントディレクトリに依存しない。
    *   補助関数（各 JSDoc 付き）: `oz/` 以下のファイルを再帰的に列挙して相対パス（区切り `/`）の配列を返す関数（`readdirSync(..., { withFileTypes: true })` で、ディレクトリは再帰し、通常のファイルだけを集め、最上位の `FINGERPRINTS.txt` を除く）、2つのパスを UTF-8 のバイト列で比べる関数（`Buffer.compare`）、ファイルの中身から 0x0D を取り除いて SHA-256 の16進を返す関数、期待される一覧の全文（上記の形式）を作る関数、一覧ファイルを読んで CR を取り除いた全文を返す関数。
    *   テスト（日本語の名前）:
        1. 一覧の各行が「64文字の小文字の16進＋空白2つ＋パス」の形であること。
        2. 一覧に書かれたパスの集合と、`oz/` の実際のファイル（一覧ファイルを除く）の集合が一致すること（ファイルを足した・消したときに失敗する）。
        3. 一覧の各ファイルの指紋が、実際のファイルの指紋と一致すること（ファイルを変えて一覧を作り直さなかったときに失敗する）。
        4. 一覧の全文が、作り直しのコマンドの出力と同じであること（並び順、区切りの空白2つ、末尾の改行）。
    *   失敗のメッセージには「`oz/` を変えたら一覧を作り直す（開発資料4章の作り直しのコマンド）」の趣旨を含める。
    *   **不一致に気づけることの確認（タスク2で一度行い、元に戻す）:** エンジンのコード（`oz/index.js`・`oz/src/*.js`）には一時的にも触れず、変更してよい `oz/ENGINE_API.md` と一時ファイルだけで食い違いを作る。変更する前の `oz/ENGINE_API.md` を scratchpad に退避し、次の4つを1つずつ行って `node --test` を実行し、結果を記録する。各確認の後に退避したファイルで元に戻す（`git checkout` は使わない）。
        *   変更: `oz/ENGINE_API.md` の末尾に1行足す → 失敗する（テスト3・4）。
        *   追加: `oz/tmp_fingerprint_check.txt` を作る → 失敗する（テスト2・4）。

* **照合を Claude Code に実行させない設計:** 照合のコマンドは `oz/src/` のファイルをリダイレクト（`< "$f"`）で開く。公式ドキュメントでは、入力のリダイレクトの対象は `Read` の規則で確かめられるとあるが、変数で指定した対象がどう扱われるか（拒否・確認・素通り）は書かれていない。そのため照合は発注者が Git Bash で行う設計にした。発注者の手間（Git Bash を開いて1行を貼る）が許容できるかを確認してほしい。
* **防げない経路:** `Read`・`Edit` の deny は、ファイル名を書かずに読むシェルのコマンド、スクリプト、PowerShell のコマンド、`rm`・`mv`・`cp` による書き換えを防がない（公式ドキュメントの記載による）。対策はルールの文面での禁止と、指紋の照合・`git status` による事後の発見であり、事前に完全には防げない。完全に防ぐには sandbox が必要だが、本作業では使わない。
* **`oz/VERSION` の上げ方:** 現在の `oz/VERSION` は `0.1.0` のままで、Phase 02 の `oz/` の変更でも上がっていない。版番号だけでは更新の要否が分からないので、手順書では指紋一覧どうしの比較で確かめる。版番号を上げる時期の規則を決めるかどうかは発注者の判断である（本作業では `oz/VERSION` を変更しない）。
* **一覧の作り直しの運用の周知:** 作り直しの運用は開発資料4章に書く（タスク8）。憲法3章「公開APIとドキュメントの同時更新」には指紋一覧への言及がないが、`oz/` を変えて作り直しを忘れると `node --test` が失敗するので、検証コマンドで気づける。憲法や実装AI・監査AIの定義に明記するかは発注者の判断である（本作業では変更しない）。
* **タスク5の補足:** Step 1 以降の中身は、立ち上げ手順 `_doc/INITIAL_PROJECT_STARTUP.md`（`template-app` のものと同じ内容。REQ 作業手順1）に任せ、手順書には書かず「Step 1 から進める」とだけ書いた。`template-app` のファイル一覧は確認済みで、`index.html`・`oz/`・`js/`・`assets/`・`.claude/settings.json` は無い。そのため3章は「コピーのときに同名の確認は出ないのが正しく、出たらコピー先を間違えている疑いがある」と書いた（監査の指摘で修正）。5章の「照合の時期」に、4章の確認の後を加えた。
* **公式ドキュメントの URL の変化:** REQ が挙げた `https://code.claude.com/docs/en/iam` は、計画立案時点では「Authentication」のページで、permissions の項は `https://code.claude.com/docs/en/permissions` に移っていた。記録は 2章 要件7のとおり。
