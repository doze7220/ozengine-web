## 2. アーキテクチャ設計

### 要件1: 割り込みで止まった音の再開（`oz/src/Sound.js`）

**今の問題:** `Sound` は、入力を受け取り AudioContext が `running` になると、`window` の `pointerdown`・`pointerup`・`keydown`（capture）の登録を解除する。その後にブラウザが AudioContext を止める（iOS の Safari では `state` が `suspended` ではなく `interrupted` になることがある）と、再開する手段がなくなる。

**再開の仕組み（決定）:**

* AudioContext を作るとき（`createContext`）に、その AudioContext の `statechange` イベントに、`Sound.js` の中の関数（例 `onStateChange`）を登録する（`context.addEventListener('statechange', onStateChange)`）。AudioContext はページの DOM ではないので、憲法3章「エンジンのDOM操作の制限」には当たらない。`document` の `visibilitychange` などのページのイベントは使わない。
* `onStateChange` の動作:
  * `context.state === 'running'` のとき: 「一度 `running` になった」ことを記録し（下の `wasRunning`）、今の `removeGestureListenersIfDone()` を呼ぶ（入力を受け取っていれば登録を解除する）。
  * `context.state` が `running` でも `closed` でもないとき（`suspended`・`interrupted`、および将来の値）: 再開用のイベント（`GESTURE_TYPES`）を `window` に capture で登録し直す。同じ関数と同じ capture の `addEventListener` は二重に登録されないので、すでに登録されていても害はない。
  * `closed` のときは何もしない（エンジンは `close` を呼ばない）。
* 登録と解除は、今のトップレベルの `for` 文と `removeGestureListenersIfDone` の中の `for` 文を、2つの小さな関数（例 `addGestureListeners()`・`removeGestureListeners()`）にまとめて使い回す。起動時の登録は今までどおりモジュールの読み込み時に行う。
* 再開用のイベントの処理（`onGesture`）は今のまま: `Escape` の `keydown` は数えない。`inputSeen = true` にし、AudioContext があれば `resume()` を呼ぶ。`resume()` の完了で `removeGestureListenersIfDone()` を呼ぶ。失敗（reject）は握りつぶす（登録は残るので、次の入力でまた試す）。
* **入力なしの再開は試みない（決定）:** エンジンは、入力のイベントの中以外で `resume()` を呼ばない。画面に戻っただけでブラウザが自分で再開した場合は、`statechange` で `running` を検知して登録を解除する（このときは入力なしに鳴り始める）。ブラウザが再開しない場合は、画面に触れる（またはキーを押す）と、そのイベントの中の `resume()` で再開する。
* **一度 `running` になったかの記録（新しいモジュール内の変数 `wasRunning`）:** 次の3か所で `context.state === 'running'` を見たら `true` にする。(1) `createContext` で作った直後、(2) `resume()` の完了時（`removeGestureListenersIfDone` の中でよい）、(3) `onStateChange`。いったん `true` になったら戻さない。

**止まっている間の再生の扱い（決定）:**

* 「止まっている間」とは、`wasRunning` が `true`（一度鳴らせる状態になった）で、`context.state` が `running` でない間をいう。
* `playSe`: 止まっている間は捨てる（`requireSound` の名前の確認と、読み込みに失敗した名前の扱いは今のまま先に行う）。止まった AudioContext に `start()` した音は再開の瞬間にまとめて鳴るため、捨てる。再開のための入力そのものへの反応の中で呼んだ分も、その時点で再開が終わっていなければ捨てられる。
* 最初の入力のあとで、まだ一度も `running` になっていない間（`wasRunning` が `false`。タッチの最初の押下で指を離すまでの間など）は、今までどおり捨てずに `start()` する（21章「タッチの最初の押下」の動作を変えない）。
* `playBgm`・`stopBgm`: 止まっている間も今までどおり受け付ける（曲の切り替え、クロスフェード、停止の予定を行う）。AudioContext の時刻が止まっているので、音とフェードは再開後に、止まった位置から進む。流れていた BGM は、再開すると止まった位置から続きが鳴る。
* `inputSeen` が `false` の間（最初の入力の前）の扱いは今のまま（捨てる）。
* 公開API（`playSe`・`playBgm`・`stopBgm`・音量）の引数・戻り値・エラーは変えない。`Sound.js` の先頭の責務定義は「AudioContext の再開」を「AudioContext の再開（最初の入力と、ブラウザが止めたあとの入力での再開）」のように直す（3行以内）。

**`oz/ENGINE_API.md` 21章の変更（同じタスクで行う）:**

* 「時間」節の「タブを裏に回しても止まらない。」を、「PC のブラウザでは、タブを裏に回しても止まらない。スマートフォンでは、電話の着信、他のアプリへの切り替え、画面のロックなどで、ブラウザが音を止めることがある。土台に戻って画面に触れる（またはキーを押す）と再開する（次の「ブラウザが音を止めたとき」）。」の趣旨に直す。
* 「時間」節の直後に「### ブラウザが音を止めたとき」を足す。書く内容:

  * 名前の確認と `fadeMs` の確認は、止まっている間も行う。

### 要件2: 高解像度の画面への対応（`Screen`・`Layers`・`DebugOverlay`・`Engine`）

**画素数の決め方（`Screen`。決定）:**

* `Screen` は、表示の大きさ（`style.width`・`style.height`）を今までどおり計算したあと、その整数の CSS 画素数に倍率を掛けた値を Canvas の画素数（`canvas.width`・`canvas.height`）にする。
  * 倍率 = `window.devicePixelRatio` が正の有限数ならその値と 2 の小さいほう、そうでなければ（`undefined`・`0`・`NaN` など）1。上限の 2 は `Screen.js` の定数（例 `MAX_PIXEL_RATIO = 2`、JSDoc 付き）にする（エンジンの仕様として持ってよい値。REQ の制約）。
  * 画素数 = `Math.max(1, Math.round(CSS の画素数 × 倍率))`（幅と高さそれぞれ）。表示の大きさが 0 になっても画素数は 1 以上にする。
  * 画素数を代入すると `ctx` の状態と画面が初期化されるので、今の値と違うときだけ代入する（幅と高さを別々に比べる）。
* 今の constructor の `canvas.width = width; canvas.height = height;`（論理解像度の代入）は削除し、`_fit()` の中で画素数を決める。`resize` のたびに `_fit()` が表示の大きさと画素数の両方を合わせる（登録は今のまま1つ）。
* `toLogical` は表示の矩形と論理解像度で換算しているので変えない（画素数に依存しない）。
* `Screen` は `ctx` を持たず、描画も変換の設定もしない。倍率や画素数を返す公開のメソッド・ゲッターは足さない（`Layers` は `ctx.canvas` から画素数を読む）。
* 先頭の責務定義を「論理解像度の保持、縦横比を保った表示サイズの調整、表示サイズと画素密度（`devicePixelRatio`、上限 2）に合わせた Canvas の画素数の調整、画面座標から論理座標への変換」の趣旨に直す（3行以内）。クラスと `_fit` の JSDoc も直す。

**拡大の変換を毎フレーム設定する場所（`Layers`。決定）:**

* 開発資料4章で `Layers` は「消去と、呼び出しごとの save / restore」を担い、毎フレームの描画の入口である。画素数の変更で `ctx` の変換が初期化されても、次のフレームの描画の始めに必ず設定し直せるよう、変換の設定を `Layers.render` の消去と一緒に置く。`GameLoop` は呼び出しの順序だけを担い、変更しない。`Screen` は `ctx` を扱わない。
* **憲法3章「Canvas状態の保護」に従う（発注者決定）:** 拡大の変換は `render` の中だけで有効にし、`render` の外へ漏らさない。`render` の後に描く `DebugOverlay` は、`Layers` が残した変換に頼らず、自分の `save` / `restore` の中で同じ拡大を設定する（下の「`DebugOverlay` の拡大」）。`Layers` と `DebugOverlay` の間に、変換の受け渡しによる暗黙の結合を作らない。
* `Layers` の constructor に論理解像度を足す: `new Layers(names, width, height)`（`Engine.start` が `config.width`・`config.height` を渡す。固定値ではなく起動設定から受け取る値）。
* `Layers.render(ctx, scenes, time)` の全体を次の順にする:
  1. `ctx.save()` で描画前の状態を保存する。
  2. `ctx.setTransform(1, 0, 0, 1, 0, 0)` で変換を初期化する。
  3. `ctx.clearRect(0, 0, ctx.canvas.width, ctx.canvas.height)` で画素数の全体を消去する（ここでの `ctx.canvas.width` は画素数として正しい）。
  4. `ctx.setTransform(ctx.canvas.width / width, 0, 0, ctx.canvas.height / height, 0, 0)` で論理座標への拡大を設定する（縦と横の比は別々に求める。表示の大きさの整数への切り捨てで、縦横の比がわずかに違うことがあるため）。
  5. 今までどおり、レイヤーごとに `save` → `draw` → `restore` を呼ぶ。
  6. `ctx.restore()` で 1 の状態に戻す（変換を外へ漏らさない）。
* `render` が `save` / `restore` で閉じること（`render` の後の `ctx` に拡大の変換が残らないこと）を `render` の JSDoc に書く。
* 先頭の責務定義を「レイヤー順の走査、画面の消去と論理座標への拡大の設定、呼び出しごとの save / restore」の趣旨に直す（3行以内）。constructor の JSDoc に `width`・`height` を足す。

**`DebugOverlay` の拡大（決定）:**

* `DebugOverlay` の constructor に論理解像度を足す: `new DebugOverlay(width, height)`（`Layers` と同じく、`Engine.start` が `config.width`・`config.height` を渡す。固定値ではなく起動設定から受け取る値）。フィールドに保持し、JSDoc を書く。
* `draw(ctx)` は、すでにある `ctx.save()` の直後に `ctx.setTransform(ctx.canvas.width / width, 0, 0, ctx.canvas.height / height, 0, 0)` で論理座標への拡大を設定し、その後は今までどおり描いて `ctx.restore()` で閉じる。`setTransform`（絶対の設定）を使うので、呼ばれる前の `ctx` の変換に依存しない。`(8, 8)` の位置と `16px` の文字は今までと同じ論理座標で描かれる。
* FPS の計算（`update`）は変えない。`GameLoop` の呼び出し（`overlay.draw(ctx)`）も変えない。
* 先頭の責務定義を「FPS の計算と、論理座標での左上への表示（拡大の設定を含む）」の趣旨に直す（3行以内。時間を引数でのみ受け取り、ゲーム状態を参照しないことは残す）。constructor と `draw` の JSDoc を直す。
* 拡大の比の計算（画素数 ÷ 論理解像度）は `Layers` と `DebugOverlay` の2か所に同じ式で書く（共通の関数やモジュールは作らない。新しい依存を作らないため）。

* `Engine.start` の変更は `new Layers(config.layers, config.width, config.height)` と `new DebugOverlay(config.width, config.height)`（`config.debug` が有効なときの生成）の2か所だけ。`Engine` の責務定義は変えない。

**PC での動作:** 論理座標、`onPointer` の座標、画面のボタン・バーチャルパッドの当たり判定は変わらない（`toLogical` は変えない）。描画の位置と大きさは論理座標のまま拡大されるので変わらない。画素数が表示に合うので、縮小表示の PC でも拡大表示の PC でも、線と文字は表示の画素でくっきり描かれる（意図した変化）。

**`oz/ENGINE_API.md` の変更（同じタスクで行う）:**

### 要件3: boot 画面（`js/scenes/BootScene.js`。決定）

* **新しいファイル `js/scenes/BootScene.js`**（ファイル全体の目印は付けない）。クラス名 `BootScene`（`Scene` を継承）。先頭行の責務定義は「最初の入力を受ける画面（黒い背景と『TAP SCREEN』の表示）と、入力で次の画面へ進むこと。」の趣旨（3行以内）。
* **constructor の引数（決定）:** 1つのオブジェクト `{ screen, layer, next }`（`@typedef` で JSDoc を書く）。
  * `screen`: `{ width, height }`（解像度。背景を塗る範囲と文字の中央の位置に使う）。
  * `layer`: 描くレイヤー名（文字列）。レイヤー名は `js/main.js` が決めるので、固定値を持たずに受け取る。
  * `next`: 次の画面のシーンを作る関数（引数なし、`Scene` のインスタンスを返す）。進むときに呼んで、`Engine.changeScene(next())` する。シーンを積むたびに新しいインスタンスを作る（ENGINE_API 5章）ため、インスタンスではなく関数で受け取る。
* **描画:** `draw(ctx, layer)` で、`layer` が受け取ったレイヤー名のときだけ、`ctx.save()` → 黒（`#000000`）で `screen` の全体を `fillRect` → 白い文字「TAP SCREEN」を画面の中央に描く（`textAlign: 'center'`、`textBaseline: 'middle'`）→ `ctx.restore()`。文字・フォント（例 `'48px sans-serif'`）・色はファイルの先頭の定数（JSDoc 付き）にし、新規プロジェクトで書き換えやすくする。`js/scenes/uiText.js`（目印付き）は import しない。描画の中で状態を変えない。
* **進め方:**
  * `onPointer(pointer)`: `'down'` で「このシーンで押した」ことを記録する（フィールド、JSDoc 付き）。`'up'` のとき、このシーンで押していれば `Engine.changeScene(this.next())` する（前の画面で押して、この画面で離した `'up'` では進まない）。
  * `onKeyDown(code)`: `code === 'Escape'` なら何もしない（エンジンが最初の入力に数えないため）。それ以外は `Engine.changeScene(this.next())` する。
  * バーチャルパッドは登録しない（表示も反応もしない）。画面のボタンも登録しない。
* **押した瞬間の SE（要件4。目印付き）:** `onPointer` の `'down'` と、`onKeyDown`（`Escape` 以外、進む前）で、土台の既存の SE（`Sound.playSe('se')`）を1回鳴らす。この部分は `/* ozengine sample: begin */`・`/* ozengine sample: end */` で囲む。
  * `Sound` の import も目印の範囲に入れる（例: 目印なしの `import { Engine, Scene } from 'oz';` の下に、目印で囲んだ `import { Sound } from 'oz';` と SE の名前の定数 `BOOT_SE = 'se'` を置く）。
  * 目印の行（begin と end）は、それぞれ単独の行にする（手順書 6-2 の `sed '/begin/,/end/d'` は、同じ行に begin と end があると範囲が閉じないため）。メソッドの中の範囲も、消したあとに文法が壊れない位置（文の単位）に置く。
* **次の画面の指定（決定）:** `js/main.js` から渡す。
  * 目印の外（新規プロジェクトに残る部分）: `import { BootScene } from './scenes/BootScene.js';` を置き、`config.scene` を `new BootScene({ screen, layer: 'main', next: () => new Scene() })` にする（`screen` は `{ width: config.width, height: config.height }`。`layer` は目印の外の `config.layers` の `'main'`）。新規プロジェクトでは `next` を自分の最初のシーンを作る関数に書き換える旨を JSDoc（またはコメント）に書く。
  * 目印の中（土台の見本）: `config.layers` を今の5つにし、`config.scene` を `new LoadScene(screen, () => new BootScene({ screen, layer: 'ui', next: () => new TitleScene(screen) }))` にする。`LoadScene`・`TitleScene` の import は目印の中に置く。
  * 目印の外のコードは、目印の付いたファイル（`LoadScene`・`TitleScene`・`uiText.js` など）を import しない。
* **ロードとの順序（決定）: ロード → boot → タイトル。** boot 画面で SE（`se`）を鳴らすには、先に `Assets.load` が終わっている必要があるため。`LoadScene` は次の画面を作る関数を受け取り、ロード完了後に `Engine.changeScene(next())` する（`LoadScene` は `TitleScene` を import しなくなる。`BootScene` も import しない）。
* **タイトルの BGM（決定）:** `TitleScene.init` でボタンの登録に続けて `playBgm()` を呼び、入力を待たずに BGM を流す（boot 画面で最初の入力が済んでいるため）。入力への反応の中で `playBgm` を呼ぶ処理（`onKeyDown` の上書きと、`startPlay` の中の `playBgm()`）は削除する（`onKeyDown` の上書きを消すと、`FlightScene.onKeyDown` のミュートキーがそのまま効く）。メニューの「タイトルに戻る」でタイトルに入ったときも `init` で `playBgm` を呼ぶが、同じ曲なので何も起きない（ENGINE_API 21章）。
* **目印を消した後:** `js/` に `main.js`・`scenes/BootScene.js`・`scenes/MenuScene.js`・`ui/virtualPadConfig.js`・`ui/virtualPadView.js` の5ファイルが残る。起動すると boot 画面（黒い背景と「TAP SCREEN」）が出て、押す（離す）かキーを押すと空のシーンへ進む（画面は黒いまま）。SE の部分は消えているので、音の素材が無くてもエラーにならない。これをタスクの中で、スクラッチパッドに `js/` をコピーして手順書 6-2 のコマンドで目印を消し、構文チェックと import の確認を行って確かめる（リポジトリのファイルは変えない）。

## 5. 懸念事項・要確認ポイント
* **テストプレイで確かめること（発注者。GitHub Pages の `/ozengine-web/` の下で行う）:**
  * **割り込みのあとの音の再開（iPhone の Safari）:** タイトルで BGM が流れている状態で、(1) 電話の着信（または FaceTime など）、(2) 他のアプリへの切り替えと戻り、(3) 画面のロックと解除、のそれぞれのあと、土台に戻って画面に触れると BGM が止まった位置から戻るか。その後のプレイでブーストの SE が鳴るか。戻っただけで（触れる前に）鳴り始めることがあるか（ブラウザが自分で再開する場合。どちらでも仕様の範囲）。
  * 再開のために触れた1回目の操作の SE は、鳴らないことがある（仕様。2章 要件1）。気になるほどかを確かめる。
  * iOS の Safari には、割り込みのあと AudioContext が `running` に戻っても音が出ない不具合が報告されていることがある。その場合は AudioContext の作り直しなど別の対応が必要になるので、症状（どの操作のあとか、ページの再読み込みで直るか）を報告してほしい（本計画では対応しない）。
  * **高解像度:** iPhone で、タイトルの文字、ボタンの枠、機体と星の線が、今までよりくっきり見えるか。バーチャルパッドの既定の画像（SVG）がぼやけていないか（ぼやける場合も、本作業では画像の形式を変えない。結果を報告してほしい）。
  * **PC での動作が変わらないこと:** 座標（ボタン・メニューの押せる位置）、キー操作、描画の位置と大きさが今までと同じか。大きなモニターでは線と文字がくっきりするのは意図した変化。ブラウザの拡大縮小（Ctrl + / -）をしても表示が崩れないか。`?debug` を付けたときの FPS の表示が左上の今までの位置と大きさで出るか。
  * **重さ:** 画素密度の高い大きなモニター（倍率 2）の PC や、古いスマートフォンで、FPS が落ちていないか（画素数が増えるため。`?debug` で確かめられる）。
  * **アドレスバーの出入り（iPhone）:** スクロールなどでアドレスバーの大きさが変わり、表示の大きさが変わったときに、画面がちらつかないか、位置がずれないか。
  * **画素密度の違うモニターの間でウィンドウを動かしたとき（PC）:** ブラウザが `resize` を出さない場合、ウィンドウの大きさを変えるまで画素数が前のモニターのままになる（少しぼやける、または重い）。気になるかを確かめる（本計画では `resize` 以外の検知はしない）。
  * **boot 画面:** 起動すると、ロード中の表示のあと、黒い画面に「TAP SCREEN」が出るか。タップ（指を離したとき）、クリック（ボタンを離したとき）、キー（`Escape` 以外を押したとき）でタイトルへ進むか。`Escape` では進まないか。boot 画面にバーチャルパッドが出ないか。
  * **boot 画面の SE が鳴る時期（要件4。タスク7の入力）:** ロード中は画面に触れず、「TAP SCREEN」が出てから初めて触れる（ロード中に触れると最初の入力が済んでしまい、確認にならない）。iPhone の Safari を含む実機で、SE が押した瞬間に鳴るか、指を離したときに鳴るかを、端末・ブラウザごとに記録する。ミュートを保存した状態（土台のミュートの設定）と、iPhone の消音スイッチが入った状態では鳴らないので、確認の前に両方を解除しておく。
  * **タイトルですぐ BGM が流れること:** boot 画面から進むと、タイトルで入力を待たずに BGM がフェードインするか。プレイ中のメニューの「タイトルに戻る」でタイトルに戻っても、BGM が途切れず続くか。
  * 同じ機会に、Phase 03-02 のテストプレイ（発注者の判断で後回しにしたもの）の確認項目（`./_log/res/261110_1013_RES_Phase03-02_マルチタッチとバーチャルコントローラー.md` 5章）も行う。
* **タスク7の実行時期:** タスク7は、上の「boot 画面の SE が鳴る時期」の結果を受け取ってから、結果を添えて実行の指示を出す。タスク8（開発資料への反映）はタスク7の後に行う。
* **`Layers` の変換と憲法3章「Canvas状態の保護」（解消）:** 監査の指摘と発注者の決定により、`Layers.render` は全体を `save` / `restore` で閉じて変換を外へ漏らさず、`DebugOverlay` は自分の `save` / `restore` の中で拡大を設定する形にした（2章 要件2）。`Layers` が残した変換に `DebugOverlay` が頼る結合はなくなった。拡大の比の式が `Layers` と `DebugOverlay` の2か所に重複するが、新しい依存を作らないための扱いとする。
