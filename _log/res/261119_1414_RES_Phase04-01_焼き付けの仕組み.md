# RES: 作業計画・作業レポート Phase 04-01 : 焼き付けの仕組み
* 参照元REQ: `./_log/req/261119_1414_Phase04-01_焼き付けの仕組み.md`

## 1. 作業目的
`draw(ctx)` で描けるもの（スプライトJS、図形、文字）を、前もってページに追加しない Canvas に焼き付けておき、毎フレームはその画像を貼るだけにする仕組み「キャンバスキャッシュ」（公開オブジェクト `CanvasCache`）をエンジンに入れる。焼き付けた結果は `draw(ctx)` を持つオブジェクト（「焼き付け」）として返し、呼ぶ側はスプライトJSと同じ書き方のまま差し替えられるようにする。多数のスプライトを同時に描くゲームで、毎フレームのベクターの描画の負荷を減らすためのものである。

本作業はエンジン（`oz/`）だけを変える。土台（`js/`・`assets/`・`index.html`）は変えない。

## 2. アーキテクチャ設計

### 全体の形
* 処理はすべて新しいモジュール `oz/src/CanvasCache.js` に置く。`CanvasCache.js` は他のエンジンモジュールを import しない（`js/`・`assets/` も import しない）。
* `CanvasCache.js` の名前付き export は次の5つ。`oz/index.js` から再exportするのは `CanvasCache` だけ。

  | export | 使う者 | 内容 |
  | --- | --- | --- |
  | `CanvasCache` | 利用側（`oz/index.js` から公開） | `create(source, options)` だけを持つオブジェクト |
  | `setPixelRatioSource(getRatioX, getRatioY)` | `Engine` だけ | 画素の倍率の求め方（関数2つ）を受け取ってモジュールの中に保持する |
  | `validateCreateArgs(source, options)` | 内部とテスト | 引数の検証と正規化（Canvas を使わない） |
  | `computeBakeLayout(bounds, scale, ratioX, ratioY)` | 内部とテスト | 焼き付ける画像の画素数・余白・描く位置の計算（Canvas を使わない） |
  | `snapToDevicePixels(matrix, layout)` | 内部とテスト | 画素合わせで描けるかの判定と、描く画素の位置の計算（Canvas を使わない） |

  `validateCreateArgs`・`computeBakeLayout`・`snapToDevicePixels` は `oz/src/VirtualPad.js` の `validatePadLayout` と同じ扱い（テストのための名前付き export、非公開）。
* 焼き付けのオブジェクトは、`CanvasCache.js` の中の export しないクラス `Bake` のインスタンスとする。公開メソッドは `draw(ctx)`・`refresh()`・`dispose()` の3つだけで、状態はすべてプライベートフィールド（`#`）に持つ（倍率などを外から読めないようにする）。
* 焼き付けの一覧（レジストリ）は持たない（下の要件3の「焼き直す時期」を参照）。モジュールの状態は、`setPixelRatioSource` で受け取った関数2つ（起動前は `null`）だけで、`window` には何も足さない。

### 要件1: 公開API
* `CanvasCache.create(source, options)` → `Bake` のインスタンスを返す。
  * `source`: `typeof source === 'function'` なら `source(ctx)` として呼ぶ。そうでなく、`draw` が関数のオブジェクトなら `source.draw(ctx)` として呼ぶ（`this` は `source`）。エンジンは呼ぶだけで、`source` のほかのキー（`bounds` を含む）を読まない。
  * `options.bounds`: `create` のときに4つの値を新しいオブジェクトへ写して保持する（後から呼ぶ側が元のオブジェクトを書き換えても、焼き直しの範囲は変わらない）。
  * `options.scale`: `undefined` のときだけ既定値 `1`。`create` のときに決まり、変えられない。
  * `options` のほかの項目は読まない（エラーにもしない）。
* 上記と3つのメソッド以外の公開APIは作らない（倍率の取得、範囲の取得などは作らない）。

### 要件2: 描かれる位置と大きさ（画素の計算）
記号: `s` = `scale`、`rx`・`ry` = 画素の倍率（Canvas の画素数 ÷ 論理解像度。x と y を別に持つ。`Layers` が設定する拡大の変換 `canvas.width / width`・`canvas.height / height` と同じ値）。
* **焼き付けの密度:** `densityX = s × rx`、`densityY = s × ry`（`source` の座標の1単位が、焼き付けた画像の何画素に当たるか）。
* **余白:** `BAKE_MARGIN = 2`（焼き付けた画像の画素で、四方に取る。モジュール内の定数で export しない）。アンチエイリアスのにじみは縁から1画素程度なので、丸めを含めて2画素で足りる量とする。
* **画素数と原点（`computeBakeLayout`）:**
  * `left = Math.floor(minX × densityX) − BAKE_MARGIN`、`right = Math.ceil(maxX × densityX) + BAKE_MARGIN`（`top`・`bottom` も同様に Y で求める）。
  * `pixelWidth = right − left`、`pixelHeight = bottom − top`（どちらも整数で 1 以上）。
  * `originX = −left`、`originY = −top`（`source` の原点が焼き付けた画像のどの画素の角に当たるか。整数にすることで、`source` の原点が画素の境目に揃う）。
  * 描く位置（論理座標。呼ぶ側の `ctx` の上で、`scale` を掛けた後の大きさ）: `destX = left / rx`、`destY = top / ry`、`destWidth = pixelWidth / rx`、`destHeight = pixelHeight / ry`。
  * 戻り値: `{ pixelWidth, pixelHeight, originX, originY, densityX, densityY, destX, destY, destWidth, destHeight, ratioX, ratioY }`（`ratioX`・`ratioY` は計算に使った `rx`・`ry`。焼き直しの判定に使う）。
  * これにより、画像の画素 p は `source` の座標 `(p − originX) / densityX` に、論理座標では `(p − originX) / densityX × s` に当たり、「`ctx.scale(s, s)` → `source` を描く」と同じ位置・同じ大きさになる。
* **焼き付けるとき:** `ctx.setTransform(densityX, 0, 0, densityY, originX, originY)` を設定してから `source` を呼ぶ。
* **描くとき（`Bake#draw`）:**
  1. 画素合わせの判定（`snapToDevicePixels`）: `ctx.getTransform` が関数なら `matrix = ctx.getTransform()` を取り、`|b| ≤ ε`・`|c| ≤ ε`・`|a − layout.ratioX| ≤ ε`・`|d − layout.ratioY| ≤ ε`（`ε = 1e-6`。モジュール内の定数）のとき、呼ぶ側は拡大・縮小・回転を掛けていない（`Layers` の拡大と平行移動だけ）と判断し、`{ x: Math.round(e + a × destX), y: Math.round(f + d × destY) }`（画面の画素の位置）を返す。当てはまらなければ `null`。`a`・`d` が負（反転）や回転のときも `null`。
  2. 判定が `{x, y}` なら、`ctx.save()` → `ctx.setTransform(1, 0, 0, 1, 0, 0)` → `ctx.drawImage(canvas, x, y)`（拡大なし、1画素 = 1画素）→ `ctx.restore()`。位置を画面の画素に丸めるので、補間によるぼやけが出ない。
  3. `null` なら、`ctx.drawImage(canvas, destX, destY, destWidth, destHeight)` だけを呼ぶ（`drawImage` は `ctx` の状態を変えないので `save`/`restore` は不要）。回転・拡大のときはブラウザの補間で描かれる。
  * `imageSmoothingEnabled` は設定しない（補間を切らない。呼ぶ側が切っていればそのまま）。
  * 呼ぶ側の `ctx` の状態は、どちらの経路でも元のまま終わる。
* **`bounds` の外:** 余白を超える部分は画像の外で切れる。OZ Vector Editor の `bounds` は線の太さの半分を含む。手で範囲を書く場合は呼ぶ側が線の太さ（や影など）を含める。

### 要件3: 焼き付ける解像度と自動の焼き直し
* **倍率の知り方:** `Engine.start` が、`Screen` を作った後・最初のシーンを積む前に、`setPixelRatioSource(() => config.canvas.width / config.width, () => config.canvas.height / config.height)` を呼ぶ。`CanvasCache` は渡された関数を呼んで今の倍率を読むだけで、canvas 要素も `Screen` も知らない。`Screen` は変更しない（`Screen` から通知を受けないので、`Screen` が `CanvasCache` を import することもない）。依存の向きは `Engine → CanvasCache` の一方向。
* **倍率は利用側に公開しない:** `setPixelRatioSource` は `oz/index.js` から再exportしない。`Bake` は倍率を外から読めるプロパティを持たない。
* **焼き直す時期（決定）: 焼き付けを描くとき。** `Bake#draw(ctx)` の始めに、今の倍率（`getRatioX()`・`getRatioY()`）を焼き付けたときの `layout.ratioX`・`layout.ratioY` と `!==` で比べ、違えば（または前回の焼き付けが失敗して `layout` が無ければ）、その場で焼き直してから描く。
  * ウィンドウの大きさ・画面の向き・`devicePixelRatio` のどれで変わっても、`Screen` が canvas の画素数を変えた後の最初の描画で必ず検知できる（`resize` イベントの順序に頼らない）。古い解像度の絵が描かれることはない。
  * 描かれていない焼き付けは、次に描かれるときに焼き直す。手放していない焼き付けは、どれも描くときには必ず今の倍率で焼かれているので、「手放していないすべての焼き付けを自動で焼き直す」を満たす。手放した焼き付けは描けない（エラー）ので、焼き直しの対象から外れる。このため一覧（レジストリ）は不要とする。
  * 焼き直しても `Bake` のインスタンスと Canvas は同じものを使い続ける（呼ぶ側は同じオブジェクトのまま）。
* **焼き付けの手順（`Bake` の内部メソッド `#bake()`。`create`・`refresh`・自動の焼き直しで共通）:**
  1. `layout = computeBakeLayout(bounds, scale, getRatioX(), getRatioY())`。
  2. 保持している `layout` を `null` にする（途中で失敗したときに、次の描画で焼き直させるため）。
  3. `canvas.width = pixelWidth`、`canvas.height = pixelHeight` を毎回代入する（同じ値でも代入する。代入で画像が消え、`ctx` の状態が初期化される）。
  4. `ctx.save()` → `try { ctx.setTransform(...); source を呼ぶ } finally { ctx.restore() }`。
  5. 成功したときだけ、保持する `layout` を新しい値にする。
* 焼き付け先の Canvas は `document.createElement('canvas')` で作り、ページに追加しない（`OffscreenCanvas` は使わない。iOS の Safari で 2D の `OffscreenCanvas` が使えるのは 16.4 以降で、古い端末を切り捨てないため）。1つの `Bake` につき1枚を `create` のときに作る。`getContext('2d')` が `null` なら `[oz] CanvasCache.create: 焼き付け用の Canvas を用意できません` を投げる。
* `scale` と大きく違う倍率で描いたときのぼやけ・線の淡さには対処しない（要件8で注意として書く）。

### 要件4: 明示の焼き直し
* `Bake#refresh()`: 手放していなければ `#bake()` を呼ぶ（その時点の `source` を呼び直す）。同じオブジェクトをそのまま使える。

### 要件5: 手放す
* `Bake#dispose()`: 手放し済みなら何もしない。そうでなければ手放し済みの印を付け、`canvas.width = 0`・`canvas.height = 0` を代入して画像のメモリを早く返し（iOS の Safari で Canvas のメモリが残りにくくするため）、Canvas・`ctx`・`layout`・`source` への参照を `null` にする。
* 手放した後の `draw`・`refresh` は次のエラーを投げる。
  * `[oz] 焼き付けの draw: dispose の後には使えません`
  * `[oz] 焼き付けの refresh: dispose の後には使えません`

### 要件6: 作れる時期
* `create` の始めに、`setPixelRatioSource` が呼ばれていなければ（関数が `null` なら）`[oz] CanvasCache.create: Engine.start の前には使えません` を投げる。この判定を引数の検証より先に行う（`Engine.addVirtualPad` などと同じ順）。
* 焼き付けは `create` の中ですぐ行う（`new Bake(...)` の中で `#bake()` を呼ぶ）。

### 要件7: 引数が正しくないとき（`validateCreateArgs`）
上から順に調べ、最初に当たったものを投げる（`Error`）。戻り値は正規化した `{ bounds: { minX, minY, maxX, maxY }（写し）, scale }`。

| 条件 | 文面 |
| --- | --- |
| `source` が関数でも、`draw` が関数のオブジェクトでもない（無い・`null` を含む） | `[oz] CanvasCache.create: source (draw(ctx) を持つオブジェクト、または ctx を受け取る関数) が渡されていません` |
| `options` が `null` でないオブジェクトでない（無いを含む） | `[oz] CanvasCache.create: options (設定オブジェクト) が渡されていません` |
| `bounds` が `null` でないオブジェクトでない（無い・`null` を含む） | `[oz] CanvasCache.create: bounds (焼き付ける範囲 { minX, minY, maxX, maxY }) が渡されていません` |
| 4つの値のどれかが有限の数値でない（`typeof` が `number` でない、`NaN`、`±Infinity`） | `[oz] CanvasCache.create: bounds の minX / minY / maxX / maxY は有限の数値で指定してください` |
| `maxX <= minX` または `maxY <= minY` | `[oz] CanvasCache.create: bounds の範囲が空です（maxX は minX より、maxY は minY より大きくしてください）` |
| `scale` が `undefined` でなく、正の有限数でない（`null`・0 以下・`NaN`・`Infinity`・数値でない） | `[oz] CanvasCache.create: scale は正の有限数で指定してください` |

* **`source` が例外を投げたとき（決定）:** 包み直さず、そのまま投げる。`create` の途中なら焼き付けは返らない。`refresh()`・自動の焼き直し（`draw` の中）の途中なら、例外はその呼び出しから投げられ、その焼き付けは次に描くときにもう一度焼き直す（`layout` を `null` にしてあるため）。フレーム処理の中で起きればループが止まる（ENGINE_API 15章と同じ）。
* **焼き付け用の `ctx` の状態（決定）:** 焼き付けのたびに Canvas の大きさを代入して状態を初期化し、さらに `save`/`try`/`finally`/`restore` で囲む。`source` が `ctx` の状態を戻さずに終わっても、例外を投げても、次の焼き付けに持ち越さない。呼ぶ側の `ctx`（`draw` に渡すもの）の状態は変えない。
* **Canvas の大きさ・メモリの上限（検討の結果、対処しない）:** 上限はブラウザと端末で違い（iOS の Safari は1枚の面積と全体のメモリに上限がある）、エンジンで正しい値を持てないため、縮めて焼く・エラーにする、のどちらもしない。上の `getContext('2d')` が `null` のときのエラーだけを持つ。5章の懸念事項に挙げ、ENGINE_API に「大きな範囲と大きな `scale` は避ける」注意を書く。

                *   `### refresh()`: その時点の描く処理を呼び直して焼き直す。色や演出を切り替えた後に呼ぶ。

## 5. 懸念事項・要確認ポイント

### 懸念事項
* **Canvas の大きさ・メモリの上限（対処しない）:** iPhone の Safari などには、Canvas 1枚の面積と、全体の Canvas のメモリに上限がある。大きな `bounds` と大きな `scale`（さらに画素の倍率は最大 2）を組み合わせたり、焼き付けを大量に持ち続けたりすると、上限を超えて絵が出ない・`getContext` が `null` になることがある。エンジンは上限の値を持たず、縮めて焼く・事前にエラーにする、のどちらもしない（`getContext('2d')` が `null` のときのエラーと、`dispose` で画素数を 0 にしてメモリを返すことだけを行う）。ENGINE_API に注意として書く。実際のゲームで問題になったら、上限の扱いを別の作業で決める。
* **尖った角の線のはみ出し:** OZ Vector Editor の `bounds` は線の太さの半分だけを含むが、書き出しの `draw` は `lineJoin = 'miter'`・`miterLimit = 10` で描くため、鋭い角の線は `bounds` より外へ出ることがある。その部分は焼き付けで切れる（余白 2 画素を超える分）。土台の機体（`ship.js`）は線を描かない（`strokeColor: null`）ので影響しない。気になる場合はエディタ側の `bounds` の求め方の問題として扱う。
* **画素合わせによる動きの段差:** 拡大・縮小・回転を掛けずに描くときは、位置を画面の画素に丸めるので、ゆっくり動く物は画面の1画素（論理座標では `1 / 画素の倍率`）ずつ段々に動く。直接描いたときの「画素の間の位置」のなめらかさは失われる。くっきり描くこと（要件2）を優先した。回転を掛けたときは丸めず、補間で描く（この場合は直接描いたときより少し柔らかく見えることがある）。
* **自動の焼き直しの時期と負荷:** 倍率が変わった後の最初の描画で、描かれる焼き付けがまとめて焼き直されるため、そのフレームだけ重くなる。ウィンドウの大きさを手で変えている間は、ほぼ毎フレーム倍率が変わり、毎フレーム焼き直しが起きる。端末の回転のような一度きりの変化では問題にならない想定。
* **画素の倍率の比較:** `Engine` が渡す関数と `Layers` の拡大の変換は同じ式（`canvas.width / width`）なので、画素合わせの判定（`|a − ratioX| ≤ 1e-6`）は通常一致する。式を片方だけ変えると画素合わせが働かなくなる（描けはするが補間になる）。
* **`source` の扱いの順:** `draw` を持つ関数（関数に `draw` プロパティがあるもの）は関数として呼ぶ。通常のスプライトJSやつなぎのスプライトはオブジェクトなので影響しない。
* **`options` の知らない項目:** 綴りの誤り（`scal` など）はエラーにせず無視する（REQ が求めるエラーに含まれないため）。
* **ENGINE_API 25章の例のコード:** 実機では動かしていない（文面だけ）。手で範囲を書く例の文字は `font` を指定していないので、既定のフォントで描かれる。
* **文書の範囲外の記載:** 公開オブジェクトの数（「5つ」）を書いた文書が `oz/ENGINE_API.md` 以外（`_doc/` の手順書など）にあっても、本作業の変更対象外なので直さない。必要なら別の作業で確認する。

### 目視確認推奨箇所（後の作業「土台を焼き付けで描く」で見るべき点）
* 直接描いたときと、位置・大きさが一致すること（重ねて見比べる、または切り替えて見比べる）。
* 回転していない状態で、直接描いたときよりぼやけていないこと（縁がくっきりしていること）。
* 回転して描いたときに、ギザギザが目立たないこと、ぼやけすぎないこと。
* ウィンドウの大きさを変えたとき、スマートフォンの向きを変えたとき、ブラウザの拡大率を変えたときに、焼き直されてぼやけないこと（古い粗い絵が残らないこと）。
* 絵の縁（特に `bounds` に接する線や塗りの端）が欠けていないこと。
* ゆっくり動く物の動きの段差（上の懸念事項「画素合わせによる動きの段差」）が気にならないこと。
* 多数を描いたときに、直接描くより軽くなっていること。
