# RES: 作業計画・作業レポート Phase 04-02 : ゲームの土台での利用と資料の仕上げ
* 参照元REQ: `./_log/req/261119_1635_Phase04-02_ゲームの土台での利用と資料の仕上げ.md`

## 1. 作業目的
エンジンに入ったキャンバスキャッシュ（`oz/ENGINE_API.md` 25章の `CanvasCache`）を使って、ゲームの土台の機体（`assets/sprites/ship.js`）を、タイトルとプレイの両方で焼き付けた絵で描くように変える。テストプレイで「直接描く」と「焼き付けで描く」を見比べられるよう、一時的な切り替え（メニューの項目と PC のキー）を足し、発注者の OK の後に消す。あわせて、土台に組み込んだ結果に照らして `oz/ENGINE_API.md` を仕上げ、新規プロジェクトの手順書（`_doc/newgame/`）に直すところが無いかを確かめ、新しいゲームがキャンバスキャッシュを使い始められる状態に資料をそろえる。

本作業ではエンジンの処理（`oz/src/`・`oz/index.js`・`oz/VERSION`）は変えない。`oz/` の中で変えるのは `oz/ENGINE_API.md` と、その作り直しの `oz/FINGERPRINTS.txt` だけである。

## 2. アーキテクチャ設計

### 要件1: 土台の機体を焼き付けで描く
**今のシーンの `init`・`destroy` の持ち方（確かめた結果）:**
* `FlightScene`（`js/scenes/FlightScene.js`）は `init`・`destroy` を持たない（基底の `Scene` の何もしない `init`・`destroy` のまま）。
* `TitleScene` は `init()` を上書きしている（スタートボタンの登録と BGM の開始）。`super.init()` は呼んでいない。`destroy` は持たない。
* `PlayScene` は `init()` を上書きしている（バーチャルパッドとメニューを開くボタンの登録）。`super.init()` は呼んでいない。`destroy` は持たない。
* `js/` のどこにも `destroy` は無い。
* シーンの切り替え: タイトル → プレイは `TitleScene.startPlay` の `Engine.changeScene(new PlayScene(...))`、プレイ → タイトルはメニューの「タイトルに戻る」の `backToTitle`（`Engine.changeScene(new TitleScene(...))`）。どちらも毎回新しいインスタンスを作る。`changeScene` は最前面から順に全シーンの `destroy()` を呼んでから新しいシーンの `init()` を呼ぶ（ENGINE_API 6章）。メニューは `pushScene`／`popScene` なので、メニューを開閉してもプレイのシーンの `init`・`destroy` は呼ばれない。

**どこで作ってどこで手放すか（決定）:**
* 機体はタイトルとプレイの共通の処理なので、焼き付けは基底の `FlightScene` が持つ。シーンのインスタンスごとに1つ持つ（モジュールの中で共有しない）。
  * `FlightScene` の constructor で `this.shipImage = null`（JSDoc 付き）を置く。
  * `FlightScene` に `init()` を新しく書き、`this.shipImage = CanvasCache.create(shipSprite, { bounds: shipSprite.bounds })` で作る。範囲は `ship.js` の `bounds` をそのまま渡す。`scale` は書かない（既定の `1` = 今の表示の大きさ。ENGINE_API 25章の使い方の例と同じ書き方）。
  * `FlightScene` に `destroy()` を新しく書き、`this.shipImage.dispose()` を呼ぶ。
  * `TitleScene.init` と `PlayScene.init` の先頭で `super.init()` を呼ぶ（呼ばないと焼き付けが作られず、`draw` で `this.shipImage` が `null` のまま使われてエラーになる）。
  * `TitleScene`・`PlayScene` には `destroy` を書かない（`FlightScene.destroy` がそのまま使われる）。将来、派生クラスに `destroy` を書く場合は `super.destroy()` を呼ぶことを、`FlightScene.destroy` の JSDoc に書いておく。
* 手放した焼き付けを描かないこと: `changeScene` で外れたシーンには `draw` が呼ばれない（スタックに無いため）。新しいシーンは自分の `init` で新しい焼き付けを作る。メニューを積んでいる間はプレイのシーンはスタックに残り、`destroy` されないので、焼き付けも生きたまま描かれる。よって、タイトル ⇔ プレイを何度行き来しても、手放した焼き付けを描くことはない。
* 描き方: `FlightScene.drawShip` の `shipSprite.draw(ctx)` を `this.shipImage.draw(ctx)` に替える。`ctx.save()` → `translate`（カメラ + 機体の位置）→ `rotate`（機体の角度）→ 描く → `ctx.restore()` の形と位置・回転の付け方は今のまま変えない。
* 焼き付けを作る・手放すのは `init`・`destroy` の中だけで、`draw`・`update` の中では行わない（憲法3章「ロジックと描画の分離」）。焼き直しはエンジンが焼き付けの `draw` の中で自動で行う（ENGINE_API 25章「自動の焼き直し」。利用側の状態は変えない）。
* 星・トレイル・風・文字の描画は変えない。`js/entities/Ship.js` には触れない（描画を持ち込まない）。`assets/sprites/ship.js` は手で編集しない（`bounds` を読むだけ。ENGINE_API 23章で読んでよいとされている）。
* 参照する資料: `js/` を実装するタスクでは `oz/src/` を読まず、`oz/ENGINE_API.md`（主に 5章・6章・23章・25章）だけを参照する。25章で分からないこと、例のとおりに書いて動かないことがあれば、5章「懸念事項」に不足として記録し、要件4のタスクで直す。

**補足（画素合わせ）:** 機体は常に画面の中央に描かれる（カメラが機体を中央に置くため、`translate` の値は常に `(screen.width / 2, screen.height / 2)` = `(640, 360)`）。回転が `0` ちょうどのときは画素合わせで描かれ、それ以外は画像の補間で描かれる（ENGINE_API 25章「描かれる位置と大きさ」）。位置は動かないので、前の作業の懸念事項「画素合わせによる動きの段差」は土台の機体では起きない。

### 要件2: 見比べ用の一時的な切り替え（決定事項）
**状態の置き場所（決定）:** 新しいファイル `js/scenes/bakeToggle.js` に置く（`slow.js` と同じく、状態とその切り替えだけを持つ）。
* モジュールの中の変数 `baked`（既定 `true`）に持つ。ページを開いている間だけ持ち、`Storage` には保存しない（再読み込みで ON に戻る）。シーンのインスタンスに持たないので、タイトルとプレイを行き来しても状態はそのまま続き、タイトルとプレイの両方の機体に効く。「タイトルに戻る」でも元に戻さない（スローと違い、タイトルでも見比べられるようにするため）。
* export は2つ: `isBaked()`（読み取りのみ。`draw` から呼んでよい）、`toggleBaked()`（切り替え。入力の配信の中から呼ぶ）。import は無い。
* ファイル全体の目印 `/* ozengine sample */` を責務定義の直後に付ける。このファイルを import するのは、目印の付いたファイル（`FlightScene.js`・`playMenu.js`）だけにする。目印の無い `MenuScene.js`・`BootScene.js`・`js/ui/`・`js/main.js` からは import しない（憲法3章「サンプルコードの目印」）。

**切り替えの操作（決定）:**
* メニューの項目: プレイ中のメニュー（`js/scenes/playMenu.js`）の「ミュート」と「タイトルに戻る」の間に、ラベルが関数の項目 `isBaked() ? '焼き付け: ON' : '焼き付け: OFF'` を足す。選ぶと `toggleBaked()`。項目のキーは `KeyB`（メニューを開いているときも B キーで選べる）。項目は5つになる（`MenuScene` は項目の数に合わせて縦に並べるので、`MenuScene.js` は変えない。5項目の高さ 80×5 + 24×4 = 496 は画面の高さ 720 に収まる）。
* PC のキー: `KeyB`（B キー。Bake の頭文字）。今の割り当て（`ArrowLeft`・`ArrowRight`・`Space`・`KeyS`・`KeyP`・`KeyM`、boot 画面の `Escape`）と重ならない。`FlightScene.onKeyDown` で受けるので、タイトルとプレイの両方で効く（`PlayScene.onKeyDown` は先に `super.onKeyDown(code)` を呼んでいるので、そのまま効く）。boot 画面とロード画面では効かない（boot 画面では B キーも「次へ進む」になる）。
* スマートフォン: プレイ中のメニューの項目で切り替える（タイトルにはメニューが無いので、タイトルでは切り替えられない。状態は表示で分かる）。

**状態の表示（決定）:** タイトルとプレイの両方で、右上の状態表示の3行目（1行目「ミュート中」、2行目「スロー」の下）に、常に「焼き付け: ON」または「焼き付け: OFF」を描く（タイトルへ戻っても状態が分かるようにする）。
* 描く関数は、今の状態表示と同じく `js/scenes/uiText.js` に `drawBakeLabel(ctx, screen, baked)` として足す（`uiText.js` は `bakeToggle.js` を import せず、状態は引数で受け取る。`drawSlowLabel` を `PlayScene` が `isSlow()` を見て呼ぶのと同じ分け方）。
* 呼ぶのは `FlightScene.draw` の `ui` レイヤー（`drawMuteLabel` の後）で、`drawBakeLabel(ctx, this.screen, isBaked())` とする。

**描き分け:** `FlightScene.drawShip` の中で、`isBaked()` が真なら `this.shipImage.draw(ctx)`、偽なら `shipSprite.draw(ctx)`（今までの描き方）を呼ぶ。`draw` の中では状態を読むだけで変えない。切り替えても焼き付けは作り直さず、手放しもしない（OFF の間は焼き付けが描かれないので、自動の焼き直しもその間は起きず、ON に戻した最初の描画で必要なら焼き直される。ENGINE_API 25章「自動の焼き直し」）。

**一時的なコードの目印:** 切り替えのために足すコード（import・定数・分岐・項目・関数）の JSDoc か直前のコメントに「見比べ用の一時的な切り替え（テストプレイの後に消す）」と書き、消すタスクで漏れなく見つけられるようにする。消すタスクでは `bakeToggle`・`isBaked`・`toggleBaked`・`drawBakeLabel`・`BAKE_` を `js/` から grep して、残っていないことを確かめる。

**消したあとの形（タスク5）:** `bakeToggle.js` を削除し、`FlightScene.js`・`playMenu.js`・`uiText.js` から切り替えのコードを除く。機体は常に `this.shipImage.draw(ctx)` で描かれ、メニューは今の4項目（閉じる・スロー・ミュート・タイトルに戻る）に戻り、右上の3行目の表示も無くなる。`FlightScene.js` の `shipSprite` の import は、焼き付けの `create` に使うので残す。

### 要件4: `oz/ENGINE_API.md` の仕上げ
**計画の時点で確かめた結果:**
* 25章の使い方の例（スプライトJSの `bounds` を渡す例）は、要件1の土台の書き方（`init` で `create`、`draw` で `translate`・`rotate` の後に焼き付けの `draw(ctx)`、`destroy` で `dispose`）と同じ形である。`scale` を省いて既定の `1` を使う点も同じ。
* 「注意」の1項目目（`scale` と大きく違う倍率で描くと、拡大ではぼやけ、縮小では細い線が淡くなる。大きさを変えて描くならその大きさの `scale` で別に焼き付ける）は、REQ の求める内容をすでに満たしている。
* 「自動の焼き直し」は、描かれていない焼き付けは次に描くときに焼き直されることが読み取れる（「次にその焼き付けを描くときに、エンジンが焼き直す」）。

**直すこと（決定。タスク3で行う）:**
1. **派生クラスでの `init`・`destroy` の注意を足す:** 土台では `TitleScene`・`PlayScene` が `init` を上書きしていて、基底の `FlightScene.init` を呼ぶ必要があった。同じ形（基底のシーンで焼き付けを持つ）は新しいゲームでも起きやすいので、25章「作れる時期」に次の趣旨の1項を足す。
   * シーンの基底クラス（自分で作った `Scene` の派生クラス）の `init` で作り `destroy` で手放す場合、そのクラスをさらに継承したクラスで `init`・`destroy` を書くときは、`super.init()`・`super.destroy()` を呼ぶ。呼ばないと、焼き付けが作られずに描こうとしてエラーになる、または手放されずに画像のメモリが残る。
2. **23章から25章への参照を足す:** 23章「使い方の例」の例のコードの後に、多数のスプライトを毎フレーム描くときは、キャンバスキャッシュ（25章）で焼き付けておき、同じ書き方（`draw(ctx)` を呼ぶ）で描けることを1文で足す（23章「使い方」の `bounds` の項は範囲としての参照だけで、使い方への案内が無いため）。
3. **土台に組み込んだ結果による見直し:** タスク1・2の実装で、25章のとおりに書いて動かないこと・分からないことが記録されていれば（5章「懸念事項」）、それに合わせて25章を直す。記録が無ければ、上の1・2のほかは変えない。

* `oz/ENGINE_API.md` を変えるので、タスク3の最後に `oz/FINGERPRINTS.txt` を作り直し、`node --test` が `fail 0` であることを確かめる。

## 5. 懸念事項・要確認ポイント

### 懸念事項
* **回転したときの柔らかさ:** 機体はほぼ常に回転して描かれるので、焼き付けは画像の補間で描かれる（ENGINE_API 25章）。直接描く（ベクター）よりわずかに柔らかく見えることがある。テストプレイで「区別がつく」「ぼやける」と判断された場合は、推測で直さず、現場設計セッションに返す（エンジンの直し方は設計で判断する）。
* **ウィンドウの大きさを手で変えている間の負荷:** 画素の倍率がほぼ毎フレーム変わり、そのたびに機体の焼き直しが起きる（前の作業の RES の懸念事項）。土台では焼き付けは1つだけなので重くならない見込みだが、発注者が判断する。
* **OFF の間の焼き直し:** 切り替えが OFF の間は焼き付けが描かれないので、その間に画面の大きさが変わっても焼き直されない。ON に戻した最初の描画で焼き直されるので、古い粗い絵は出ない想定である（ENGINE_API 25章「自動の焼き直し」）。
* **切り替えの状態:** ページを開いている間だけ持ち、保存しない。再読み込みで ON に戻る。「タイトルに戻る」でも元に戻らない。
* **タイトルでの切り替え:** スマートフォンのタイトルにはメニューが無いので、タイトルでは切り替えられない（プレイ中のメニューで切り替えてから「タイトルに戻る」で見る）。PC は B キーでタイトルでも切り替えられる。
* **タスク5の実行の時期:** タスク5は、発注者のテストプレイの OK の後に、実行の指示があってから行う。それまでは土台に一時的な切り替え（メニューの5項目目と右上の3行目の表示）が残る。
* **タスク5の実行済み:** 切り替えのコードは消えた。「タスク5の後の短い確認」（目視）を推奨する。
* **エンジンの変更:** 計画の時点では、`oz/src/` の変更が要るところは見つかっていない。

### 目視確認推奨箇所（テストプレイ。タスク1・2の後、タスク5の前）
GitHub Pages で公開したページ（`/ozengine-web/` の下。リポジトリ `doze7220/ozengine-web` の場合は `https://doze7220.github.io/ozengine-web/`。末尾の `/` まで入れて開く）を、PC とスマートフォンで開く。boot 画面で画面に触れる（キーを押す）とタイトルに進み、タイトルで画面に触れるとプレイが始まる。

**見比べ用の切り替えの操作方法**
* PC: タイトルでもプレイでも、**B キー**を押すたびに「焼き付けで描く」と「直接描く」が切り替わる。プレイ中は、メニュー（画面上の「メニュー」ボタン、または P キー）の項目「焼き付け: ON」／「焼き付け: OFF」を押しても（メニューを開いた状態で B キーを押しても）切り替わる。
* スマートフォン: プレイ中に画面上の「メニュー」ボタンを押し、項目「焼き付け: ON」／「焼き付け: OFF」を押す。押すたびに表示が切り替わる。「閉じる」で戻る。
* 今の状態は、タイトルとプレイの右上（「ミュート中」「スロー」の下の3行目）に「焼き付け: ON」または「焼き付け: OFF」と出る。開いた直後は「焼き付け: ON」（既定）。

**確かめること（操作 → 期待する結果）**
1. 見た目の区別: プレイ中に左右キー（スマートフォンはスティック）で機体を回転させながら、切り替えを何度か ON／OFF する（タイトルの自動操縦のデモでも、PC は B キーで同じように見る）。 → ON と OFF で、機体の位置・大きさ・くっきり具合の区別がつかない。回転したときにギザギザが目立たず、ぼやけすぎない。
2. 大きさ・向き・拡大率を変えたとき（切り替えは ON）: PC でウィンドウの大きさを変える、ブラウザの拡大率を変える（Ctrl + `+`／Ctrl + `-`、Ctrl + `0` で戻す）。スマートフォンで画面の向きを縦・横に変える。 → 変えた後も機体がぼやけない（古い粗い絵が残らない）。B キー（スマートフォンはメニュー）で OFF にして見比べても、くっきり具合が同じ。
3. 縁: ON で機体の先端（右）と左後ろの2つの角をよく見る。OFF と見比べる。 → 縁や角が欠けていない（切れていない）。
4. 大きさを変えている間の重さ（PC）: ON のまま、ウィンドウの端をつかんで大きさを続けて変える。 → 動きが重くならない（機体・星の動きがカクつかない）。気になるかどうかを判断する。
5. 行き来: プレイ → メニュー →「タイトルに戻る」→ タイトルで画面に触れてプレイ、を3回以上くり返す。ON と OFF のどちらの状態でも行う。 → エラーにならず（PC では開発者ツールのコンソールに赤いエラーが出ない）、毎回タイトルとプレイで機体が表示される。右上の「焼き付け: ON／OFF」の表示が、行き来しても切り替えた状態のまま続く。
6. メニューの並び: プレイ中にメニューを開く。 → 「閉じる」「スロー: ON／OFF」「ミュート: ON／OFF」「焼き付け: ON／OFF」「タイトルに戻る」の5つが縦に並び、画面に収まっている。

問題が出た場合は、どの手順で、どの端末・ブラウザで、どう見えたか（ON と OFF のどちらで）を、実装セッションに伝える。実装セッションは推測で直さず、現場設計セッションに返す。
