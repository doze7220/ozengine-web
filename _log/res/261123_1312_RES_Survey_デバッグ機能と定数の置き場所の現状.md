**全タスク共通の制約**

* 今回やらないこと: コード・資料の修正、直し方の決定、他のリポジトリの調査、UI 部品や描画の性能の調査。

#### 数え方（タスク4〜11・16 で共通）
変えたときは、そのタスクの『調査内容』に変えた点と理由を書く。

* **(a) 名前の付いた定数**: モジュールの先頭の `const`、クラスの `static`、定数として使われる凍結したオブジェクト・配列など。名前の数と、値の数（オブジェクト・配列の場合は末端の値ごとに1件）の両方を書き、**集計には値の数を使う**。`0`・`1`・`-1` も名前が付いていれば数える。モジュールの状態を入れる変数（`let`、空の `Map` など）、関数、import した名前の別名は数えない。ほかの定数から計算で求める定数は1件と数え、式を値の欄に書く。
* **(b) 直接書かれた値で、名前の付いた定数にしたほうがよいと考えられる値**: 処理の中・引数の既定値・その場のオブジェクトに直接書かれた値。同じファイルの中で同じ意味で使う同じ値は1件とし、出現数を併記する。
* **(c) 同じ値が複数の場所にあるもの**: (a)・(b) と重なる別の数え方で、(a)・(b) の合計には足さない。**組の数**と、その組に入る**場所の数**を書く。名前が付いているかを問わない。import して共有している値は1つの場所と数える（写しではないため）。
* **(b) に数えないもの（REQ の指定）**: `0`・`1`・`-1`、半分にするための `2`、配列の添字、`Math.PI` を使った角度の一周などの自明な値、エラー文・JSDoc の文章、イベント名・型の判定に使う言語やブラウザ側で決まっている文字列。(c) でも、これらが同じであることだけを理由に組を作らない。
* **迷う値の種類の扱い（この計画で決めたもの）**:
  * 単位の換算の `1000`（ミリ秒と秒）: (b) に数えない。出現する場所を「数えなかった値」に書く。
  * `console.*` の文（`[oz]` を含む）: エラー文と同じ扱いで数えない。
  * import のパス、オブジェクトの項目名、クラス名・関数名: 数えない。素材のファイル名・パスは数える。
  * `KeyboardEvent.code` の値（キーの割り当て）、レイヤー名、素材の名前、保存に使う名前: 数える。
  * 画面に出す文字（ボタンの文字、見出しなど）: 数える。(b) の中の「画面の文字」として件数を分ける。
  * エンジンが決めた種類の名前（ポインタの種類、描く関数の種類、位置の名前など。ブラウザが決めた名前と同じ綴りのものを含む）: 数える。(b) の中の「種類の名前」として件数を分ける。
  * Canvas 側で決まっている文字列（`textAlign`・`lineCap` の値など）: 数えない。色・フォントの指定は数える。
  * 画面の中の位置・大きさ（座標）: 数える。
  * 上にない迷う種類が出たら、数えたか数えなかったかと理由を、そのタスクの『調査内容』に書く。前のタスクの4章に同じ種類の扱いがあれば、それに合わせる。
* **(a)・(b) の値ごとの種類**: 数・色・フォント・名前（キー、レイヤー、素材、保存）・画面の文字・種類の名前・その他。
* **値の分類の記号（2-4）**: `E` = エンジンの内部の値、`G` = ゲームごとに変えたい値、`B消` = 土台の値で新規プロジェクトの手順の後に消えるもの（目印の中）、`B残` = 土台の値で残るもの（目印の外）。1つに決まらない値は `E/G`・`G/B消`・`G/B残` のように両方を書く。`oz/` の値は `E`・`G`・`E/G`、`js/` の値は `G`・`B消`・`B残`・`G/B消`・`G/B残` のどれかになる。`G` を含む値には、既に起動設定・引数で変えられるか（その手段）と、`js/` の場合は目印の中か外かを書く。`G`・`B` などの分け方はコードだけから決まらないので、判断の理由を『推測・所見』に書く。
* **値の台帳の形（タスク4〜9）**: ファイルごとに次の表を『事実』に書く（分類の列だけは判断なので、列の見出しに「（判断）」と書く）。「(b) にしたほうがよい」と考えた理由は『推測・所見』に種類ごとにまとめて書く。

  | 番号 | 行 | 名前（なければ「なし」） | 値 | (a)/(b) | 種類 | 出現数（行） | 分類（判断） |
  | --- | --- | --- | --- | --- | --- | --- | --- |

  番号は `タスク番号-通し番号`（例 `4-1`）。似た値が続くときは、(a)/(b)・種類・分類がすべて同じときに限り1行にまとめ、件数を書く（1つでも違うときは行を分ける）。表の後に、ファイルごとの「(a) 名前の数・値の数／(b) の件数（種類別）／分類ごとの件数／数えなかった値の種類」と、コメント・JSDoc に書かれた値（行・書かれている値・指している元の値が分かればその場所）の一覧を書く（後者はタスク15の材料）。0件のファイルも「0件」と書く。

### 要件3: すでに定数がまとまっている場所と、その書き方の違い
* 値がまとまっている場所を洗い出し、場所ごとの書き方の違いを表で比べる。同じ役割の値が場所によって違う形で書かれている例を挙げる。

### 要件4: 定数を外に出すときにぶつかる点

* `js/` から `oz/src/` の値を使いたいときの経路（`oz/index.js` から公開されているもの、されていないもの）を示す。

#### R7: 値の受け渡しと依存の向き（同 3章、4章の末尾）
`Engine` が各モジュールを生成する（`Layers` と `DebugOverlay` には、起動設定の `width`・`height` を論理解像度として渡す）。`Engine` は `DebugOverlay` を起動設定の `debug` にかかわらず常に作り、`debug` を表示の有無の起動時の値として設定する（`GameLoop` へは常にインスタンスを渡す）。`Time`・`Scenes`・`Layers`・`Input`・`DebugOverlay` のインスタンスを `GameLoop` へ、`Screen`・`Scenes`・`Buttons` のインスタンスに加え、`Keys`・`VirtualPads` を `Input` へ、`VirtualPad` を `VirtualPads` へ引数で渡すので、`GameLoop` と `Input` と `VirtualPads` はこれらを import しない。`Scenes` と `Layers` も互いを import しない。`Engine` は起動時（最初のシーンを積む前）に、画素の倍率（Canvas の画素数 ÷ 論理解像度）の求め方を関数として `CanvasCache` へ渡すので、`CanvasCache` は `Screen` を import せず、`Screen` も `CanvasCache` を知らない。同じく起動時（最初のシーンを積む前）に、論理解像度（起動設定の `width`・`height`）を `Ui` へ渡す（`setUiScreenSize`）ので、`Ui` は `Engine`・`Screen` を import しない。窓（`Ui.createWindow` の戻り値）はシーンが持ち、ポインタはシーンの `onPointer` から窓へ渡される（`Input` は `Ui` を知らず、窓は `Engine.addButton` と入力の仕組みに登録されない）。

依存の向きは次のとおりで、逆向きの import を禁止する。

```
利用側の js/ → oz/index.js → Engine / Scene / Assets / Sound / Storage / CanvasCache / Ui
Engine → Scene / GameLoop / Time / Screen / Scenes / Layers / Input / Buttons / Keys / VirtualPad / VirtualPads / DebugOverlay / CanvasCache / Ui

Scene・GameLoop・Time・Screen・Scenes・Layers・Input・Buttons・Keys・VirtualPad・VirtualPads・DebugOverlay・Sound・Storage・CanvasCache は他のエンジンモジュールに依存しない。
UI 部品のファイル（Ui・UiWindow・UiButton・UiValue・UiCheckbox・UiSlider・UiChoices・UiPartKinds・UiTabs・UiScroll・UiScrollGesture・UiSpec・UiRect・UiMetrics・UiRenderer・UiStandardLook）は、UI 部品のファイルどうし以外のエンジンモジュールに依存しない。中の向きは Ui → UiWindow・UiRenderer、UiWindow → UiSpec・UiMetrics・UiRect・UiButton・UiPartKinds・UiTabs・UiScroll、UiPartKinds → UiButton・UiValue・UiCheckbox・UiSlider・UiChoices、UiScroll → UiSpec・UiMetrics・UiRect・UiPartKinds・UiScrollGesture、UiScrollGesture → UiMetrics、UiButton・UiValue・UiCheckbox・UiSlider・UiChoices・UiTabs → UiSpec・UiMetrics・UiRect、UiRenderer → UiStandardLook。
例外: Assets → Sound（音声のデコードと、名前で預けるため）。
```

`Engine`・`GameLoop`・`Input` は `Assets`・`Sound`・`Storage` を import しない。

**エンジンに入れないもの:** スプライトの描画処理（絵の中身を描くこと。`CanvasCache` は渡された描く処理を呼んで焼き付けるだけで、これと両立する）、アニメーション、カメラ、当たり判定、物理、パーティクル、Entity基底クラス、遷移演出。必要になったPhaseで、発注者の承認を得てから検討する（憲法3章「先回り実装の禁止」）。

#### R10: 憲法3章（`PROJECT_CONSTITUTION.md`）
本章では、エンジン本体（`oz/`）を「エンジン」、エンジンを使う側（`index.html`・`js/`・`assets/`）を「利用側」と呼ぶ。

*   **依存方向は一方向のみ:** 依存は「利用側 → エンジン」だけを許可する。エンジンから利用側（`js/`・`assets/`）を import してはならない。ゲーム固有の処理は、シーンやコールバックとして利用側から受け取ること。
*   **ゲーム固有知識の混入禁止:** エンジンに、ゲーム名、シーン名、レイヤー名、解像度、キー割り当てなどを固定値で書いてはならない。これらは利用側から設定すること。
*   **入口の一本化:** エンジンの公開APIは `oz/index.js` からのみ export すること。`oz/index.js` には再export以外の処理を書いてはならない。利用側から `oz/src/` を直接 import してはならない。
*   **公開APIとドキュメントの同時更新:** 公開APIを追加・変更・削除するタスクでは、同じタスク内で `oz/ENGINE_API.md` を更新すること。`oz/src/` を読まなくても利用側を実装できる内容を保つこと。
*   **利用側での基礎処理の直書き禁止:** `js/` に `requestAnimationFrame`・`addEventListener`・`getContext` を書いてはならない。必要な機能がエンジンにない場合は、回避コードを書かず、RESに記録して発注者の判断を仰ぐこと。
*   **利用側の実装で `oz/src/` を読むことの禁止:** `js/` を実装するタスクでは、`oz/src/` を読まず、`oz/ENGINE_API.md` だけを参照すること（2章の閲覧の許可より本項を優先する）。ドキュメントで分からないことは、RESに不足として記録すること。
*   **サンプルコードの目印:** `js/` のうち、新規プロジェクトで消す前提のコードには目印を付けること。ファイル全体なら責務定義の直後に `/* ozengine sample */` を書き、ファイルの一部なら `/* ozengine sample: begin */` と `/* ozengine sample: end */` で囲む。目印の付いた部分をすべて消しても、エラーなく起動できる状態を保つこと。
*   **時間の受け渡し:** 経過時間は最上位のループから引数で渡すこと。ループと時間管理を担うモジュール以外が、`performance.now()` などで独自に時間を取得してはならない。例外として、`Sound` は音の予定時刻にだけ `AudioContext.currentTime` を使ってよい。その値をゲームの更新や描画に使ったり、公開したりしてはならない。
*   **グローバル汚染の禁止:** `window` にプロパティを追加してはならない。すべてのオブジェクトはモジュール内でカプセル化すること。
*   **先回り実装の禁止:** REQで求められていない機能を、将来必要になりそうという理由で実装してはならない。アニメーション、カメラ、当たり判定、Entity基底クラスなどは、実際に必要になったPhaseで発注者の承認を得てから追加すること。
