# RES: 作業計画・作業レポート Phase 06-01 : 起動設定 `debug` の意味
* 参照元REQ: `./_log/req/261124_1257_Phase06-01_起動設定debugの意味.md`

## 1. 作業目的
起動設定 `debug` は、今は FPS の表示の起動時の値（`Engine.fpsVisible`）を決めるだけで、ゲームからは読めない。これを「開発モードで起動したか」を表すものにし、`Engine.debug`（読み取り専用）でゲームが読めるようにする。公開するゲームで、開発用の入口をゲームが隠せるようにするための土台である。

あわせて、土台の `js/main.js` の URL の `?debug` を読む処理を `ozengine sample` の目印の外へ移し、新規プロジェクトで見本を消した後も使えるようにする。`?debug=0` は開発モードにしない。

エンジンは、開発モードかどうかで、起動時の FPS の表示のほかの動きを変えない。起動設定を変えていない既存のゲームの動きは変わらない。開発用の入口の出し分け（`js/scenes/` の変更）は今回しない。

## 2. アーキテクチャ設計

### 今の作り（計画のために確かめた結果）
* **`oz/src/Engine.js`:** `start` の中で `newOverlay.visible = Boolean(config.debug);` を行うだけで、`debug` の値は保持していない。読み取り専用の値（`Engine.fps`・`Engine.virtualPadEnabled`・`Engine.virtualPadTouched`）は、どれもオブジェクトリテラルの getter だけ（setter なし）である。代入は strict モードで `TypeError`、strict でないコードでは無視される。
* **最初のシーンの `init`:** `start` の中で、モジュールの変数（`overlay`・`time`・`scenes`・`buttons`・`keys`・`pads`）を入れた後の `newScenes.push(config.scene)` から呼ばれる。したがって、この `push` より前に開発モードの値を入れておけば `init` から読める。
* **起動前の判定:** `requireStarted(apiName)` が `scenes === null` なら `[oz] <API名>: Engine.start の前には使えません` を投げる。JSDoc には「（バーチャルパッドの操作用）」と書かれている。
* **`js/main.js`:** `config.debug = new URLSearchParams(location.search).has('debug');` が `ozengine sample` の範囲の中にある。今は `?debug=0` でも真になる。
* **`debug` の古い意味が書かれている箇所:** `oz/ENGINE_API.md` は 3章の表の `debug` の行と、14章の `Engine.fpsVisible` の行・その下の箇条書きの3か所だけである（`debug` を含む行の全文検索で確かめた）。`Engine.js` では `config.debug` の JSDoc の1か所である。
* **自動テスト:** 今の状態で `node --test` は `tests 514`・`fail 0`。`Engine` は対象外のままにする（要件6）。

### 要件3: 土台の URL の指定（`js/main.js`）
* 目印の外（`screen` の定義の直後、`config` の定義の前）に、次の定数を置く。

    ```js
    /**
     * 開発モードで起動するか。真なら Engine.debug が true になり、FPS を表示した状態で始まる。
     * URL に ?debug を付けて開くと真になる（?debug=1 など、0 以外の値も真）。付けないときと ?debug=0 のときは偽。大文字の ?DEBUG は指定とみなさない。
     * 偽に固定するなら、右辺を false に書き換える。
     * @type {boolean}
     */
    const debug = ![null, '0'].includes(new URLSearchParams(location.search).get('debug'));
    ```

    * `get('debug')` は、指定が無ければ `null`、`?debug` なら `''`、`?debug=0` なら `'0'` を返す。`null` と `'0'` だけを偽とするので、REQ の表のとおりになる。`URLSearchParams` は大文字と小文字を区別し、`?a=1&debug` のように並べても同じに働く。同じ名前が2つ以上あるときは先頭の値で決まる（`?debug=0&debug` は偽）。
    * 偽に固定するときは、この右辺の1か所を `false` に書き換えるだけで、使われない変数や関数は残らない。
* `config` に `debug,` を足す（`scene` の行の直後、`virtualPad` の行の前）。`config` の JSDoc に、`scene:` の行と `virtualPad:` の行の間へ次の1行を足す。`@type` は変えない（`debug?: boolean` がすでにある）。

    ```js
     * debug: 開発モードで起動するか（上の debug の値）。
    ```

* 目印の範囲からは `config.debug = new URLSearchParams(location.search).has('debug');` の行だけを消す。`LoadScene`・`TitleScene` の import と、`config.layers`・`config.scene` の書き換えは目印の中に残す。目印の行そのものは変えない。

     * 責務: Engine.start の呼び出しと、開発モードの指定（URL の ?debug）、レイヤーと最初の画面の流れ（boot 画面と次の画面）の定義を行う利用側のエントリポイント。

新しい節の文面は次のとおりとする。

````markdown
### 開発モード（`debug` と `Engine.debug`）

起動設定 `debug` は、開発モードで起動するかどうかを表す。ゲームは `Engine.debug` で読み、開発用の入口（開発用のキーやメニューの項目など）を出すかどうかを決める。

| API | 読み書き | 値 |
| --- | --- | --- |
| `Engine.debug` | 読み取りのみ | 起動設定 `debug` を `Boolean(...)` で解釈した `true` / `false`（`debug` を省くと `false`） |

* **読める時期:** `Engine.start` の後。最初のシーンの `init` の中でも読める。`Engine.start` の前に作るシーンの `constructor` では読めない（エラー）ので、`init` の中か、それより後に読む。
* **変わらない:** 値は `Engine.start` のときに決まり、その後は変わらない。変える方法は無い。
* **FPS の表示との関係:** 真なら FPS を表示した状態（左上）で、偽なら表示しない状態で始まる。起動した後の `Engine.fpsVisible`（14章）と `Engine.debug` は互いに影響しない。FPS の表示を消しても `Engine.debug` は変わらず、開発モードでなくても `Engine.fpsVisible` で FPS を表示できる。
* **ほかの動きは変わらない:** エンジンは、開発モードかどうかで、起動時の FPS の表示のほかの動き（FPS の計算、警告、`timeScale`、入力、描画など）を変えない。開発用の入口を隠すのはゲームである。
* **真にする条件:** エンジンは URL などを見ない。どういうときに `debug` を真にするかは、`Engine.start` を呼ぶ側が決めて渡す。

使い方の例（開発用のキーを、開発モードのときだけ受け付ける）:

```js
onKeyDown(code) {
  if (code === 'KeyF' && Engine.debug) Engine.fpsVisible = !Engine.fpsVisible;
}
```

エラー:

* **起動前に読む:** `Error`（`[oz] Engine.debug: Engine.start の前には使えません`）。
* **代入:** 起動の前後にかかわらず、strict モードのコード（ES Modules の中。ゲームのコードは常にこれ）では `TypeError` で、値は変わらない。strict でないコード（開発者ツールのコンソールなど）ではエラーにならず無視され、値は変わらない。
* フレーム処理の中でこれらのエラーを起こすと、ほかの例外と同じくループが止まる（15章）。
````
